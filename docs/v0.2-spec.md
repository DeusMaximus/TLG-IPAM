# TLG-IPAM v0.2 — Scan agents and remote MCP

**Status:** accepted (draft 5) · 13/11/2026 · tracked as GitHub milestones M0–M3
**Extends:** `TLG-IPAM-Project-Brief.md` v1.1 (which lists "discovery agents or active network scanning" as a v1 non-goal — this spec lifts that)
**Audience:** the project owner, and whichever coding agent implements it. This is the contract for work that has not shipped; the brief describes what `main` does. Each PR folds the behaviour it ships into the brief.

Domains in this document are placeholders (`example.com`, `home.arpa`), per the repo convention. The document names no person, real domain, or real address.

**Changes in draft 2:** remote MCP uses a built-in OAuth server instead of an external identity provider (§6); new security model section (§7); remote grants are read-only by default; separate `OWNER_PASSWORD`; forward-DNS and `request_scan` restrictions; settled decisions recorded (§9).

**Changes in draft 3:** one agent per VLAN is the documented pattern; guided agent install from the Agents page with single-use enrolment tokens (§5.6); agent version reporting; remaining decisions settled (§9).

**Changes in draft 4:** agent code source settled (GitHub: container registry image and release wheel); minimum Python for the systemd install settled at 3.11 (§9). Otherwise identical to draft 3.

**Changes in draft 5:**

- **Scan scope (§5.3, new):** the DHCP pool is not scanned unless enabled per subnet; each reserved range can be excluded from scanning.
- **ARP** is an active request/reply sweep, not a read of the kernel neighbour table (§5.2).
- **Jobs are leased**, incomplete scans never mark addresses dead, and the agent reports live addresses only (§5.1, §5.7).
- **Findings have a key**; accept is conditional on the observation being unchanged; dismissals move to their own table (§5.5).
- **Enrolment:** tokens table carries enrolment tokens; agents can be re-enrolled without losing their scan targets; install commands corrected (§4.2, §5.6).
- **Linking uses a one-time code from the private UI** in place of `OWNER_PASSWORD`, which is removed (§6).
- Remote write access uses OAuth scopes; the write setting is honoured in both directions; refresh rotation has a retry window (§6.4, §6.5).
- New nullable `changes.actor` column for audit attribution (§4.3).
- `Host.last_seen` semantics, the `stale` status value, and subnet-deletion cleanup aligned with the current code (§5.4, §5.5).
- M2 split into M2a and M2b (§2).

**Changes from the review of PR #1:**

- Forward-DNS results have a table, `fdns_results` (§5.4, §5.7).
- The systemd agent's token file is owned by the service user, and `install` does the enrolment exchange (§5.6).
- A scan target needs a liveness method, and a job can only mark addresses dead when it ran one (§5.2, §5.7).

## 1. Goals and non-goals

**Goals**

1. A remote **scan agent** that checks in to the server, receives its scan instructions, and reports what it sees: which addresses respond, their MAC addresses (same-L2 subnets only), and their DNS names.
2. Scan results are **suggestions, never automatic writes**. The owner (or an assistant over MCP) accepts or dismisses each one.
3. The MCP endpoint can be reached at a **public HTTPS URL** by web-only clients (Claude.ai, ChatGPT, Gemini, Mistral) using OAuth, **with no external identity provider required**.
4. The same image supports three ways of running it, chosen by configuration alone: local with a static key, remote with built-in OAuth, and remote behind the operator's own access proxy.
5. Move to **FastMCP 4** and pin dependencies.

**Non-goals for v0.2**

- Native OIDC login. Deferred; see §6.7 for how operators get SSO without it.
- Port scanning, service detection, OS fingerprinting, SNMP.
- Uptime history or time-series data. One row per address holding the latest state; trends belong in a monitoring system.
- Multi-user accounts or roles. Still single-owner.
- Agents for Windows or macOS. Linux only.
- Pushing changes *to* DNS or DHCP. Read and compare only.
- IPv6 scanning.

**Permanent non-goals** (security invariants, §7.2)

- Remote command execution or server-driven self-update on the agent.
- Scan or agent configuration over MCP.

### 4.1 FastMCP 4

### 4.2 Credentials

Today one static `API_KEY` is shared by the SPA, REST callers, and MCP clients, sent as `X-API-Key`. Each new kind of caller gets its own, narrower credential.

| Credential | Presented as | Stored | Can reach |
|------------|--------------|--------|-----------|
| Owner key (`API_KEY`, env) | `X-API-Key` on REST; `Authorization: Bearer` on `/mcp` | env | everything |
| Enrolment token (`tlge_…`; M2b) | once, in the install command | `tokens` table, hashed; single-use, expires after 1 hour | `POST /api/v1/agent/enrol` only |
| Agent token (`tlga_…`) | `Authorization: Bearer` | `tokens` table, SHA-256 hash + display prefix | `/api/v1/agent/*` only |
| Link code (M3) | typed into the consent page | memory, hashed; single-use, expires after 10 minutes | approves one OAuth client link — nothing else |
| OAuth grant (M3) | `Authorization: Bearer` | OAuth tables, tokens hashed | `/mcp` only; read-only unless enabled |

- `/mcp` moves from the hand-rolled `APIKeyASGIMiddleware` to FastMCP's own `auth=`. In M1 that is a small `TokenVerifier` that accepts the owner key and returns both scopes (§6.5). No deployed clients exist to break, so `X-API-Key` on `/mcp` is dropped rather than kept as an alias; README examples for `mcp-remote` change to `--header "Authorization: Bearer …"`.
- The owner key is compared in constant time (`hmac.compare_digest`) on both REST and `/mcp`. Today's check in `auth.py` uses `!=`.
- New table `tokens`:

  | Field | Notes |
  |-------|-------|
  | `id` | uuid |
  | `kind` | `agent` or `enrol` |
  | `agent_id` | FK → agents. An agent can hold several rows over time; at most one unrevoked `agent` token |
  | `token_hash`, `token_prefix` | SHA-256; prefix for display |
  | `created_at`, `last_used_at` | |
  | `expires_at`, `used_at` | enrolment tokens only |
  | `revoked_at` | |

  A token is shown once, at creation. In M2a the Agents page creates an agent and its `agent` token directly; M2b adds the `enrol` kind.
- Token create/revoke is audit-logged (`entity_type="token"`).

### 4.3 Audit attribution

The change log gains one nullable column, `changes.actor` (str(80)). It holds who acted when that is narrower than the `source`:

| Source | Used for | `actor` |
|--------|----------|---------|
| `ui`, `api` | unchanged | null |
| `mcp` | MCP tool writes | null for the owner key; `grant:<client name>` for an OAuth grant |
| `agent` | enrolment, agent self-reported errors that change agent state | `agent:<agent name>` |
| `oauth` | grant issued, grant revoked by refresh reuse, link code burned | `grant:<client name>` or null |

- New values fit the existing `source` column (8 characters).
- The client name is self-declared by the client and is later read back over MCP through `list_changes`. It is sanitised once, at registration: printable characters only, at most 60. It goes in `actor`, never interpolated into `summary`.
- `ChangeOut` and the `list_changes` tool return `actor`.

## 5. M2 — Scan agent

### 5.1 Model

```
agent ──outbound HTTPS──▶ server
  1. POST /api/v1/agent/checkin   → "here is who I am and what interfaces I have"
                                  ← "scan these ranges now, with these methods"
  2. (agent scans)
  3. POST /api/v1/agent/results   → live addresses for one job
```

- **Pull only.** The agent makes outbound requests; nothing listens on it. This works whether the server is on the same LAN, behind a tunnel, or on a VPS.
- **Stateless agent.** Configuration on the agent is a server URL, a token, and a safety allowlist (§5.6). The server decides what is due. "Scan now" in the UI marks a subnet due; the agent picks it up at its next check-in (default 60 s).
- **Server is the scheduler.** It tracks `last_scan_at` per target and returns only the targets that are due.
- **Jobs are leased.** Issuing a job stores `current_job_id` and `job_issued_at` on the target. A target with a live lease is not issued again. The lease expires after the per-job timeout plus a margin (defaults: 10-minute timeout, 15-minute lease), after which the target is due again. The agent keeps checking in on schedule while it scans and runs jobs one at a time.
- **Fixed vocabulary.** A job names a subnet, address ranges inside that subnet, and a subset of the methods in §5.2. There is no field through which the server can send a command, a script, a binary, or a target outside the subnet.

### 5.2 Scan methods

| Method | What it does | Works across a router? | Notes |
|--------|--------------|------------------------|-------|
| `icmp` | Echo sweep of the job's ranges | Yes | Misses hosts that drop ping |
| `arp` | ARP request to each address in the job's ranges; a reply means alive and supplies the MAC | **No — same L2 only** | Catches hosts that drop ping. One request and one retry per address |
| `rdns` | PTR lookup for each live address | Yes | Queries the subnet's `dns_servers` (already on the `Subnet` model), falling back to the agent's resolver |
| `fdns` | Resolve each existing host's FQDN and compare with its recorded IP | Yes | Stretch for M2a. **Only names under the subnet's effective domain are sent**; a host whose FQDN falls outside it is skipped. Without this, anyone who can edit a hostname can make the agent resolve arbitrary internal names and read the answers back as findings |

- An address is **alive** if it answers `icmp` or `arp`. These two are the **liveness methods**; `rdns` and `fdns` say nothing about whether an address is up.
- **A scan target needs a liveness method.** The server refuses to save a target whose methods include neither `icmp` nor `arp`.
- **`arp` is active, not a neighbour-table read.** The agent sends ARP requests from a raw `AF_PACKET` socket on the interface whose network contains the range (standard library only; `CAP_NET_RAW` is already required for `icmp`). The kernel neighbour table is not consulted: its `STALE` and `DELAY` entries describe hosts that may have left, entries below the garbage-collection threshold never expire, and the result would depend on sysctl timing.
- The sweep skips the network and broadcast addresses of the subnet (prefixes of /30 and shorter), matching `hosts._check_not_reserved`.

The server knows which targets are L2-local for an agent from the interfaces the agent reports at check-in. If `arp` is enabled for a subnet the agent only reaches via a router, the server drops `arp` from that job and the UI says "MAC collection unavailable — agent is not on this subnet". If that leaves the job with no liveness method (an `arp`-only target on a routed agent), no job is issued and the UI says the target cannot be scanned by this agent.

**MAC coverage is the main design constraint.** An agent collects MACs only for the subnet it has an interface in, even when it can ping other VLANs through the router.

**Documented pattern: one agent per VLAN.** Each agent is single-homed and scans its own subnet with all methods. Because the agent is small and stateless, it does not need a dedicated machine: it can be installed on any existing Linux host or container that already lives on that VLAN. The guided install in §5.6 exists to make this cheap.

Other arrangements work without code changes and are the operator's choice:

- A VLAN with no agent can be assigned to an agent elsewhere for ICMP + DNS only.
- A multi-homed agent (an interface in each VLAN, IP forwarding off) covers several subnets from one host. Not recommended: it shows up as several devices in some network controllers, and a host that touches every VLAN is the most valuable one on the network to an attacker.
- Later, a **controller collector** (§5.9) can supply MACs without any L2 presence.

### 5.3 Scan scope

Not every address in a subnet is worth scanning. The **scan scope** of a subnet is its usable addresses minus two kinds of excluded range:

| Range | Setting | Default |
|-------|---------|---------|
| The subnet's DHCP pool (`dhcp_start`–`dhcp_end`) | `scan_targets.scan_dhcp_pool` | **off** — the pool is not scanned |
| Each reserved range | `reserved_ranges.scan_excluded` | **scanned** — the flag is unset |

Reasons for the defaults: addresses in the DHCP pool change hands, so what answers there today says nothing durable about the network, and the pool is where phones and laptops live (§7.1). Reserved ranges hold statically addressed equipment the owner does care about. A range is excluded when it holds devices that should not be probed, or that someone else manages.

Rules:

- **Exclusion is absolute.** No packet of any method is sent to an excluded address, including one that has a host record. A host recorded inside an excluded range has no observation, no scan-derived `last_seen`, and raises no findings (including `stale` and `fdns_mismatch`). The UI shows "not scanned" for it. An owner who keeps static leases inside the pool and wants them tracked turns pool scanning on.
- **Exclusion wins.** An address in both an excluded and a scanned range is excluded.
- **One function decides.** `services/scans.scan_scope(subnet)` returns the in-scope ranges. Job creation, ingest validation, findings, and the UI all call it; nothing else works scope out.
- **Leaving scope deletes data.** When a change puts addresses out of scope (pool scanning turned off, a range excluded, the pool or CIDR edited), their observations and dismissals are deleted in the same transaction.
- **Scope changes are audit-logged** like any other subnet or reserved-range write.
- **Scope is not configurable over MCP** (invariant, §7.2). `add_reserved_range` over MCP creates a scanned range, which leaves scope unchanged. `delete_reserved_range` over MCP refuses a range with `scan_excluded` set, with an error saying to remove it in the UI, because deleting it would widen what is scanned. `scan_dhcp_pool` lives on the scan target, which MCP cannot reach at all.
- When the pool is scanned, an unknown address inside it is still classified `dynamic` and hidden by default (§5.5).
- A subnet with no DHCP pool defined shows the pool setting disabled.

**`changes.actor`** — see §4.3.

**Deletion and edits**

- Deleting a subnet deletes its scan target, observations, and dismissals. `subnets.delete_subnet` must do this before deleting the subnet, because foreign keys are enforced.
- Changing a subnet's CIDR or DHCP pool applies the "leaving scope" rule in §5.3.
- Deleting an agent revokes its tokens and sets `agent_id` to null on its scan targets. The targets keep their settings and show as unassigned.

**`Host.last_seen`**

The stored column stays and keeps meaning "set by hand". It is still writable, and `clear_fields: ["last_seen"]` still clears it. What changes is the output:

- `host_out` serialises `last_seen` as the later of the stored value and the matching observation's `last_seen_at`.
- A new output field `last_seen_source` is `manual`, `scan`, or null, so a caller who clears the manual value and still sees a date knows why. The `update_host` docstring says the same.
- `hosts_out` fetches observations for the whole batch in one query, as it already does for subnet domains.

Scan ingest never touches `hosts`, so the "every write is audit-logged" invariant holds without logging every sweep.

### 5.5 Findings (the "optional, not automatic" part)

Findings are **computed at read time** from `hosts ⋈ observations`, restricted to the scan scope (§5.3); they are not stored.

| Finding | Condition | Observed value | Offered action |
|---------|-----------|----------------|----------------|
| `unknown_host` | address alive, no host record | the MAC, or empty | Create host, pre-filled with MAC and name |
| `mac_missing` | host has no MAC, observation has one | the MAC | Set MAC |
| `mac_mismatch` | both present, differ | the MAC | Replace MAC |
| `name_missing` | host has no hostname, PTR exists | the PTR name | Set hostname |
| `name_mismatch` | PTR differs from `hostname` + effective domain | the PTR name | Replace hostname |
| `fdns_mismatch` | the host's `fdns_results` row is for its current FQDN, and its addresses do not include the host's IP (an empty list counts) | the resolved addresses, sorted, or `unresolved` | Informational |
| `stale` | host status `active`, not seen for N days (default 30) | last-seen timestamp, or `never` | Informational; offer status → `offline` |

**Identity.** A finding is identified by `(subnet_id, ip, type, observed)`. Every finding returned by the API and by MCP carries all four.

Rules:

- `unknown_host` inside the subnet's DHCP pool (only possible when pool scanning is on) is classified `dynamic` and hidden behind a filter by default.
- No `mac_missing`/`mac_mismatch` finding is raised when `mac_randomised` is true.
- PTR comparison strips the effective domain (host override, else subnet default) before comparing with `hostname`, case-insensitively.
- `stale` is raised for a never-seen host only when both the scan target and the host record are older than N days. Otherwise every host would be stale the day scanning is switched on.
- **Accept** takes the finding's key. The server recomputes the finding; if it no longer exists or its observed value has changed since it was shown, that record is reported `skipped` with reason `changed` and nothing is written. Otherwise it calls the existing hosts service (`create_host`/`update_host`), so validation and the audit log apply unchanged. The change summary notes the value came from a scan.
- **Dismiss** takes the same key and stores it in `finding_dismissals`. A finding is hidden while a dismissal with the same observed value exists; it reappears when the observed value changes.
- Bulk accept is per finding type per subnet, with per-record results (`accepted`/`skipped`/`error` + reason), matching the existing bulk endpoints.

### 5.6 Agent

- Python, in `agent/` in the same repo, published as a second image. Dependencies limited to an HTTP client, `icmplib`, and `dnspython`. ARP uses the standard library.
- Linux only. Runs as a container with `network_mode: host` and `CAP_NET_RAW`, or as a systemd unit in an LXC. Host networking is required to reach the VLAN's L2 segment.
- Configuration (env): `IPAM_URL`, `IPAM_AGENT_TOKEN`, `ALLOWED_CIDRS`, `MAX_PPS`.
- **`ALLOWED_CIDRS` is an agent-side guard**, defaulting to RFC 1918 + CGNAT ranges. The agent refuses any job whose subnet is outside it, or whose ranges are outside the job's subnet, and reports the refusal. Reason: the server tells agents what to sweep, and a mistyped public CIDR in the IPAM must not turn the agent into a scanner pointed at someone else's network.
- Rate limit (default 200 packets/s) and a per-job timeout (default 10 minutes). Server refuses to create a scan target for a prefix shorter than /20.
- TLS verification on, no opt-out flag. A private CA is handled by mounting a CA bundle.
- **Updates are the operator's job** (pull a new image or re-run the install command). Once installed, the agent never downloads or runs anything the server sends.
- Rootless container runtimes cannot grant a usable `CAP_NET_RAW` on the host network. Document this as unsupported.

**M2a install.** The Agents page creates an agent and shows its `tlga_…` token once. The operator runs the container with `IPAM_AGENT_TOKEN` set. No enrolment, no systemd installer.

**Guided install (M2b)**

The Agents page has an **Add agent** flow: name the agent, and the page shows a ready-to-paste command with prerequisites listed beside it. Two tabs:

| Tab | Prerequisites | Command shape |
|-----|---------------|---------------|
| Container | Docker or Podman (rootful); Linux host on the target VLAN | `docker run -d --name tlg-ipam-agent --restart unless-stopped --network host --cap-add NET_RAW -v tlg-ipam-agent:/var/lib/tlg-ipam-agent -e IPAM_URL=… -e IPAM_ENROL_TOKEN=tlge_… <registry>/tlg-ipam-agent:<version>` |
| systemd | Linux with systemd; Python ≥ 3.11 with `venv`; root | `sudo python3 -m venv /opt/tlg-ipam-agent`, then `sudo /opt/tlg-ipam-agent/bin/pip install <release wheel URL>`, then `sudo /opt/tlg-ipam-agent/bin/tlg-ipam-agent install --url … --enrol-token tlge_…` |

- **The server renders the command; it does not serve the code.** The image comes from the project's GitHub container registry and the wheel from the GitHub release, both pinned to the version matching the server. A compromised server therefore cannot hand a new agent host something to run as root. Releasing a version means publishing both artefacts; add that to the release checklist and build them in CI from the tag.
- **The systemd install lives under `/opt`, not in a user's home.** The service runs as a dedicated unprivileged user, which could not execute a virtual environment inside another user's home directory, and a per-user install is not on `sudo`'s path.
- **Enrolment tokens.** "Add agent" creates the agent in state `pending` and an `enrol` token bound to it, single-use, expiring after 1 hour. It is exchanged at `POST /api/v1/agent/enrol` for the long-lived `tlga_…` token. A command left in shell history or a chat log is useless afterwards.
- **Where the exchange happens and where the token lives.** Container: the agent exchanges on first start and stores the token in the named volume. systemd: `tlg-ipam-agent install`, running as root, does the exchange itself and writes the token to `/var/lib/tlg-ipam-agent/token`, owned by the service user, mode `0600`. The service user can read it on every start and never needs write access, and the enrolment token never reaches the disk.
- **A stored agent token always wins.** If the agent finds a stored token it ignores `IPAM_ENROL_TOKEN`. The container's volume is what lets the image be updated by recreating the container without enrolling again.
- **Re-enrol.** An existing agent has a "Re-enrol" action that issues a new enrolment token for the same agent. Exchanging it revokes the previous agent token. The agent keeps its identity and scan targets. This is the recovery path for a lost volume, a rebuilt host, or an enrolment whose response never arrived.
- The enrol endpoint has a small global attempt throttle; it is the only agent route reachable without a long-lived token.
- `tlg-ipam-agent install` creates the service user, enrols as above, writes `/etc/tlg-ipam-agent/agent.env` (server URL and settings; no secrets), installs a systemd unit with `AmbientCapabilities=CAP_NET_RAW`, and enables it. `tlg-ipam-agent uninstall` reverses it.
- **Suggest, don't assume.** At first check-in the server matches the agent's reported interface to a subnet and the UI offers "Scan *subnet* with this agent?" with default methods and the default scope. One click to accept; nothing is scanned until the owner does.
- **Version reporting.** Check-in carries the agent version and a protocol version. The Agents page flags agents older than the server expects and shows the update command. A protocol mismatch gets a clear error on the page; the agent is given no jobs rather than failing silently.

### 5.7 Endpoints

Agent-facing (agent token only, except `enrol`):

```
POST /api/v1/agent/enrol          (enrolment token, single use; M2b)
  → { hostname, platform, version }
  ← { agent_id, agent_token }

POST /api/v1/agent/checkin
  → { version, protocol, hostname, platform, interfaces: [{name, cidr, mac}], capabilities: [...] }
  ← { checkin_interval_s,
      jobs: [{ job_id, subnet_id, cidr, ranges: [{start, end}], methods,
               dns_servers, timeout_s, fdns: [{host_id, fqdn}] }] }

POST /api/v1/agent/results
  → { job_id, subnet_id, started_at, finished_at, complete,
      observations: [{ ip, mac?, rdns_name? }], fdns: [{host_id, addresses}], error? }
  ← { accepted, rejected: [{ip, reason}] }
```

- `ranges` is the scan scope from §5.3, as inclusive start–end pairs inside `cidr`.
- `observations` lists **live addresses only**.

Server-side ingest:

- `job_id` must equal the target's `current_job_id`, the target must be assigned to this agent, and every `ip` must fall inside the job's ranges. Anything else is rejected per record. A second result set for the same job is refused. Accepting a result clears the lease.
- Each reported address is upserted with `alive=true` and `last_seen_at` set.
- **Only when `complete` is true and the job ran a liveness method** (`icmp` or `arp`, as issued by the server, not as claimed by the agent), every other in-scope observation for the subnet is set to `alive=false`. An interrupted or timed-out scan therefore never marks an address dead; it only adds what it saw.
- Each `fdns` entry is upserted into `fdns_results`, with an empty address list recorded for a name that did not resolve. An entry is accepted only for a `host_id` the server sent in that job. Rows whose host no longer exists are deleted.
- `mac` only accepted when the server considers the target L2-local for that agent.
- `rdns_name` is **untrusted input**: any device can name itself, and these strings are later read by an LLM over MCP. Restrict to the DNS hostname character set, lowercase, cap at 253 characters, drop anything else.
- Body size cap. The 90-day prune runs here.

Owner-facing (owner key):

- CRUD for `/agents` and `/scan-targets`; `POST /agents/{id}/re-enrol` (M2b).
- `PATCH /subnets/{id}/reserved-ranges/{range_id}` to set `scan_excluded` (reserved ranges are create/delete only today).
- `POST /subnets/{id}/scan` (request scan).
- `GET /subnets/{id}/findings`, `POST /findings/accept`, `POST /findings/dismiss`; accept and dismiss take a list of finding keys.

### 5.8 UI and MCP

**UI**

- **Agents page:** Add agent, status dot from `last_checkin_at`, version with an "update available" flag, reported interfaces, subnets covered, enable/disable, revoke, re-enrol. Pending enrolments are listed until used or expired.
- **Subnet settings:** scanning section — agent, methods, interval, "Scan DHCP pool" checkbox (off by default, disabled when no pool is defined), "Scan now", last scan time and duration.
- **Reserved ranges:** a "Scan" checkbox per range (`.tlg-check`), on by default.
- **Subnet view:** findings count badge; a findings panel grouped by type with accept/dismiss per row and bulk accept; last-seen indicator on host rows, reading "not scanned" for hosts outside the scan scope; "show dynamic" filter, shown only when pool scanning is on.

**MCP** (keep the tool count small; update `EXPECTED_TOOLS` and the brief's tool table)

| Tool | Class | Purpose |
|------|-------|---------|
| `list_scan_findings(subnet_id?, type?)` | read | Read findings, denormalised with host and subnet names |
| `request_scan(subnet_id)` | write | Mark a configured target due |

- `request_scan` has a **per-subnet cooldown** (default 15 minutes, applied to every caller including the UI button). Repeated scans are how someone with read access would turn "latest state" into a presence timeline.
- `request_scan` is classed as a write tool, so read-only remote grants (§6.5) cannot call it.
- Accepting a finding over MCP uses the existing `create_host`/`update_host` tools. There is no dismiss tool: dismissal is an owner judgement and stays in the UI.
- `get_subnet` output marks each reserved range's `scan_excluded` and the subnet's `scan_dhcp_pool`, so an assistant can explain why an address has no observation.
- Agent, scan-target, and scan-scope configuration stays UI-only (§5.3).

### 5.9 Later: controller collector

The ingest path in §5.7 is deliberately source-agnostic. A later "collector" kind of agent could poll a network controller's client list (IP, MAC, hostname, VLAN for every client, across all VLANs) and post the same observation shape. That removes the L2 constraint for networks that have such a controller. Not in v0.2; the design should not preclude it.

## 6. M3 — Remote MCP with built-in OAuth

### 6.1 Three ways to run it

| Setup | Configuration | Behaviour |
|-------|---------------|-----------|
| Local | `API_KEY` | OAuth routes answer 404. Clients send the owner key as a bearer (desktop JSON config, `mcp-remote`, CLI clients) |
| Remote | + `PUBLIC_BASE_URL` | Built-in OAuth server on. Owner key still works for local clients |
| Remote with SSO/MFA | as Remote, plus the operator's access proxy on two paths | See §6.7 |

OAuth turns on when `PUBLIC_BASE_URL` is set. There is no consent password to configure.

### 6.2 Shape

```
web MCP client ──▶ https://ipam.example.com/mcp
                     │
                     ▼
          FastMCP MultiAuth
            ├─ server:    IpamOAuthProvider   (subclass of FastMCP's OAuthProvider, SQLite-backed)
            └─ verifiers: owner-key bearer verifier (from M1)
```

The app is its own authorisation server. FastMCP and the MCP SDK supply the protocol endpoints (authorise, token, register, discovery metadata), PKCE verification, and redirect-URI validation. `IpamOAuthProvider` supplies storage, the consent step, and token issue/refresh. FastMCP's 369-line `InMemoryOAuthProvider` is the reference for the method set; expect roughly 400 lines plus tests.

### 6.3 Linking flow

Linking a client needs a **link window**, opened by the owner from the private UI. Outside a window the server registers no clients and authorises nothing.

1. In the UI the owner chooses **Link a client**. If `MCP_REMOTE_WRITES` is on, the dialog has an "Allow this client to make changes" checkbox, off by default. The UI then shows a one-time **link code** and a 10-minute countdown.
2. The owner adds the server URL in the web client. The client discovers the server from `/.well-known/…` and registers itself (dynamic registration).
3. The client sends the owner's browser to the authorise endpoint. The provider stores the pending request server-side and redirects to the **consent page** with an opaque transaction ID.
4. The consent page shows the client's self-declared name (marked as unverified), **the redirect host in prominent text**, and the access being granted (read-only or read-write, as chosen in step 1). The owner types the link code.
5. On success the provider issues a single-use authorisation code, closes the window, and redirects to the client, which exchanges the code for tokens.

Link window rules:

- One window at a time. It closes on the first successful link, after 10 minutes, or when the owner cancels it.
- The code is 10 characters from an unambiguous alphabet, generated server-side, held hashed in memory, compared in constant time.
- **Five wrong codes burn the window.** The owner opens a new one. This bounds guessing to five attempts per window the owner chose to open, and there is no lockout an outsider can hold shut.
- Register and authorise requests outside a window are refused with a plain error page saying to start from the IPAM's own UI. Discovery metadata and the token endpoint always answer, so existing links keep refreshing.
- Window state and pending transactions are in memory. A restart cancels a link in progress and nothing else.
- Opening a window is audit-logged (`source="ui"`); a burned window and an issued grant are audit-logged (`source="oauth"`, `entity_type="link_window"` and `"grant"`).

Consent page requirements: served with `frame-ancestors 'none'`; no external assets; CSRF token bound to the transaction; the transaction expires with the window.

Cost of this design: the owner must be able to reach the private UI at the moment of linking. That is accepted; linking is rare, and it is what removes the standing secret.

### 6.4 Storage and lifetimes (additive tables)

| Table | Holds |
|-------|-------|
| `oauth_clients` | `client_id`, declared name (sanitised, §4.3), redirect URIs, `created_at`, `linked_at` |
| `oauth_grants` | one per approved link: `client_id`, `can_write`, `created_at`, `last_used_at`, `revoked_at` |
| `oauth_tokens` | SHA-256 hash, `grant_id`, kind (`code`/`access`/`refresh`), `expires_at`, `rotated_at`, PKCE challenge for codes |

- Authorisation code: 5 minutes, single use.
- Access token: 1 hour.
- Refresh token: 30 days, rotated on every use.
- **Retry window.** A refresh token presented again within 60 seconds of its rotation is treated as a retry (a lost response or two concurrent requests) and is answered with a new pair. Presented later than that, it is treated as theft and revokes the whole grant.
- Tokens are stored hashed only. All of this lives in the one SQLite file, so the existing backup covers it and links survive a restore.

### 6.5 Limits on what a remote grant can do

- **Scopes.** Two scopes exist: `ipam:read` and `ipam:write`. Write tools require `ipam:write` through FastMCP's scope checks (`require_scopes`, present in FastMCP 4.1.8) rather than hand-written tagging. The owner-key verifier returns both scopes.
- **Read-only by default.** `MCP_REMOTE_WRITES=false` is the default. A grant's `can_write` is fixed when the link window is opened.
- **The setting is honoured in both directions.** A token carries `ipam:write` only when the grant has `can_write` **and** `MCP_REMOTE_WRITES` is currently on; the provider applies this each time it loads a token. Turning the setting on later does not upgrade existing read-only links. Turning it off takes write access away from every grant at once.
- FastMCP decides whether a tool the caller lacks the scope for is hidden from the tool list or listed and refused. Record which in the spike (§6.8); either is acceptable.
- A grant reaches `/mcp` only — never `/api/*`, the backup endpoint, or the SPA.

### 6.6 Abuse controls

| Control | Detail |
|---------|--------|
| Link window | Registration and authorisation only while the owner has a window open; five wrong codes burn it (§6.3) |
| Registration bounds | At most 50 registered clients. At the cap, a new registration evicts the oldest client that was never linked rather than being refused. A registration not linked within 24 hours is deleted |
| Visibility | A **Linked clients** list in the UI (name, redirect host, read/write, created, last used) with revoke. Every grant issue, refresh-reuse revocation, and manual revoke is audit-logged (`entity_type="grant"`) |
| Audit attribution | MCP writes from a grant record the client in `changes.actor` (§4.3) |

### 6.7 Exposure and SSO

- Publicly routable: the `/mcp` mount (transport and OAuth routes) and `/.well-known/*` only. The SPA and `/api/*` stay private.
- An access proxy in front of the MCP transport, token, or register endpoints must pass traffic through without an interactive login; web MCP clients cannot complete one.
- **SSO or MFA without native OIDC:** only the owner's browser ever visits the authorise and consent pages. An operator can put their access proxy's login in front of just those two paths, in addition to the link code. This is a documentation page, not a feature.
- Well-known routes must be installed on the parent FastAPI app, before the SPA catch-all, which would otherwise answer them with `index.html`.
- `PUBLIC_BASE_URL` is installation identity: issuer and callback URLs come from it, never from `Host` or `X-Forwarded-*`. Changing it invalidates every link.
- The existing `MCPPathRewriteMiddleware` must keep rewriting only the exact path `/mcp`; OAuth paths must 404 rather than redirect on a trailing slash.
- `/api/v1/agent/*` needs to be reachable by agents only. If agent and server share a LAN it is not public.

### 6.8 Client compatibility spike (first task in M3)

FastMCP's support for metadata-document clients (CIMD) appears to live in its `OAuthProxy` class, not in the `OAuthProvider` base class used here, so the built-in server would offer dynamic registration only. Confirm this against the installed version first. In earlier testing on another project, Claude.ai and ChatGPT linked via CIMD, while Gemini, Mistral, and MCP Inspector used dynamic registration.

Spike: stand up the provider with the in-memory store and confirm each of the four web clients links against a dynamic-registration-only server. If Claude.ai or ChatGPT will not, wire in FastMCP's `CIMDClientManager` (a separate, reusable class) before building the rest.

The spike also answers two things the rest of the design depends on:

- whether each client registers at "add connector" time or only when it first authorises, which decides whether the link window must be open before the URL is entered;
- how FastMCP presents a tool the caller lacks the scope for (§6.5).

### 6.9 Configuration

```
PUBLIC_BASE_URL=https://ipam.example.com
MCP_REMOTE_WRITES=false
```

### 6.10 Acceptance

- Each of Claude.ai, ChatGPT, Gemini, Mistral links and completes `list_subnets`.
- With no link window open, registration and authorisation are refused, and existing links keep working.
- A wrong code issues nothing; the fifth wrong code burns the window; the burn appears in the audit log.
- A second client cannot link on a window that has already been used.
- With `MCP_REMOTE_WRITES=false`, `create_host` and `request_scan` from a grant do not succeed; `list_hosts` works.
- A read-write grant loses write access when `MCP_REMOTE_WRITES` is turned off, without relinking.
- A refresh token reused within 60 seconds gets a new pair; reused after that, it revokes the grant.
- Revoking a client in the UI stops its next request.
- Links survive a container restart and a restore from backup.
- `mcp-remote` with the owner key as bearer still works with OAuth enabled.
- With OAuth unconfigured, `/.well-known/*` and the OAuth routes return 404.
- A change made through a grant shows the client in `actor`, and a client name containing markup or instructions arrives sanitised.

## 7. Security model

### 7.1 Worst case: an attacker holds a grant

There is no standing consent secret to guess. A grant reaches an attacker by phishing the owner during an open link window, by theft of a client's stored tokens, or through a compromised client.

| The attacker gets | Limited by |
|-------------------|------------|
| A full, current map of the network: subnets, VLANs, gateways, hostnames, MACs, notes, live addresses | Nothing — this is the residual exposure of running remote MCP at all |
| Presence tracking by polling live state | The DHCP pool, where personal devices live, is not scanned by default; `request_scan` is a write tool and has a cooldown; no history is stored |
| Vandalism of host records | Read-only grants by default; audit log with the client in `actor`; backups |
| Stored prompt injection — text planted in notes or hostnames that the owner's own assistant later reads alongside more powerful tools | Read-only grants by default; `rdns_name` and client-name sanitisation |

| The attacker does not get | Because |
|---------------------------|---------|
| Any reach into the network | The agent is pull-only with a fixed method vocabulary; it does not proxy, tunnel, or execute |
| New scan targets, agents, or a wider scan scope | Configuration is UI/REST-only, and the grant cannot reach REST |
| The owner key, backup, or UI | Separate credential; `/api/*` and the SPA are not public |
| A second link | Linking needs a code from the private UI |

### 7.2 Invariants

Add these to `AGENTS.md` alongside the existing architecture invariants.

1. The agent never executes, downloads, or updates from anything the server sends. Agent code comes from the published release, never from the server.
2. MCP never gains agent, scan-target, or scan-scope configuration, and no MCP call can widen what is scanned.
3. Scan ingest never writes to `hosts`.
4. No packet is sent to an address outside the scan scope, and scan scope is computed in one place (`services/scans.scan_scope`).
5. `fdns` only resolves names under the subnet's effective domain.
6. Linking a client requires a one-time code minted from the private UI. There is no static consent secret.
7. Remote grants are read-only unless the operator opts in, and never reach `/api/*`.
8. Strings that originate from the network or from a client (`rdns_name`, agent-reported fields, OAuth client names) are sanitised at ingest and never interpolated into change summaries.

### 7.3 Likelier attacks than guessing

- **Consent phishing.** The link window narrows this to the minutes the owner has one open, but inside a window anyone can register a client named after a well-known assistant. The consent page's redirect-host display is the remaining defence; test it with a lookalike.
- **A vulnerability in the app.** The server sits on the operator's network behind a tunnel, so code execution there is a foothold on the LAN — worse than anything in §7.1. Deployment guidance: unprivileged container, its own VLAN or firewall rules allowing only what it needs, non-root process.

## 8. Deployment guidance to document

- Unprivileged container or LXC, isolated as in §7.3, included in the backup schedule.
- Tunnel or reverse proxy publishes only the paths in §6.7.
- One uvicorn worker.
- Agents: one per VLAN, single-homed, on an existing host or a small container; `ALLOWED_CIDRS` reviewed, not left at default, if the network uses unusual ranges.
- Scan scope: leave DHCP pools unscanned unless static leases inside them need tracking; exclude any reserved range holding devices that should not be probed.

## 9. Decisions

**Settled**

| Decision | Outcome |
|----------|---------|
| Identity provider | None required. Built-in OAuth server; native OIDC deferred |
| Consent secret | **Changed in draft 5.** A one-time link code from the private UI. `OWNER_PASSWORD` is removed |
| Remote writes | Off by default; enforced with scopes; the setting applies in both directions |
| Reference deployment | An LXC on the operator's own network, in the backup schedule, published through a tunnel. The project stays deployment-neutral |
| MAC coverage across VLANs | One agent per VLAN is the documented pattern; other arrangements remain possible |
| ARP method | Active request/reply sweep; the neighbour table is not used |
| Scan scope | DHCP pool not scanned by default; reserved ranges scanned by default; exclusion is absolute; not configurable over MCP |
| `Host.last_seen` | Output is the later of the manual value and the observation; `last_seen_source` says which |
| Finding dismissals | Own table, keyed by subnet, address, type, and observed value |
| Milestone order | M0 → M1 → M2a → M2b → M3; M3 may start once M1 is done |
| Agent language | Python, in-repo, with a guided install from the Agents page |
| `request_scan` cooldown | 15 minutes per subnet |
| Agent code source | GitHub: container image from the project's registry, wheel from the GitHub release. The server never serves agent code |
| Minimum Python (systemd install) | 3.11 |

**Open**

None. What remains unknown is the M3 client-compatibility spike (§6.8), which is a set of tests to run, not a choice to make.
