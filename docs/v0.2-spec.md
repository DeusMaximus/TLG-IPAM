# TLG-IPAM v0.2 — Scan agents and remote MCP

**Status:** accepted (draft 5) · 13/11/2026 · tracked as GitHub milestones M0–M3
**Extends:** `TLG-IPAM-Project-Brief.md` v1.1 (which lists "discovery agents or active network scanning" as a v1 non-goal — this spec lifts that)
**Audience:** the project owner, and whichever coding agent implements it. This is the contract for work that has not shipped; the brief describes what `main` does. Each PR folds the behaviour it ships into the brief.

Domains in this document are placeholders (`example.com`, `home.arpa`), per the repo convention. The document names no person, real domain, or real address.

**Changes in draft 2:** remote MCP uses a built-in OAuth server instead of an external identity provider (§6); new security model section (§7); remote grants are read-only by default; separate `OWNER_PASSWORD`; forward-DNS and `request_scan` restrictions; settled decisions recorded (§9).

**Changes in draft 3:** one agent per VLAN is the documented pattern; guided agent install from the Agents page with single-use enrolment tokens (§5.6); agent version reporting; remaining decisions settled (§9).

**Changes in draft 4:** agent code source settled (GitHub: container registry image and release wheel); minimum Python for the systemd install settled at 3.11 (§9). Otherwise identical to draft 3.

**Changes in draft 5:**

- **Scan scope (§5.3, new):** the DHCP pool is not scanned unless enabled per subnet; each reserved range can be excluded from scanning.
- **ARP** is an active request/reply sweep, not a read of the kernel neighbour table (§5.2).
- **Jobs are leased**, a scan whose liveness sweep did not complete never marks addresses dead, a stored name is cleared only by a DNS answer that there is none, and the agent reports live addresses only (§5.1, §5.7).
- **Findings have a key**; accept is conditional on the observation being unchanged; dismissals move to their own table (§5.5).
- **Enrolment:** tokens table carries enrolment tokens; agents can be re-enrolled without losing their scan targets; install commands corrected (§4.2, §5.6).
- **Linking uses a one-time code from the private UI** in place of `OWNER_PASSWORD`, which is removed (§6).
- Remote write access uses OAuth scopes; the write setting is honoured in both directions; refresh rotation has a retry window (§6.4, §6.5).
- New nullable `changes.actor` column for audit attribution (§4.3).
- `Host.last_seen` semantics, the `stale` status value, and subnet-deletion cleanup aligned with the current code (§5.4, §5.5).
- M2 split into M2a and M2b (§2).

**Changes from the review of PR #1:**

- Forward-DNS results have a table, `fdns_results` (§5.4, §5.7).
- The systemd agent's token file is owned by the service user, and `install` does the enrolment exchange (§5.6).
- A scan target needs a liveness method, and a job can only mark addresses dead when it ran one (§5.2, §5.7).

## 1. Goals and non-goals

**Goals**

1. A remote **scan agent** that checks in to the server, receives its scan instructions, and reports what it sees: which addresses respond, their MAC addresses (same-L2 subnets only), and their DNS names.
2. Scan results are **suggestions, never automatic writes**. The owner (or an assistant over MCP) accepts or dismisses each one.
3. The MCP endpoint can be reached at a **public HTTPS URL** by web-only clients (Claude.ai, ChatGPT, Gemini, Mistral) using OAuth, **with no external identity provider required**.
4. The same image supports three ways of running it, chosen by configuration alone: local with a static key, remote with built-in OAuth, and remote behind the operator's own access proxy.
5. Move to **FastMCP 4** and pin dependencies.

**Non-goals for v0.2**

- Native OIDC login. Deferred; see §6.7 for how operators get SSO without it.
- Port scanning, service detection, OS fingerprinting, SNMP.
- Uptime history or time-series data. One row per address holding the latest state; trends belong in a monitoring system.
- Multi-user accounts or roles. Still single-owner.
- Agents for Windows or macOS. Linux only.
- Pushing changes *to* DNS or DHCP. Read and compare only.
- IPv6 scanning.

**Permanent non-goals** (security invariants, §7.2)

- Remote command execution or server-driven self-update on the agent.
- Scan or agent configuration over MCP.

### 4.1 FastMCP 4

Verified on 13/11/2026: with a fresh install (FastMCP 4.1.8, MCP SDK 2.3.0, FastAPI 0.162, Starlette 1.10) the existing suite passes 80/80 unmodified on Python 3.13 and 3.15. One deprecation warning: `tests/test_mcp.py` reads `Tool.inputSchema`, now `input_schema`.

### 4.2 Credentials

Today one static `API_KEY` is shared by the SPA, REST callers, and MCP clients, sent as `X-API-Key`. Each new kind of caller gets its own, narrower credential.

| Credential | Presented as | Stored | Can reach |
|------------|--------------|--------|-----------|
| Owner key (`API_KEY`, env) | `X-API-Key` on REST; `Authorization: Bearer` on `/mcp` | env | everything |
| Enrolment token (`tlge_…`; M2b) | once, in the install command; `Authorization: Bearer` to the enrol route | `tokens` table, SHA-256 hash + display prefix; single-use, expires after 1 hour | `POST /api/v1/agent/enrol` only |
| Agent token (`tlga_…`) | `Authorization: Bearer` | `tokens` table, SHA-256 hash + display prefix | `/api/v1/agent/*` only |
| Link code (M3) | typed into the consent page | memory, hashed; single-use, expires after 10 minutes | approves one OAuth client link — nothing else |
| OAuth grant (M3) | `Authorization: Bearer` | OAuth tables, tokens hashed | `/mcp` only; read-only unless enabled |

- `/mcp` moves from the hand-rolled `APIKeyASGIMiddleware` to FastMCP's own `auth=`. In M1 that is a small `TokenVerifier` that accepts the owner key and returns both scopes (§6.5). No deployed clients exist to break, so `X-API-Key` on `/mcp` is dropped rather than kept as an alias; README examples for `mcp-remote` change to `--header "Authorization: Bearer …"`.
- The owner key is compared in constant time (`hmac.compare_digest`) on both REST and `/mcp`. Today's check in `auth.py` uses `!=`.
- The server refuses to start unless `API_KEY` is set, non-empty, free of whitespace at either end (refused, not trimmed) and not the published placeholder `change-me`; the message names `API_KEY`, says how to generate a key and never contains the key. An empty presented key never matches, whatever the setting holds.
- New table `tokens`:

  | Field | Notes |
  |-------|-------|
  | `id` | uuid |
  | `kind` | `agent` or `enrol` |
  | `agent_id` | FK → agents. An agent can hold several rows over time; at most one unrevoked `agent` token |
  | `token_hash`, `token_prefix` | SHA-256; prefix for display |
  | `created_at`, `last_used_at` | `last_used_at` written at most every 10 s per token |
  | `expires_at`, `used_at` | enrolment tokens only |
  | `revoked_at` | |

  A token is shown once, at creation. In M2a the Agents page created an agent and its `agent` token directly. Since M2b (#21) "Add agent" creates the agent `pending` with an `enrol` token, and only the enrolment exchange issues an `agent` token (§5.6). "At most one unrevoked `agent` token" is enforced by a partial unique index on `agent_id`, as well as by the service. `token_prefix` is the first 13 characters (`tlga_` or `tlge_`, and 8 of the 43 random ones). A token is *live* while it is unrevoked and, for an enrolment token, unused and before `expires_at`; revoking an agent's tokens (revoke, delete, re-enrol) revokes only live ones, so a spent or expired enrolment token keeps its row as it ended.
- Token create, use (the enrolment exchange) and revoke are audit-logged (`entity_type="token"`).
- Authentication only reads. An agent token's `last_used_at` is written by the request the route serves, in that request's own transaction, only when the stored time is unset or 10 s old (a condition in the SQL `UPDATE`, so racing requests write it once): a check-in once it has taken its slot (§5.7), a result set once it is accepted. A refused bearer never writes it, nor does a request refused before it takes its check-in slot, nor a refused result set. A check-in refused after it has taken its slot (`409` or `422`, §5.7) has written it, together with `last_checkin_at` and `last_error`. If the database refuses a write of either route (an `OperationalError`: locked past SQLite's busy timeout, a read-only file, a full disk), the transaction is rolled back and the request is refused with `503 UNAVAILABLE` in the REST error shape: retryable, and nothing of the request is written. The message says the database is busy only for a lock; the server logs the operation and SQLite's error name, never SQL, parameter values or the bearer. A failed rollback, a failure of the authentication read itself, and a database error that is not an `OperationalError` (an integrity or programming error, say) are a bare 500. The write is a heartbeat, not an audit entry.
- The enrolment exchange is not an authenticated agent request and does not run through this authentication. What it records of its token's use is `used_at`, which spends it; it writes no `last_used_at` on the enrolment token or on the agent token it issues, whose first is written by the agent's first check-in. A write it cannot make is `503 UNAVAILABLE` as above, and nothing of it is written.

### 4.3 Audit attribution

The change log gains one nullable column, `changes.actor` (str(80)). It holds who acted when that is narrower than the `source`:

| Source | Used for | `actor` |
|--------|----------|---------|
| `ui`, `api` | unchanged | null |
| `mcp` | MCP tool writes | null for the owner key; `grant:<client name>` for an OAuth grant |
| `agent` | enrolment, agent self-reported errors that change agent state | `agent:<agent name>` |
| `oauth` | grant issued, grant revoked by refresh reuse, link code burned | `grant:<client name>` or null |

- New values fit the existing `source` column (8 characters).
- The client name is self-declared by the client and is later read back over MCP through `list_changes`. It is sanitised once, at registration: printable characters only, at most 60. It goes in `actor`, never interpolated into `summary`.
- `ChangeOut` and the `list_changes` tool return `actor`.

## 5. M2 — Scan agent

### 5.1 Model

```
agent ──outbound HTTPS──▶ server
  1. POST /api/v1/agent/checkin   → "here is who I am and what interfaces I have"
                                  ← "scan these ranges now, with these methods"
  2. (agent scans)
  3. POST /api/v1/agent/results   → live addresses for one job
```

- **Pull only.** The agent makes outbound requests; nothing listens on it. This works whether the server is on the same LAN, behind a tunnel, or on a VPS.
- **Stateless agent.** Configuration on the agent is a server URL, a token, and a safety allowlist (§5.6). The server decides what is due. "Scan now" in the UI marks a subnet due; the agent picks it up at its next check-in (default 60 s).
- **Server is the scheduler.** It tracks `last_scan_at` per target and returns only the targets that are due. `last_scan_at` is when the last completed job was issued, by the server's clock, so a scan requested while a job runs is still due after it: a request is served by a job issued after it.
- **Jobs are leased.** Issuing a job stores `current_job_id` and `job_issued_at` on the target. A target with a live lease is not issued again. The lease expires after the per-job timeout plus a margin (defaults: 10-minute timeout, 15-minute lease), after which the target is due again. The agent keeps checking in on schedule while it scans and runs jobs one at a time. The server issues at most one job per check-in, and none to an agent that still holds a live lease, so a queued job's lease cannot run out before it starts. The lease is a compare-and-set on the lease the check-in read. The agent records the same lease, and is busy while it is live: reassigning or deleting the target mid-scan sends the agent nothing, so it does not free an agent that is still scanning.
- **A check-in refused before it takes its slot changes nothing.** One inside the rate limit (`429`, §5.7), or refused because the owner disabled the agent or revoked its token after it authenticated (`403`, §5.7), writes no row: not `last_checkin_at`, not the token's `last_used_at`, nothing in the change log. One refused for its protocol or a field (`409`, `422`) has taken its slot and records it, the token's use and `last_error` (§5.7). A check-in that is served writes its slot, its report, the token's use and any lease in one transaction, which is rolled back whole if the database refuses a write (`503`, §4.2).
- **Fixed vocabulary.** A job names a subnet, address ranges inside that subnet, and a subset of the methods in §5.2. There is no field through which the server can send a command, a script, a binary, or a target outside the subnet.

### 5.2 Scan methods

| Method | What it does | Works across a router? | Notes |
|--------|--------------|------------------------|-------|
| `icmp` | Echo sweep of the job's ranges | Yes | Misses hosts that drop ping |
| `arp` | ARP request to each address in the job's ranges; a reply means alive and supplies the MAC | **No — same L2 only** | Catches hosts that drop ping. One request and one retry per address |
| `rdns` | PTR lookup for each live address | Yes | Queries the subnet's `dns_servers` (already on the `Subnet` model), falling back to the resolvers in the agent host's `/etc/resolv.conf`. With neither, no lookup is made and the result set is incomplete. With `ALLOWED_DNS_SERVERS` set on the agent's host, only the servers inside it are asked (§5.6) |
| `fdns` | Resolve each existing host's FQDN and compare with its recorded IP | Yes | Stretch for M2a (#20). **Only names under the subnet's effective domain are sent**; a host whose FQDN falls outside it is skipped. Without this, anyone who can edit a hostname can make the agent resolve arbitrary internal names and read the answers back as findings. The bound is the subnet's own domain: a host's domain override places its FQDN, and an override outside the subnet's domain puts the host outside it (§5.7). A records only |

- An address is **alive** if it answers `icmp` or `arp`. These two are the **liveness methods**; `rdns` and `fdns` say nothing about whether an address is up.
- **A scan target needs a liveness method.** The server refuses to save a target whose methods include neither `icmp` nor `arp`.
- **`arp` is active, not a neighbour-table read.** The agent sends ARP requests from a raw `AF_PACKET` socket on the interface whose network contains the range (standard library only; `CAP_NET_RAW` is already required for `icmp`). The kernel neighbour table is not consulted: its `STALE` and `DELAY` entries describe hosts that may have left, entries below the garbage-collection threshold never expire, and the result would depend on sysctl timing.
- **How the ARP sweep runs.** The agent reads its interfaces again as the job starts and uses the first one whose IPv4 network contains the whole subnet (the server's own rule for issuing `arp`) and has a MAC; with none, `arp` is not run and the result set is incomplete. The socket is created with protocol 0 and bound to ARP on that one interface, so no frame from another interface is queued on it. A first round sends one broadcast request to each address, paced at `MAX_PPS` with the agent's other sends (§5.6), then waits 1 s for replies (less once every request is answered); a second round retries only the addresses still silent when their slot comes, and waits the same. A send never waits for the socket to be writable: a full send queue is a failed send. The listener lets the rest of the agent run after every 64 frames it reads, so a station that floods the segment cannot hold back the job's deadline or the agent's check-ins. A reply is taken only if it is a well-formed Ethernet/IPv4 ARP reply addressed to the interface's own address, from a unicast MAC, for an address the agent sent a request to, and is not a frame the host itself is sending; the first reply for an address supplies its MAC. Gratuitous and unsolicited replies, replies for other hosts, malformed frames and later replies for an answered address are dropped. An address the interface itself holds gets no request, since the kernel answers none of its own on the wire: it is reported alive with the interface's MAC, as `icmp` reports it alive through the host's own stack. The sweep runs after the ICMP sweep, inside the same deadline; a socket that cannot be opened, written or read stops it, and the result set reports what answered and is incomplete.
- **What an ARP reply cannot prove.** ARP carries no nonce, so a reply is matched to a request only by its sender address: a reply queued after the socket is bound and before the listener reads it, or a late reply to an earlier job, counts once its sender has been asked in this one. A proxy-ARP router, or an access point answering for a client that has left, reports an address with no host behind it. Any station on the segment can claim an asked address with a MAC of its choosing; that is an observation, which reaches hosts only through a finding the owner accepts (§5.5). `complete` means every issued request was sent and every wait ran before the deadline, not that no reply was lost: a reply the kernel dropped looks like silence.
- The sweep skips the network and broadcast addresses of the subnet (prefixes of /30 and shorter), matching `hosts._check_not_reserved`.
- **No server to ask is not an empty answer.** The servers a job's PTR lookups ask are chosen once, as the lookups start: the job's `dns_servers`, else the host's resolvers, read from `/etc/resolv.conf` again for every job and never cached, so a corrected file takes effect at the next job without a restart. The file is read off the event loop, in a thread, one read at a time. The path is looked at first (`os.stat`, following a link), and only a regular file of at most 64 KiB is opened, by dnspython, which parses it: a FIFO, a device or a directory at the path, or a larger file, gives none without being opened, and so does a read that has not finished within 1 second (a stalled network mount), while the agent's check-ins and deadlines keep running. The look is not a bound on the open: a file that grows after it is parsed whole, and a FIFO swapped in after it blocks the read's one thread until a writer comes, as a stalled mount does. Both need control of the agent's host, which already decides what the path holds. The wait for it is also cut at the job's deadline, which is then reported as the PTR lookups' timeout. While such a read stays blocked, every job that names no DNS server finds none, and correcting the file does not end that: the blocked operation must return, or the agent be restarted. A job that names its own DNS servers reads no file and is not affected. Only entries that are IP addresses are kept, before the list is cut to 3, so an entry the agent cannot query with UDP (a DNS-over-HTTPS URL, which dnspython accepts) never takes the place of one it can; a file dnspython refuses (missing, unreadable, no `nameserver` line, or one that is neither an address nor an `https` URL) gives none. **The host's limit on DNS servers** (#93): with `ALLOWED_DNS_SERVERS` set (§5.6), the servers so chosen, the job's or the host's, are then narrowed to those inside it, in their order, before any query, and a server outside it is sent nothing (`guard.dns_servers`). The narrowing comes after the cut to 3, so it only ever takes a server away and never brings in one that would not have been asked. When it takes some and leaves others, the others are asked as they would be were the rest silent, and the scan stays complete; the error says so ahead of what the lookups met, by counts only: `rdns: 2 of the 3 DNS servers to ask are outside ALLOWED_DNS_SERVERS and were not asked`. An answer from a server that is left, that there is no name, clears a stored name as it would were the others down. When it takes them all, no lookup is made and no DNS packet sent, and the host's resolvers are not asked in the job's servers' place: the result set is `complete: false` with the error `rdns not run: all 3 DNS servers to ask are outside ALLOWED_DNS_SERVERS` (`the 1 DNS server to ask is …` for one), so the server keeps every stored name. With no server at all the error is the one below, whatever the setting. With none, no lookup is made and no DNS packet is sent: the result set is `complete: false` with the fixed error `rdns not run: the agent has no DNS server to ask (…)`, so the server keeps every stored name (§5.7). A lookup that sent no query is not a completed lookup either, when it tried and failed: its every attempt failed before the query went out (the server is not an address, no socket of its family on the host, the kernel refuses the send, the socket cannot take it at once), whether its servers or its own 2 seconds ran out first. Its error is `rdns stopped: no DNS query could be sent to any server (<exception type>)`; the lookups still running are cancelled at once and no lookup starts after it, so no query is handed to a socket after the failure. A query a cancelled lookup had already handed over is the kernel's: the agent hands a query to the kernel at once or not at all, and aborts a lookup's socket as the lookup ends, so none is left to go later (§5.6). The names the finished lookups found are reported, and the result set is incomplete. A lookup the job's deadline stops before its first attempt made none, and is the deadline's cut-off, reported as the PTR lookups' timeout. A lookup that sent its query to at least one server is a completed lookup, and the scan stays complete, but what it found is one of three things, reported per address (#100): a name; an answer that there is none, which the record says with `rdns_no_name: true`; or no usable answer from any server asked, for which the record carries neither. **Which records of a reply are read** (#144, `probe.read_reply`). The name the answer is about is the question's name, followed along the CNAME records the answer section holds, each at the name the chain has reached so far, to the chain's last target (RFC 2317's classless delegation is such a chain; one that loops is no usable answer). A PTR record is the name only at that name (the first of them, when that name holds more than one, as RFC 2181 §10 allows), and a reply that holds one there is read as that name whatever else it holds (#149). A PTR record at any other owner, the chain's earlier links included, answers some other question: it is never the name, and a reply that holds one but none at the chain's end is no usable answer, never "no name", even beside an SOA that would otherwise say so. The chain is followed by each name's case-folded wire form, label lengths included, never by dnspython's hash of a name, which ignores where its labels split, so the walk's work grows in step with the reply's records however its names are built (#149); reading the reply off the wire is dnspython's own work and is not bounded by this, but a reply is read only if it is no longer than the payload the query advertised (1,232 bytes, below; #153) and its header claims at most one question and at most 32 records in its other three sections together (below; #160). dnspython's parse costs work that grows with the square of a reply's records when their names hash alike, and holds the agent's event loop while it runs. By size alone a reply could hold 244 entries (the smallest is a question at the root name, 5 bytes), and no ceiling on the work followed from that; the worst replies built at 1,232 bytes took about 0.12 s to parse. With the header's counts bounded, a ceiling is derived, for a 64-bit CPython whose dictionary probes as 3.13's does: dnspython indexes records in one dictionary by keys that hold the section and the owner name, a question is inserted once and a record of another section looked up and, when new, inserted, and a name is compared only with a stored key of the same hash and section. CPython's probe visits slot i, then 5·i + perturb + 1, with perturb starting as the hash and shifted right by 5 bits before each step. From the step to the 14th visit on, perturb is 0 whatever the hash (for 0x8000000000000000 it is still 8 at the step to the 13th), and from there each visit is 5·i + 1 of the last, a recurrence whose one cycle passes through every slot of the table. The 13th visit is the slot just before the 14th on that cycle, so the 13th and every later visit are consecutive points of it and none repeats before the probe meets an empty slot, which it does within one turn. Only the first 12 visits can repeat a slot, so a probe compares each stored key of its hash at least once and at most 12 keys more, and none when no such key is stored. One question meets nothing, and 32 records make at most 2·(12 + m) summed over m from 1 to 31, (32 − 1)·(32 + 24) = 1,736 name comparisons, each over at most 127 labels. The index is not the only comparison of an owner name: an OPT record's owner is compared once with the root, and a second OPT is refused before that comparison; an OPT takes a record's place, so a reply with one makes at most 1 + 2·(12 + m) summed over m from 1 to 30, 1,651. A TSIG record adds none, since the lookup gives dnspython no key and it refuses one. The suite's test of that premise (`test_one_probe_compares_at_most_twelve_keys_more_than_it_holds_of_one_hash`, on named hashes and 3,000 drawn at random, on the interpreter that runs it) is a tripwire, not a proof: a change to the probe that touched only hashes it does not try would pass it. So the premise is rechecked whenever the agent's interpreter changes, by running that test on the new interpreter and reading its `Objects/dictobject.c` probe against the rule above: the image's interpreter changes only when its base's pin moves (#94), which can bring another 3.13 patch release and is where the recheck is a step (`AGENTS.md`, Commands, "The agent's base image"), and a native install runs whatever supported CPython its host has, 3.11 or later. The worst reply built inside both limits (32 answer records at distinct owners of one hash over a shared 125-label tail, 800 bytes) makes 1,426 and parses in about 23 ms where it was measured, holding the event loop as long; the briefed review's strongest made 1,528 in about 24 ms; 1,736 comparisons of such names take about 24 ms there. Before the budget, a 1,232-byte reply of 59 such records made 4,110 comparisons in 64 ms. An SOA in the authority section counts only for a zone that contains that name: the SOA's owner is the name or an ancestor of it. Records of other types, and CNAMEs at owners the chain does not reach, are not read. `NXDOMAIN` is taken as it is, without reading the reply's records. "No name" is `NXDOMAIN`, or a `NOERROR` without a PTR record at that name whose authority section holds such an SOA (RFC 2308's NODATA, with or without the CNAMEs that led to it, and with or without name servers beside it), or that carries no record at all, in its answer or its authority (`probe.says_no_name`). No usable answer is no reply in its time, `SERVFAIL`, `REFUSED` or another rcode, a truncated, malformed or mismatched reply, a reply longer than the payload the query advertised (not parsed, #153), a PTR record at an owner the question does not reach with none at the chain's end, an SOA only for zones that do not contain the name (an unrelated zone's, or the question's own zone's beside a CNAME whose target lies outside it; before #144 any SOA counted), a referral (a `NOERROR` without a PTR record whose authority holds name servers and no SOA, from a server that does not recurse, whatever CNAMEs its answer holds: RFC 2317's classless reverse delegation is a CNAME followed by one; round 1 of the briefed review on #100), or a `NOERROR` whose answer holds records but no PTR record and whose authority is empty (a CNAME the reply leaves unresolved, records of another type). After a reply without a usable answer the next configured server is asked; the agent follows no referral or CNAME itself, and sends no query but the one PTR query to each configured server in turn. Only `rdns_no_name` lets the server clear a stored name (§5.7), so a resolver outage, or a firewall that drops port 53, leaves the names as they were; a stale name stays until a server answers again, which is accepted. One address's unanswered lookup decides nothing for another's. A job with any unanswered lookup says so in `error`, by counts only (`rdns: no DNS server gave a usable answer for N of M addresses; their stored names are kept`), unless the deadline cut the lookups short, which its own error says. **When the agent's own limits refused a reply** (#164), the error says so after the count, by limit, in lookups: of those lookups, the ones a server answered with a reply the agent did not read, for its size and for its header's counts. "Their stored names are kept" then becomes "names kept", so that the longest error still fits: `rdns: no DNS server gave a usable answer for N of M addresses, names kept; the agent refused a reply over 1232 bytes in A lookups, over 1 question or 32 records in B lookups`. A limit that refused no reply is left out (`… in 3 lookups`, never `… in 0 lookups`), and one lookup reads `1 lookup`. A lookup is counted under each limit any of its servers' replies met, so one can be in both counts; a datagram from a source other than the address and port the query went to is dropped, as above, and is never counted. A lookup a later server answered, with a name or that there is none, had a usable answer and is not in those counts, whatever an earlier server sent: they explain the lookups whose name was not learned. **When a later server answered after a refused reply** (#170), the owner is told by a notice at the end of the error, in the same words: `rdns: a later server answered after the agent refused a reply over 1232 bytes in A lookups, over 1 question or 32 records in B lookups`, counting by limit the lookups whose answer came from a later server after an earlier server's reply was refused (`scan.answered_later`, from `probe.AnsweredPastRefusal`). Such a lookup lost nothing: its answer decides its record exactly as it would alone, and the scan stays `complete`. But it spent one more query and one more packet of the budget than it needed (a first server whose every reply is refused costs up to 254 of each a scan for a /24, every scan, a little over a second of budget at the default `MAX_PPS`), and without the notice that server would show only on the day the later one stops answering, when names stop being learned. It is a notice, not a failure, and `error` is where it goes: the UI shows the text beside the last scan as "Agent reported: …", in its own place from "incomplete", which only `complete` sets; the result set has no field for a notice, and adding one would raise `PROTOCOL_VERSION` (§5.7) to carry text the field already carries. A scan whose every lookup was answered with no reply refused on the way carries no error, as before. The notice follows the counts' rules: a limit that refused none is left out, counts and fixed words only (nothing says which configured server it was, nor which address), and only a reply from the query's own address and port ends an attempt, so a datagram from elsewhere on the segment can neither set it nor raise its counts. It also follows a timeout's error or a lookup that could send nothing, counted over the lookups that returned, and it comes last. It is the first part of an error given up: when the whole would not fit the 500 the server stores, the notice is left out whole before #164's counts are. The remedy is the one below for the server whose replies are refused, or, when the later server is the one that should answer reverse lookups, to list it first. When the deadline cuts the lookups short, the count of lookups without a usable answer stays out of the error, as before #164, since the timeout's error already says they did not all run, but the refusals of the lookups that returned follow it: `timed out after T s during the PTR lookups; rdns: before the timeout, the agent refused a reply over 1232 bytes in A lookups, …`. A lookup the deadline stops returns what its attempts met, a refusal included; one the pool cancels returns nothing and is not counted. With no refused reply the text is what it was before #164, word for word. Counts and fixed words only: nothing of a reply, a name, an address or a server. The longest error a job can carry, the longest failure of each of its steps with these counts at four digits, is 458 characters (368 when the lookups end in the timeout; 495 and 405 before #20, when a job issued `fdns` began with `not run by this agent release: fdns`), inside the 500 the server stores, and is stored as sent (`test_scan.py`'s `test_the_longest_error_a_job_can_carry_is_stored_whole`). With half its lookups answered by a later server, the notice at four digits as well would take either past the 500, so it is left out whole and the same 458 (or 368) is stored as sent (`test_the_notice_is_the_first_part_given_up_by_the_longest_error`); the notice is kept whenever it fits, which on its own it always does. #93's notice of servers `ALLOWED_DNS_SERVERS` left out is given up last, after #164's counts, since it is short and names a cause on the agent's own host that no count shows: with two of three servers left out, the longest error would pass the 500, so the counts are left out whole and 457 characters are stored as sent, the notice kept (456 after a timeout, with the counts; `test_the_notice_of_servers_left_out_is_kept_over_the_refusal_counts`). The forward-DNS check's lookups (#20, below) add parts of their own, and their counts are the first given up: the order is the forward lookups' notice, the PTR lookups' notice, the forward lookups' refusal counts, the PTR lookups' refusal counts, then #93's notice. A job whose PTR lookups stop for a query that could not be sent and that has names to resolve adds `fdns not run`, and its longest error is 472 characters, stored whole, or 480 with #93's notice, still kept. A job whose PTR lookups all end with refused replies and whose forward lookups then fail too would carry both lookups' counts, 643 characters at four digits: both counts are given up, and 465 characters are stored as sent; with #93's notice as well nothing more fits, so it is given up too (`test_the_longest_error_with_forward_lookups_gives_up_their_counts_first`). The counts are kept whole or left out whole: should the rest of a job's error grow so that they would not fit the 500 (the agent's own copy of the server's cap, which `test_contract.py` holds equal to it), the error is sent with the count of lookups without a usable answer in its words before #164 and no refusal count, never cut before a number (`scan.error_text`; round 1 of the briefed review, finding 2). **What to do about it:** the two limits are the agent's, fixed in its code, and are not settings; a correct server can pass them, since both are valid DNS. A reply past 32 records can come from a resolver or authoritative server that sends its zone's name servers and their addresses with every answer (more than ten name servers, each with an IPv4 and an IPv6 address, pass it within 1,232 bytes): point the subnet at a resolver set to send minimal responses (`minimal-responses` in BIND, and in Unbound, whose default it is), which leaves them out. A forwarder (dnsmasq, Pi-hole, AdGuard Home, Technitium, a router's DNS) has no such setting: find which server produces the PTR answer it passes on (the upstream it forwards reverse lookups to, or a conditional forwarder for the reverse zone), and point the subnet, or the forwarder's reverse lookups, at a resolver that answers minimally. A reply over 1,232 bytes is from a server that ignores the payload the query advertised: one that honours it truncates instead, which is no usable answer either, so the remedy is again a minimal answer, which fits. Minimal responses leave out only the authority and additional sections: a name whose PTR record set is itself over the budget, or over 1,232 bytes, is the zone's own data, which no resolver setting shortens; only its zone's owner can. A PTR answer whose name is not a hostname is dropped (§5.7) and is not "no name": its record carries neither, and the stored name stays. A job with no live address makes no lookup and needs no server.
- **The forward-DNS check** (#20). For a job issued `fdns`, after the PTR lookups, the agent resolves each name the job sent (§5.7) through the same resolver: the servers chosen once for the job (a job with names and no live address still chooses them), narrowed by `ALLOWED_DNS_SERVERS`, one UDP query per server for the name's A records only, a slot of the `MAX_PPS` budget before each, the payload and record limits, and a reply read as a PTR reply is: the A records at the question's name or at the end of its CNAME chain in the reply, all of them, are the addresses; `NXDOMAIN`, or a `NOERROR` that `says_no_name` for that name, is a name that does not resolve; anything else (silence, `SERVFAIL`, a referral, an alias left unresolved, A records only at other owners, an SOA of another zone, a reply refused unread) is no usable answer, and the next server is asked. **A records only:** v1 is IPv4-only and a host's address is IPv4, so an AAAA record could only say "not this host"; a name with only AAAA records answers NODATA, and does not resolve to an IPv4 address. A name a server answered has an entry in the result set's `fdns`, its addresses (each once, sorted) or an empty list; **a name no server gave a usable answer for has none**, so "did not resolve" and "no usable answer" stay distinct as they are for `rdns`, and the server keeps that host's stored answer. Such names are counted in the error, `fdns: no DNS server gave a usable answer for N of M names; their stored answers are kept`, with the refusals and the later-answer notice of #164 and #170 in the same words under `fdns:`, and the scan stays complete. With no server to ask, or every server outside `ALLOWED_DNS_SERVERS`, the lookups are not made and the job is incomplete; the error names the lookups not made (`fdns not run: …`, or `rdns and fdns not run: …` when both needed a server). A forward lookup that could send its query to no server stops the rest, as a PTR lookup's does (`fdns stopped: …`, incomplete), and the answers found are reported. The forward lookups run only after PTR lookups that neither timed out nor stopped: after a PTR lookup that could send nothing, no query is handed to a socket, so they are not run (`fdns not run`, incomplete), and a timeout ends the job as before. **What the agent checks, and what it cannot.** It cannot tell whether a name is under the subnet's domain: invariant 5 (§7.2) is the server's. It refuses a job whose `fdns` is not a list of at most 4,096 entries, each a host id of the job-id form and a name in the one form `agent_protocol.fdns_name` sends (a DNS hostname, lowercase, no trailing dot), each host once: so whatever the server sends, the agent asks only DNS hostnames, only for A records, only of the servers the PTR lookups may ask, at the budget's pace, and reports back only IPv4 addresses. A server taken over can still choose the names, and read back what the subnet's DNS servers say they resolve to: that is the cost of the check, bounded by `ALLOWED_DNS_SERVERS` (who is asked), the job's limit on names, and the packet budget.

The server knows which targets are L2-local for an agent from the interfaces the agent reports at check-in. If `arp` is enabled for a subnet the agent only reaches via a router, the server drops `arp` from that job and the UI says "MAC collection unavailable — agent is not on this subnet". If that leaves the job with no liveness method (an `arp`-only target on a routed agent), no job is issued and the UI says the target cannot be scanned by this agent.

**MAC coverage is the main design constraint.** An agent collects MACs only for the subnet it has an interface in, even when it can ping other VLANs through the router.

**Documented pattern: one agent per VLAN.** Each agent is single-homed and scans its own subnet with all methods. Because the agent is small and stateless, it does not need a dedicated machine: it can be installed on any existing Linux host or container that already lives on that VLAN. The guided install in §5.6 exists to make this cheap.

Other arrangements work without code changes and are the operator's choice:

- A VLAN with no agent can be assigned to an agent elsewhere for ICMP + DNS only.
- A multi-homed agent (an interface in each VLAN, IP forwarding off) covers several subnets from one host. Not recommended: it shows up as several devices in some network controllers, and a host that touches every VLAN is the most valuable one on the network to an attacker.
- Later, a **controller collector** (§5.9) can supply MACs without any L2 presence.

### 5.3 Scan scope

Not every address in a subnet is worth scanning. The **scan scope** of a subnet is its usable addresses minus two kinds of excluded range:

| Range | Setting | Default |
|-------|---------|---------|
| The subnet's DHCP pool (`dhcp_start`–`dhcp_end`) | `scan_targets.scan_dhcp_pool` | **off** — the pool is not scanned |
| Each reserved range | `reserved_ranges.scan_excluded` | **scanned** — the flag is unset |

Reasons for the defaults: addresses in the DHCP pool change hands, so what answers there today says nothing durable about the network, and the pool is where phones and laptops live (§7.1). Reserved ranges hold statically addressed equipment the owner does care about. A range is excluded when it holds devices that should not be probed, or that someone else manages.

Rules:

- **Exclusion is absolute.** No packet of any method is sent to an excluded address, including one that has a host record. A host recorded inside an excluded range has no observation, no scan-derived `last_seen`, and raises no findings (including `stale` and `fdns_mismatch`). The UI shows "not scanned" for it. An owner who keeps static leases inside the pool and wants them tracked turns pool scanning on.
- **Exclusion wins.** An address in both an excluded and a scanned range is excluded.
- **One function decides.** `services/scans.scan_scope(subnet)` returns the in-scope ranges. Job creation, ingest validation, findings, and the UI all call it; nothing else works scope out.
- **Leaving scope deletes data.** When a change puts addresses out of scope (pool scanning turned off or the scan target deleted, a range excluded or added excluded, the pool or CIDR edited), their observations and dismissals are deleted in the same transaction (`services/scans.drop_out_of_scope`), and so are the forward-DNS answers (§5.4) of the hosts at those addresses (#20).
- **Scope changes are audit-logged** like any other subnet or reserved-range write.
- **Scope is not configurable over MCP** (invariant, §7.2). `add_reserved_range` over MCP creates a scanned range, which leaves scope unchanged. `delete_reserved_range` over MCP refuses a range with `scan_excluded` set, with an error saying to remove it in the UI, because deleting it would widen what is scanned. `scan_dhcp_pool` lives on the scan target, which MCP cannot reach at all.
- When the pool is scanned, an unknown address inside it is still classified `dynamic` and hidden by default (§5.5).
- A subnet with no DHCP pool defined shows the pool setting disabled.

Scan ingest never touches `hosts`, so the "every write is audit-logged" invariant holds without logging every sweep.

### 5.5 Findings (the "optional, not automatic" part)

Findings are **computed at read time** from `hosts ⋈ observations`, restricted to the scan scope (§5.3); they are not stored.

| Finding | Condition | Observed value | Offered action |
|---------|-----------|----------------|----------------|
| `unknown_host` | address alive, no host record | the MAC, or empty | Create host, pre-filled with MAC and name; status `dhcp` when `dynamic`, else `active` |
| `mac_missing` | host has no MAC, observation has one | the MAC | Set MAC |
| `mac_mismatch` | both present, differ | the MAC | Replace MAC |
| `name_missing` | host has no hostname, PTR exists | the PTR name | Set hostname |
| `name_mismatch` | PTR differs from `hostname` + effective domain | the PTR name | Replace hostname |
| `fdns_mismatch` | the subnet's scan target has `fdns`, the host's `fdns_results` row is for its current FQDN (the name a job would send for it now), and its addresses do not include the host's IP (an empty list counts) | the resolved addresses, sorted, joined with `, `, at most 12 and then `and N more` (so it fits the 253 characters a key's observed value takes: 214 at most); or `unresolved` | Informational: accept is refused, dismiss hides it |
| `stale` | host status `active`, not seen for N days (default 30) | last-seen timestamp, or `never` | Informational; offer status → `offline` |

**Identity.** A finding is identified by `(subnet_id, ip, type, observed)`. Every finding returned by the API and by MCP carries all four. Dismissals are matched on that key (§9).

**What accepting writes.** The key does not say everything an accept writes: an `unknown_host` is keyed by its MAC, or by nothing, but also proposes a name from the PTR record and a status from the pool classification, and a name finding's hostname depends on the effective domain. Each finding therefore also carries `proposed`, the host fields accepting it writes, and `fingerprint`, a server-computed digest of the key, the host at the address and `proposed`. Accept requires the fingerprint, so what is written is what the owner was shown; dismiss checks it only if sent, and does not store it.

Rules:

- `unknown_host` inside the subnet's DHCP pool (only possible when pool scanning is on) is classified `dynamic` and hidden behind a filter by default.
- No `mac_missing`/`mac_mismatch` finding is raised when `mac_randomised` is true.
- Name findings compare the PTR name with the host's FQDN, case-insensitively. Under the effective domain (host override, else subnet default), that is the PTR name with the domain stripped against `hostname`; nested labels stay in the hostname. A PTR name outside the effective domain never matches, and a single-label PTR name is a relative name, compared with `hostname` alone.
- `stale` is raised for a never-seen host only when both the scan target and the host record are older than N days. Otherwise every host would be stale the day scanning is switched on.
- `stale` judges "seen" by the rule `Host.last_seen` uses (§5.4): the later of the manual value and the observation's `last_seen_at`, never `alive`. Its observed value is that instant in ISO-8601 UTC. A subnet with no scan target raises no `stale`: nothing there says a host has gone. N is 30 and not yet configurable.
- What a name accept writes makes the host's FQDN the PTR name. Under the effective domain: `hostname` is the part before it, and the domain is left alone. Outside it (the bare domain included): `hostname` is the first label and `domain` the rest, an explicit override in `proposed`, so a PTR name `nas.example.com` in a `home.arpa` subnet is stored as `nas` + `example.com`, never as the FQDN `nas.example.com.home.arpa`. A single-label PTR name is written as `hostname` alone. The same mapping pre-fills an `unknown_host`.
- **Accept** takes the finding's key. The server recomputes the finding, under SQLite's write lock (§5.3: it writes on the strength of the scope); if it no longer exists, or its observed value or its fingerprint has changed since it was shown, that record is reported `skipped` with reason `changed` and nothing is written. A key without a fingerprint is an `error`. Otherwise it calls the existing hosts service (`create_host`/`update_host`), so validation and the audit log apply unchanged. The change summary notes the value came from a scan, and names the address and the finding type rather than the hostname or MAC, which came from the network (§7.2, invariant 8). Each record commits on its own. A dismissed finding can still be accepted.
- **Dismiss** takes the same key and stores it in `finding_dismissals`, after the same recomputation: a key that does not name a current finding is `skipped` (`changed`), so a stored observed value is always one the server computed. A finding is hidden while a dismissal with the same observed value exists; it reappears when the observed value changes. Dismissing is an owner write: one `subnet` audit entry per subnet per request, with a count in its summary and the keys in `after`. Dismissals deleted because their address left scope go with the change that narrowed it, as observations do.
- Findings are listed by `GET /subnets/{id}/findings`, which takes `type` and `include_dynamic`. Each finding also carries `ip_int`, `host_id`, `dynamic`, `proposed` and `fingerprint`.
- Bulk accept is per finding type per subnet, with per-record results (`accepted`/`skipped`/`error` + reason), matching the existing bulk endpoints.

### 5.6 Agent

- Python, in `agent/` in the same repo, published as a second image. Dependencies limited to an HTTP client (httpx), `icmplib`, and `dnspython`. ARP uses the standard library, and so does reading the host's interfaces (rtnetlink). The agent does not import `api/app/agent_protocol.py`, which needs pydantic: it keeps copies of the constants and rules it needs (`agent/src/tlg_ipam_agent/protocol.py`), and its tests check each against the server's module.
- **What the agent reads and writes on its host, and how.** One module, `store.py`, opens files itself (#22), for one file the running agent uses: its stored agent token, `/var/lib/tlg-ipam-agent/token`. It reads it without following a link at the path's last component (`O_NOFOLLOW`; a link in a directory above it is followed, and those directories are root's) and without waiting on a FIFO (`O_NONBLOCK`, then `fstat`), at most 4 KiB, and writes it once, at the enrolment exchange: created beside its path exclusively, with its mode (0600) and owner set before anything is written, flushed, and renamed into place. `tlg-ipam-agent install` writes its files and directories through the same module. No other agent module calls `open` in any spelling, `os.open` included, or renames, removes or changes the owner or mode of a file. Libraries open what else it reads: pathlib reads an interface's MAC from `/sys/class/net`, dnspython opens `/etc/resolv.conf` once `os.stat` has found it a regular file of at most 64 KiB (§5.2), and the TLS stack loads its CA bundle (`SSL_CERT_FILE`). The agent starts no process; `install` (`install.py`, alone) runs `useradd`, `userdel`, `groupdel` and `systemctl`, with fixed arguments, a fixed `PATH` and no shell. A running agent never imports `install` or `trust`. That is not to say `subprocess` is absent from it: the standard library's asyncio imports it in every agent process. What keeps a process launch out of the agent is that no agent module but `install.py` names one, and that nothing the server sends reaches `install`'s fixed argument lists. `agent/tests/test_invariants.py` holds this as a tripwire on the agent's source, not a proof: it refuses the listed names (`open`, the ways of writing, renaming and removing a file the allowed modules name, and those of starting a process) outside the one module each is allowed in, and the spellings of having a library open a file outside the module listed for each, and sees no spelling it does not list (`AGENTS.md`).
- Linux only. Runs as a container with `network_mode: host` and `CAP_NET_RAW`, or as a systemd unit in an LXC. Host networking is required to reach the VLAN's L2 segment.
- Configuration (env): `IPAM_URL`, `IPAM_ENROL_TOKEN` (first start) or `IPAM_AGENT_TOKEN`, `ALLOWED_CIDRS`, `ALLOWED_DNS_SERVERS`, `MAX_PPS`. Both tokens set is refused at start.
- **`ALLOWED_CIDRS` is an agent-side guard**, defaulting to RFC 1918 + CGNAT ranges. The agent refuses any job whose subnet is outside it, or whose ranges are outside the job's subnet, and reports the refusal. Reason: the server tells agents what to sweep, and a mistyped public CIDR in the IPAM must not turn the agent into a scanner pointed at someone else's network. It also refuses a job whose ranges hold more than `OBSERVATIONS_MAX` (4,096) addresses, counted before any list is built, and one that is malformed (§5.7). A value set but empty, or a network with host bits set, stops the agent at start rather than being guessed at.
- **`ALLOWED_DNS_SERVERS` is the same kind of guard for the PTR lookups** (#93), unset by default. A job's `dns_servers` are the subnet's resolvers, which may legitimately be public and need only be IP addresses, so a server that has been taken over could otherwise point the agent's queries at a resolver of its choosing, each carrying the reverse name of an address inside `ALLOWED_CIDRS`, at most three servers a lookup. Set, it lists the addresses or networks (an address alone is that one server) every DNS server the agent asks must lie in, the job's and those of the host's `/etc/resolv.conf` alike, and a server outside it is sent nothing (§5.2). The job is not refused, as a subnet outside `ALLOWED_CIDRS` is: its liveness sweep owes nothing to the subnet's DNS settings, so it runs, the servers inside the list are asked, and the error says how many were not; with none inside, no lookup is made and the result set is incomplete, so stored names are kept. An IPv4-mapped IPv6 address lies outside every IPv4 network. **A scope is never matched** (round 1 of the briefed review, finding 1): `ipaddress` finds `fe80::53%2` inside `fe80::53%1/128`, or inside an unscoped `fe80::/10`, whatever its scope, while dnspython sends the query to the interface the scope names, and the same link-local address is another host on each interface. So an IPv6 item with a scope (`fe80::53%eth0`, `fe80::%2/64`) stops the agent at start, named by its place, and a DNS server written with a zone suffix (`%…`, `%0` included), the job's or `resolv.conf`'s, is never inside the list, whatever it holds, so an unscoped `fe80::/10` lets no zoned server through. Such a server is left out and counted as any other outside the list. A link-local server written without a zone is compared by its address alone, as any other: inside the list it is kept, and its query is handed to the socket with no interface named, so the host's routing picks the link it goes out on (Linux by route lookup, macOS by its default zone where one is set); the setting does not decide that link, and no kernel refusal is relied on (round 2 of the briefed review, finding 1). Unset, a scoped server is asked exactly as before. Matching scopes instead would mean equating interface names with indexes, which a host can rename or renumber between start and query; a subnet's resolvers are rarely link-local. Unset, every server is asked as before; there is no default list, since public resolvers are a legitimate choice. A value set but empty, a name, a URL, or a network with host bits set stops the agent at start. The container takes it as `-e ALLOWED_DNS_SERVERS=…`, and the systemd unit from `install --allowed-dns-servers …` (#179), which writes it to `agent.env`, checked by the agent's own parser (`config.parse_allowed_dns`) before anything changes, a bad item named by its place. **An update run without the option keeps it**, as `agent.env` holds it (`install.kept_allowed_dns`), where every other setting is the run's own options: `ALLOWED_CIDRS` left out falls back to the private ranges, but this setting left out is any server, so dropping it on an update copied from the Agents page (which renders no options) would widen what the agent may ask without a word. Giving the option replaces it; deleting its line from `agent.env` (then `systemctl restart`) removes it. The read is strict: `agent.env` is read through `store.read_small` (a regular file of at most 4 KiB, no link; `install` never writes one larger), and only once the whole file is found in the grammar `install` writes (`install.env_assignments`), every line, unrelated ones included: split at `\n` alone, one trailing `\r` allowed, printable ASCII with no backslash, and each line empty, a comment (`#` or `;` first) or an unquoted `NAME=<value>` whose value holds only the characters `install` writes. Then the last `ALLOWED_DNS_SERVERS=` assignment decides, as in systemd. systemd's own grammar is wider (a quoted value can run across lines, a backslash continues a value onto the next line, and `\r` ends one; a backslash at the end of a comment, which systemd 257 does not take as a continuation, is outside `install`'s grammar all the same, since it allows no backslash anywhere), so a file read line by line could hold a line that is part of another value to systemd, or hide one systemd reads (round 1 of the briefed review: `OTHER="a`, `ALLOWED_DNS_SERVERS=0.0.0.0/0`, `b"` under a real `10.0.0.53` was kept as `0.0.0.0/0`). Anything outside the grammar, or a file that cannot be read, stops the update before anything changes, naming the line by its number and saying to give the option. Before #179 the docs set it for the unit in a drop-in (`Environment=ALLOWED_DNS_SERVERS=…`). Such a drop-in still applies while `agent.env` sets no value, and has no effect once it does: systemd applies `EnvironmentFile=` over `Environment=`, whichever file each comes from (measured on systemd 257); remove the drop-in's line when moving the setting to the option. The agent reads its settings once, at start, so a change to it takes effect at the restart `install` makes, or at `systemctl restart tlg-ipam-agent` after an edit by hand (a container's, when it is recreated with the variable); the start-up log line names `ALLOWED_DNS_SERVERS` as the agent took it, `unset` or the list (round 1 of the briefed review, finding 2).
- Rate limit (`MAX_PPS`, default 200 packets/s, 1–1000) and a per-job timeout (default 10 minutes; a longer `timeout_s` from the server is cut to it, so a scan always ends while its lease is live). Server refuses to create a scan target for a prefix shorter than /20. One echo request per address, a 1-second wait for its reply, at most 64 in flight.
- **`MAX_PPS` counts packets, not lookups.** Every datagram or frame the agent sends takes a slot from one budget, shared by the ICMP sweep, the ARP sweep (each request and each retry) and the PTR lookups, and kept by the agent from one job to the next, so the second in which one job ends and the next begins is held to it too. **What it bounds** is when the agent hands a packet to the kernel. Each packet is handed over in the step of the agent's event loop in which its slot is granted, before that step's first wait: an ARP request in the step that asked for the slot; an echo request in its probe's first step, in which the probe asks for its own slot (icmplib hands the request over before its first wait); a DNS query in the step that asked for the slot, on a UDP socket the agent made before it asked (bound to no port until the query goes). A slot ends when that step ends, so after its packet has been handed over, however long that took, and the next slot is granted no sooner than `1/MAX_PPS` after the slot before it ended, measured on the agent's clock. So no two packets are handed over less than `1/MAX_PPS` apart, and no window of one second holds more than `MAX_PPS` of them. Nothing is caught up: a pacing sleep that wakes late, or a hand-off the agent's process makes late (the host's scheduler, a garbage collection, other callbacks ahead of it), moves every later slot with it; a sleep that wakes early sleeps again; waiters (the PTR lookups wait 16 at a time) are served one at a time in the order they came. Measuring each slot from the grant before it, as the agent did until #121, let a hand-off delayed by a slot or more be followed at once by the next one. A packet the socket cannot take at once is not kept to go later: an ARP request or a DNS query that meets a full send buffer is a failed send (for a query, an attempt that sent nothing), and a lookup's socket is aborted when the lookup ends, cancelled or not, so no query of a job leaves after it, nor during the next job. The end of a slot is a callback the event loop runs after the step, and the next grant waits for it, so the loop turns between any two grants, even when every slot is already due and no send ever waits: a task that is ready waits for at most one send, and one that a timer or a readable socket wakes (the ARP listener, a check-in, the job's deadline, a cancellation) for at most one more. **What it does not bound:** the time from the hand-off to the wire (the kernel's and the device's queues), and the kernel's own neighbour resolution. Before the echo request to an on-link address that is not in its neighbour table, the kernel sends ARP of its own, which the agent neither sends nor counts: one request for an address that answers, and for one that does not, `mcast_solicit` requests (3 by default) `retrans_time_ms` apart (1 s), measured on Linux on a Docker internal network. So the ICMP sweep of a subnet the agent is on can put up to three of the kernel's requests on the wire for each silent address beside the agent's `MAX_PPS`. Counting a slot for them would not bound them, since the agent cannot see which addresses the kernel already has and the retries follow the kernel's timer, and running the ARP sweep first would not prevent them: a reply to the agent's own request does not enter the kernel's table (`arp_accept` is 0 by default; measured the same way), so the kernel still asks at the echo request. A host that needs the kernel's share bounded lowers `mcast_solicit`, or scans the subnet with `arp` and `rdns` only. The agent sends its DNS queries itself (`dns.asyncquery.udp`), not through dnspython's resolver, whose failover, retransmission and TCP fallback would send datagrams the budget never saw: a PTR lookup is one UDP query per server, to at most 3 of the job's servers (or the host's own) in turn, each taking a slot, with no retransmission and no TCP. A query carries EDNS(0) advertising a 1232-byte UDP payload, so a resolver can send a PTR answer whole rather than truncate it; the largest ordinary answer measured (a 253-character name behind two CNAMEs of classless delegation, for an IPv6 address, with four name servers and their addresses) is 710 bytes. The advertised size is also the most the agent reads (#153): a datagram longer than it from the server's address and port is not parsed, and that attempt ends as no usable answer, so the next server is asked; one from any other source is dropped, as a reply from another source is at any size. The same holds for a reply whose 12-byte header claims more than one question, or more than 32 records in its answer, authority and additional sections together (the OPT record of EDNS among them; #160): it is not parsed, and from the server it ends the attempt as no usable answer. The largest legitimate answers built claim 16 (the 710-byte answer above: two CNAMEs and the PTR record, four name servers, an A and an AAAA record for each, and OPT) and 5 (four PTR records of 253 characters at one name, about 1,090 bytes), and 32 is twice the larger. The counts are the sender's claim, and dnspython reads by them: a reply that holds more than it claims is parsed only as far as the counts and then refused for its trailing bytes (`ignore_trailing` is off), and one that holds less runs out and is refused as malformed, so either way the parse's work is bounded by what the header claims. A datagram shorter than a header has no counts and is refused by dnspython as malformed. A server that honours EDNS truncates instead, so a longer datagram is one the agent did not ask for. The limit refuses some valid answers: a server that ignores the advertised size and sends a longer answer whole (60 PTR records at one name, each as short as `host00.home.arpa.`, come to 1,315 bytes) is refused like any over-size reply. That address's name is not learned and a stored one is kept, and the owner sees only the job's error that no DNS server gave a usable answer for some of its addresses, a count with no reason. The record budget refuses valid answers too, with the same result: 32 or more PTR records at one name beside the OPT record a server adds (32 as short as `host00.home.arpa.` and an OPT come to 727 bytes, and the briefed review's 32 to 1,010, each a valid reply whose header claims 33), and a server that sends its zone's name servers and their addresses with every answer when the zone has more than 10 of them with both an IPv4 and an IPv6 address (9 behind two CNAMEs) (a resolver that sends minimal responses, as recursive resolvers commonly do, sends none). SERVFAIL, REFUSED, no answer or a truncated reply (TC set, used for nothing even if it carries a PTR record, and not retried over TCP) moves to the next server; NXDOMAIN or a whole answer ends the lookup. A lookup's 2 seconds start when its first query gets a slot, not while it waits for one, and the job's deadline caps them; a lookup the deadline cuts off makes the result incomplete. No ping or lookup is given longer than the job's time left, and a sweep that runs into the deadline is incomplete. As a backstop, a scan still running 30 s after its timeout (on the event loop's own clock) is stopped and reported as an agent error with no observations, so one stuck await cannot hold the agent's single worker until the job's lease runs out. The backstop stops an await, not a call that blocks the event loop itself, which nothing on the loop can interrupt: that is why the host's `resolv.conf` is read in a thread, with its own bound (§5.2).
- **Every request to the server has one deadline** (30 s) for connecting, sending, headers and body: httpx's own read timeout is per chunk, so a server that drips its answer could otherwise hold a request for ever. A results request also ends when the job's lease runs out. An answer is read undecoded: the agent asks for `identity` and refuses any other content encoding, so a small compressed answer cannot expand in memory. Each network read (at most 64 KiB) is checked against the 1 MiB cap before it is held. A 200 is acted on only in its route's shape (an integer `checkin_interval_s` and a `jobs` list; an integer `accepted` and a `rejected` list of `{ip, reason}`); anything else is retried like a 503 and starts no scan.
- **The agent logs no text the server wrote.** A refusal is logged as its status and, when it has the vocabulary's shape (`[A-Z][A-Z0-9_]*`), its `code`; a results acknowledgment as its validated counts; a failed connection as the exception's type and OpenSSL's reason code. A server can echo anything, the agent's token included, and making text printable is not redacting it. As a backstop, every log record is filtered to replace the configured token.
- A job issued a method this release cannot run (none since #20: `fdns` was the one), or issued `arp` when no interface of the agent's host with a MAC is on the subnet, runs the methods it can and is reported with `complete: false` and the reason in `error`; a sweep that skipped an issued liveness method also has `liveness_complete: false`, so it never lets the server mark a silent address dead. So is a job issued `rdns` whose PTR lookups had no DNS server to ask, whose every server is outside `ALLOWED_DNS_SERVERS`, or that could send their query to none (§5.2), with `complete: false`: a lookup not made says nothing about a name, so the server keeps the stored ones. Its liveness sweep did complete, so `liveness_complete` stays true and the dead are still marked (#100). `liveness_complete` is true when every issued `icmp` and `arp` sweep ran over every address before the deadline: a ProbeError in either, `arp` with no interface to run on, or a deadline reached in either makes it false; nothing the PTR lookups do does.
- TLS verification on, no opt-out flag. A private CA is handled by mounting a CA bundle and naming it in `SSL_CERT_FILE`. `IPAM_URL` must be `https`; plain `http` is accepted only to the agent host's own loopback, where nothing crosses a network.
- The container runs as root inside its own namespaces so that `CAP_NET_RAW` is effective for its raw ICMP and ARP sockets. `--cap-add NET_RAW` adds that capability to the runtime's default set; it does not drop the others, and Docker's defaults already include it. A least-privilege command would be `--cap-drop ALL --cap-add NET_RAW`; the Agents page does not show one yet.
- **Updates are the operator's job** (pull a new image or re-run the install command). Once installed, the agent never downloads or runs anything the server sends.
- Rootless container runtimes cannot grant a usable `CAP_NET_RAW` on the host network. Document this as unsupported.

- **Where the names in the commands come from** (#23). `<version>` is the server's own, from `GET /health`, when it is a PEP 440 public version in its normal form (`0.2.0`, `0.2.0rc1`, `0.2.0.dev0`; a spelling PEP 440 normalises to another, such as `00.02.00` or `0.2.0rc01`, is not); otherwise the page shows `<version>` for the operator to fill in rather than guess an artefact name. `<registry>` is `ghcr.io/deusmaximus`, and the release wheel URL is `https://github.com/DeusMaximus/TLG-IPAM/releases/download/v<version>/tlg_ipam_agent-<version>-py3-none-any.whl`. The release pipeline (#24) publishes both under exactly those names, and gives the server and the agent the one version, so a command the page renders for a server resolves to that server's release. No command holds the agent token (`tlga_…`), which the page never sees; the enrolment token is in the container command alone, and the systemd install reads it from standard input. `web/src/utils/install.test.js` holds every rendered command to the shapes in these two tables.
- **A page served over plain HTTP** (#21, #92). The commands carry the page's origin only when it is `https`, or plain `http` on a loopback host (the agent's own rule for `IPAM_URL`); anywhere else they carry `https://<server>`, so no command sends a token across the network in clear. The enrolment token itself reaches the browser in the answer that issues it, so on such a page the Add agent form and the re-enrol confirmation say so before the request is made, and still make it when the owner goes on. Beside the token, the page says that it has crossed in clear, and that the agent token, which the exchange returns, crosses only if the exchange is made over plain HTTP, which the commands never do. One rule, `install.agentServerUrl`, by the protocol and hostname the browser gives, decides every one of these warnings; the page parses no address. The owner key crosses the same way on every request from such a page: that is the deployment guidance's subject (#31).
- **The server renders the command; it does not serve the code.** The image comes from the project's GitHub container registry and the wheel from the GitHub release, both pinned to the version matching the server. A compromised server therefore cannot hand a new agent host something to run as root. Releasing a version means publishing both artefacts, built in CI from the tag (#24): `.github/workflows/release.yml` runs for a tag `v<version>` on a commit of `main` whose server (`api/app/version.py`) and agent (`__version__`) are both at `<version>`, builds the wheel and the image (`linux/amd64` and `linux/arm64`), checks them, publishes them under the names above with a write permission only in the two jobs that publish, and fetches both with no credential, as the commands do. Neither publish job writes until the registry or GitHub has answered what the version already holds: a read that does not say is retried, then stops the job with nothing written, and a tag with more than one release stops it too (#159). The image's base is named by digest in `agent/Dockerfile` (#94): the multi-platform index of `python:3.13-slim`, which holds both platforms' images, with the tag kept for the reader. The digest is moved forward by hand, by the command in `AGENTS.md` (Commands), at the latest before each release; the release's build warns, and does not fail, when the tag names another index. `.agents/releases.md` is the release checklist.
- **The systemd install lives under `/opt`, not in a user's home.** The service runs as a dedicated unprivileged user, which could not execute a virtual environment inside another user's home directory, and a per-user install is not on `sudo`'s path.
- **Enrolment tokens.** "Add agent" creates the agent in state `pending` and an `enrol` token bound to it, single-use, expiring after 1 hour. It is exchanged at `POST /api/v1/agent/enrol` for the long-lived `tlga_…` token. The agent stores the answer's token only if it is of exactly the form the server issues, `tlga_` and 43 characters of the URL-safe base64 alphabet (`agent_protocol.AGENT_TOKEN_FORM`, which states it for both kinds of token; #140), and takes any other answer as a `200` not in the route's shape (§5.7), after the enrolment token is spent: that form is part of the wire contract. A server that issues another raises `PROTOCOL_VERSION`, and that is what keeps an agent of an earlier release from spending its enrolment token on it (#165): the enrol body states the agent's protocol, none stated meaning protocol 2, and the exchange refuses a protocol other than its own (`409 AGENT_TOO_OLD` or `AGENT_TOO_NEW`) before it claims the token, so the token still enrols the agent once it runs the matching release. A change to the enrol answer, its token's form included, made without raising `PROTOCOL_VERSION` still has an earlier agent answered `200`, refusing the answer, with its token spent (`agent/tests/test_e2e.py` shows both). A command left in shell history or a chat log is useless afterwards. **The agent's protocol, before the claim** (#165). The agent sends its `PROTOCOL_VERSION` as `protocol` in the enrol body; a body without it, or with null, is protocol 2's (`agent_protocol.ENROL_PROTOCOL_ABSENT`), since every release before #165 spoke 2 and sent none, and that stays its meaning whatever the server's protocol becomes, for as long as such agents may exist: a server of protocol 3 refuses them before their tokens are spent. The exchange reads it once the token is found usable and its body has arrived, before the rest of the body (which another protocol may shape differently) and before it takes the write lock, so the claim is never reached: an integer other than the server's `PROTOCOL_VERSION` is `409 AGENT_TOO_OLD` (lower) or `409 AGENT_TOO_NEW` (higher), with a fixed message that names neither protocol, nothing written and the token unused (`agent_protocol.enrol_protocol_refusal`). The rule is check-in's, so enrolment never spends a token on an agent whose every check-in would be refused. Anything else that is not an integer is a `422` at `protocol`. A server before #165 ignores the field, as it ignores every unknown one, and enrols as before. Adding the field did not raise `PROTOCOL_VERSION`: a protocol-2 agent that sends it and one that does not are enrolled alike by every server. The container agent logs, from the status and code alone, which release to install (the agent's, or the server for `AGENT_TOO_NEW`) and that the token was not spent, and tries again on the refusal rule's wait; `install` says the same and to run it again with the same token. The exchange is accepted strictly before `expires_at`, judged when the claim is made (once the exchange holds the write lock: after the body has arrived, however slowly, and after any wait for SQLite's writer), once (a compare-and-set on `used_at` that also requires the token unrevoked and its agent not disabled), and in one transaction marks the token used, revokes any agent token the agent held, issues the new one, makes the agent `active` and stores what the body reports. It is the agent's own write: audit entries with `source="agent"` and `actor` `agent:<name>` (§4.3) for the enrolment token's use, the old token's revocation, the new token, and the agent. It writes no scan target and no lease.
- **Where the exchange happens and where the token lives.** Container: the agent exchanges `IPAM_ENROL_TOKEN` on first start and stores the token in the named volume, `/var/lib/tlg-ipam-agent/token` (root's, mode `0600`; the image's directory is root's, `0700`, which a new volume takes). The token file is created, empty, before the request, so a state directory that cannot take it (none mounted, read-only, not root's, writable by others) stops the agent before the enrolment token is spent; an agent token that is issued but cannot be stored stops it too, since it would be lost at the next start. The exchange and the write hold an exclusive `flock` on the state directory, and the stored token is looked for again once it is held, so two agent processes sharing one volume enrol once and both use that token. A state directory that is not a mount point (in a container, no volume) is warned about at the exchange, since the token would not outlive the container; it is not refused, since a host run outside a container keeps it on its own disk. systemd: `tlg-ipam-agent install`, running as root, does the exchange itself and writes the token to `/var/lib/tlg-ipam-agent/token`, owned by the service user, mode `0600`, in a directory root owns (`0755`; one already there is given that mode, and refused if anyone but root owns or can write it). The service user can read it on every start and never needs write access, and the enrolment token never reaches the disk.
- **The enrolment token is never on a command line.** `install` takes it on standard input alone (`--enrol-token -`), asking for it without echo on a terminal; any other value of `--enrol-token` is refused before standard input is read, without repeating it. A command line the parser refuses is answered the same way (#140): argparse would quote the argument it refuses (an unknown command, an argument it does not recognise, a value after an unknown option or after `--enrol-token -`, a value given to `--help` or `--version`, an ambiguous option with its `=value`), so the error names the kind of problem and repeats nothing typed, and says that a token typed into the command was not used but is to be treated as exposed. argparse's messages made of the parser's own names alone ("the following arguments are required: --url", "argument --url: expected one argument") are kept as it writes them, and the help text is argparse's. `install`'s own checks of an option's value repeat none either: an item of `--allowed-cidrs` or `--allowed-dns-servers` (or of the agent's `ALLOWED_CIDRS` or `ALLOWED_DNS_SERVERS`, the one kept from `agent.env` included) that is not a network is named by its place in the list ("item 3 of 4"), and a `--ca-file` that is missing, is not a regular file, or that the service user cannot read is named by the problem, never by its path (the briefed review of #140). Two measurements in #22 decided this. Under `sudo`, a token given as an argument reaches the disk: sudo logs the whole command line, and with a persistent journal (Debian 13's default) both sudo's log line and journald's record of sudo's command line hold it. From any shell, root's included, an argument is readable by every local user in `/proc/<pid>/cmdline` for as long as the exchange takes, so a slow server leaves another user time to spend the token first (the review of #130). A token piped in (`echo tlge_… | sudo … --enrol-token -`) is in the shell's history, which is the operator's: a token left there is spent, as one in a chat log is.
- **A refused exchange is not repeated in a loop.** The container's exchange is answered as a check-in is (§5.7): `429`, a 5xx or no answer waits the bounded back-off; `401`, `403` or any other 4xx waits 13.5–15 minutes, since a used, expired or revoked token stays so and only a disabled agent, or a server updated to the agent's protocol (`409 AGENT_TOO_NEW`), can come right by itself. The process keeps running while it waits, so a container's restart policy does not make a refusal a restart loop, and the enrol route's throttle, shared by every caller, is not held full by one agent with a spent token. `install` makes one attempt and says whether the token is spent.
- **A stored agent token always wins.** If the agent finds a stored token it ignores `IPAM_ENROL_TOKEN` (and logs that it did). The container's volume is what lets the image be updated by recreating the container without enrolling again. The order is: `IPAM_AGENT_TOKEN`, when set (a token the operator holds, as in M2a; the state directory is then neither read nor written), the stored token, an exchange of `IPAM_ENROL_TOKEN`. A stored file that is not an agent token stops the agent rather than being enrolled over. To enrol a container again (re-enrol), remove its volume or the token in it first.
- **Re-enrol.** An existing agent has a "Re-enrol" action that issues a new enrolment token for the same agent. Exchanging it revokes the previous agent token. The agent keeps its identity and scan targets. This is the recovery path for a lost volume, a rebuilt host, or an enrolment whose response never arrived. Re-enrol revokes an enrolment token the agent still holds unexchanged, reading the agent's tokens under the write lock, so at most one can be exchanged even when two re-enrols meet, and leaves the agent token alone until the exchange, so the agent keeps running until the new one is in use. A disabled agent is refused (`409`): it is enabled first, so that no exchange hands a token to an agent the owner has stopped. A job leased under the old token is not cleared: it runs out with its lease.
- The enrol endpoint has a small global attempt throttle; it is the only agent route reachable without a long-lived token. At most 10 attempts that did not enrol in any 60 seconds, across all callers, in the server's memory; an attempt that enrols gives its place back. While the window is full every attempt is `429 RATE_LIMITED` before its token is looked up or its body read, and a throttled attempt does not count. Per-client limits are not used: behind the proxy or tunnel the owner runs, a client's address says nothing. The tokens are 256 random bits, so the throttle is not what stops guessing; it bounds the work and log noise of the one unauthenticated agent route. Anyone who can reach it can keep the window full and hold new enrolments off; enrolled agents are not affected.
- `tlg-ipam-agent install` creates the service user (`tlg-ipam-agent`, a system user with its own group, no home and no login shell), enrols as above, writes `/etc/tlg-ipam-agent/agent.env` (server URL and settings given as `--allowed-cidrs`, `--allowed-dns-servers`, `--max-pps`, `--ca-file`; no secrets), installs a systemd unit with `AmbientCapabilities=CAP_NET_RAW` (and `CapabilityBoundingSet=CAP_NET_RAW`, `NoNewPrivileges=yes`; no namespace sandboxing, which can keep a unit from starting in an LXC), and enables and starts it. **Only root can change what runs as root.** `install` and `uninstall` run the venv's code as root, and the unit runs it with `CAP_NET_RAW`, so before either imports any of the agent's modules but the package, `cli` and `trust` (and so before any dependency), `trust.check` refuses the command unless every path it looks at is owned by root and writable by neither its group nor others. It looks at: the interpreter the unit names, resolved one path component and one link at a time from `/`, so every directory on the way and every directory a link passes through counts; every entry of the installer's `sys.path` (the venv's site-packages and `bin`, the standard library, anything `PYTHONPATH` or a `.pth` file adds), resolved the same way and then walked whole, every file and directory, a link in it followed and a linked directory walked; and the agent's package directory, wherever it was loaded from. The current directory, which `python -m` puts on `sys.path`, is taken off it before the check, so nothing later is imported from it and the walk never covers a working directory such as `/`. What it cannot see: what has run before it (the interpreter's start-up, `site` and the `.pth` files it processes, `sitecustomize`; the package's `__init__`, `__main__` or the console script, `cli` and `trust`; and the standard-library modules they import), which lies in the trees it walks, so a changed file there is refused, but only after it has run; native libraries loaded from outside Python's import path (the interpreter's own, libc, libssl); and a change made after it, which only root could make. `install` also refuses a venv the service user could not use (made under umask 077, say), and the kernel is what answers that too (#169): once the account exists and before anything is written or the token spent (on a first install, the account it made for the check goes again), it runs the interpreter the unit names as that user, with the groups systemd gives the unit's process, on the agent's own `reach` module (`python -I -B -m tlg_ipam_agent.reach`: no argument, no input, its output discarded), and judges by how that ends. That it starts at all shows that the user can execute the interpreter by the unit's path (every directory and link on the way, a `noexec` mount) and that Python's start-up can open what it reads first (the standard library it imports, the venv's `pyvenv.cfg` and `site-packages`, the package's `__init__` and `reach`), by real opens; `reach` then walks the venv and the package directory and exits 3 at the first directory that user cannot list and enter, or regular file it cannot read, and 7 when there is none, as `os.access` answers (POSIX ACLs and every group it holds count; a security module that checks only an open does not), passing over `__pycache__` (Python compiles the source when it cannot read the cached bytecode, and the installer, run as root, leaves bytecode there of root's group, which in a venv the user reads through a group it cannot read), and names it on stderr, so the operator can run it by hand as the service user to see which. A source the user cannot read is refused even when a cached bytecode file it can read would let Python import the module without it: that cache is the root-run installer's, rewritten or dropped as the source changes, and is not counted on. Only 7 is taken as usable, never an exit 0: `-I` keeps the working directory, the user's site directory and `PYTHON*` variables out of the start, but the venv's `.pth` files and a `sitecustomize` still run before `reach`, and one that ends the interpreter with status 0 would otherwise pass an environment the walk never looked at (the briefed review of PR #178). That tells an ordinary early end apart from the walk's answer; it does not attest against start-up code written to lie, which only root can put in the venv (`trust.check`). The refusal says whether the start or the walk stopped, without the path; a check that cannot be made (the start refused for another reason than the exec's `EACCES`, an exit 0 or a signal before `reach` answered, or not done within 60 s) refuses the install too. It is not a check that the agent's code works or that every module it imports later loads, only that it can be read; and it answers for the unit `install` writes, as the `--ca-file` check below does. Running the venv's own code as the service user before the token is spent adds no code to what that user runs: it is the code the unit runs as that user, which `trust.check` has found only root can change, started fresh (the child holds nothing of the installer's memory once it has exec'd). `--version`, which the release check runs, would show the start alone, which an environment whose dependency was installed under umask 077 passes. A fixed program that walks the tree as the user (`find` with `-readable`) would show the walk alone, by GNU find's predicates, which not every host's `find` has; it would not show the exec. A `--ca-file` must be readable by the service user, once the account exists and before the token is spent (the review of #130), and the kernel is what answers it (#136): the install runs `head -c 1` on the file as that user, with its primary group and every group the user database lists it in (the groups systemd gives the unit's process), so POSIX ACLs, supplementary groups and every directory and link on the way count as they will for the agent. When the read fails, `test -e`, run the same way, says whether the user cannot reach the path or reaches it and cannot read it, and the refusal says which, without the path. A check that cannot be made (a program missing or refused, or one not done within 10 s, as a FIFO put in the file's place would hold it) refuses the install too. The two programs are fixed, with no shell and the install's fixed environment; their one argument that is not fixed is the operator's own `--ca-file` path, and nothing the server sends reaches them. It answers for the unit `install` writes, not one a drop-in changes: a group a drop-in adds with `SupplementaryGroups=` is not seen, and `InaccessiblePaths=`, a private mount namespace or a security profile of the unit's own can read differently from `head`, either way. The exchange trusts exactly what the unit is given (`install.service_trust`, which also writes `agent.env`): the inherited `SSL_CERT_FILE` and `SSL_CERT_DIR` are dropped before its TLS context is made, and an install whose environment sets either one to anything the unit would not get (any `SSL_CERT_DIR`; an `SSL_CERT_FILE` other than the `--ca-file`) is refused before anything changes. A unit inherits nothing of root's environment, so a CA trusted only there would let the exchange spend the token on an agent that could not verify its server (round 2 of the review of #130). A unit does receive the system manager's own environment (`systemctl set-environment`, `DefaultEnvironment=`), which the installer cannot see, so the unit discards it itself (#138): it lists in `UnsetEnvironment=` every trust setting `agent.env` does not give (`install.discarded_trust`: `SSL_CERT_DIR` always, `SSL_CERT_FILE` without `--ca-file`). systemd applies `UnsetEnvironment=` after the manager's environment, `Environment=` and `EnvironmentFile=`, whatever the order of the lines, and `EnvironmentFile=` overrides the manager's value, so with `--ca-file` the agent sees `agent.env`'s `SSL_CERT_FILE` and without it neither variable (measured on systemd 257, Debian 13; the PR of #138 has the runs). It covers the two variables OpenSSL reads to choose its default CAs, and leaves out a drop-in the owner adds: one that sets either needs an empty `UnsetEnvironment=` in it too, which clears the unit's list. Everything that can fail locally comes before the exchange, and if the install fails before the token is stored, what it created is taken away again. Run again without `--enrol-token` it keeps the stored token, writing it again owned by the service user with mode `0600`, and rewrites the rest (an update); with a token stored, `--enrol-token` is refused. `install` reuses a `tlg-ipam-agent` account it finds, and records the uid and gid of one it creates (`/etc/tlg-ipam-agent/created-user`). `tlg-ipam-agent uninstall` reverses it: it stops and disables the unit, and removes it, both directories and their files, and the account and its group only if the record names them still; one the install found, or one replaced since, is left and said so (the review of #130). The record is removed last, once the account and group it stands for are gone, so an uninstall whose `userdel` or `groupdel` failed (the account busy, say) can be run again and finishes the job, a user already gone and its recorded group left included (round 2). An install stopped between `useradd` and writing the record leaves an account nothing records: that is recovered by hand (`userdel tlg-ipam-agent`). It leaves the virtual environment, which the operator made, and the agent's record on the server.
- **Suggest, don't assume.** At first check-in the server matches the agent's reported interface to a subnet and the UI offers "Scan *subnet* with this agent?" with default methods and the default scope. One click to accept; nothing is scanned until the owner does. The match is `GET /api/v1/scan-targets/suggestions` (`scans.suggestions`, #23), computed on read: each `active` agent with each subnet that has no scan target, is no larger than a /20, and is on the link of an interface the agent reported at its last accepted check-in (`jobs.l2_local`, the rule `arp` is judged by). Accepting creates the subnet's scan target for the agent with the defaults (`icmp`, `arp`, `rdns`; the DHCP pool not scanned; on request only) and asks for one scan of it, so the click is what starts scanning. A subnet with a target, even one assigned to no agent, is not offered. REST only: no MCP tool returns it.
- **Version reporting.** Check-in carries the agent version and a protocol version. The Agents page flags agents older than the server expects and shows the update command. A protocol mismatch gets a clear error on the page; the agent is given no jobs rather than failing silently. Both flags are on every owner answer for an agent, computed on read by `agents.agent_out` (#23) and never stored: `update_available` compares the version the agent last reported with the server's own as PEP 440 versions (`0.2.0.dev0` is older than `0.2.0`; null when either is unknown or not a version; a newer agent is not flagged), and `protocol_mismatch` is whether the `last_error` its last check-in stored is the protocol refusal (`agents.PROTOCOL_MISMATCH_PREFIX`, which `jobs._protocol_error` starts with). A refused check-in stores none of what it reports, so after a mismatch the version shown is the one last accepted.

### 5.7 Endpoints

Agent-facing (agent token only, except `enrol`):

```
POST /api/v1/agent/enrol          (enrolment token as Authorization: Bearer, single use; M2b)
  → { protocol?, hostname?, platform?, version? }
  ← { agent_id, agent_token }

POST /api/v1/agent/checkin
  → { version, protocol, hostname, platform, interfaces: [{name, cidr, mac}], capabilities: [...] }
  ← { checkin_interval_s,
      jobs: [{ job_id, subnet_id, cidr, ranges: [{start, end}], methods,
               dns_servers, timeout_s, fdns: [{host_id, fqdn}] }] }

POST /api/v1/agent/results
  → { protocol, job_id, subnet_id, started_at, finished_at, complete, liveness_complete,
      observations: [{ ip, mac?, rdns_name?, rdns_no_name? }], fdns: [{host_id, addresses}], error? }
  ← { accepted, rejected: [{ip, reason}] }
```

Protocol 2 (#100) added `protocol`, `liveness_complete` and `rdns_no_name` to the results body. The protocol is checked at check-in, which issues the job a result set answers; the results body names its own so that a result set is judged by the rule it was sent under. `protocol` is one of `agent_protocol.RESULTS_PROTOCOLS` (1 and 2) and absent means 1, whose body carried none: an agent of protocol 1 that holds a job leased before the server was upgraded still reports it, and is given no job after (§5.6). From protocol 2, `liveness_complete` is required. The enrol body states its `protocol` since #165, absent meaning 2 (§5.6, "The agent's protocol, before the claim"), so a mismatch is refused there before the token is spent, as it is at every check-in.

- Enrol: each body field is optional and checked as check-in checks it, so the exchange can also be made by hand with `{}`; a report field omitted or sent as null leaves the agent's stored value as it is, and `protocol` is judged and never stored. Refusals, in order: `429 RATE_LIMITED` (the throttle, §5.6), `401` with no bearer, `403` with one message for any bearer that is not an enrolment token exchangeable now (unknown, used, expired, revoked, another kind, or its agent disabled or deleted), `409 AGENT_TOO_OLD` / `AGENT_TOO_NEW` for an integer `protocol` other than the server's (absent meaning 2), judged before the rest of the body, `422` for a body that is not JSON or not that shape, `503` (§4.2). The `409` and the `422` leave the token usable (the body is read only once the token is found usable, and both come before the claim). None writes anything, and each but the `429` counts against the throttle.

- Responses use the REST envelope: the check-in answer is `{"data": {checkin_interval_s, jobs}}`, and refusals are `{"error": {code, message}}`.
- `protocol` is checked before the rest of the body, which another protocol may shape differently. A mismatch is `409 PROTOCOL_MISMATCH` and issues no job; it and a body that fails validation (`422`) are recorded in the agent's `last_error`. The schemas are in one module, `api/app/agent_protocol.py`, which the agent package is built against.
- `jobs` holds at most one job (§5.1). A request no job has been issued for since goes first; other due targets, retries included, go by when a job for them last started, so a target whose jobs keep timing out cannot starve the others.
- An agent may check in once every 10 seconds; a check-in inside that gap is `429 RATE_LIMITED` and changes no row, the token's `last_used_at` included. The slot is a compare-and-set on `last_checkin_at` that also requires the agent `active` and its token unrevoked, so a disable or revoke committed after a check-in authenticated refuses it (`403`, nothing written). The refusals come in a fixed order. A check-in whose agent row, as loaded at authentication, took its slot inside the gap is refused `429` from that row at once, with no statement at all, whatever the owner has committed since: a disable, revoke or delete that lands in that window is met by the agent's next request, which fails authentication with `403`. A check-in the loaded row lets through goes to the claim, which re-checks the agent's state and the token's revocation under SQLite's write lock: `403` if the owner's change has landed (even when another check-in has also taken the slot), otherwise `429` if one has. Nothing is served and nothing is written on any of them. Everything a check-in writes is that one transaction; its audit entry is built from the agent row as committed. An agent's own audit entries (`source="agent"`) are capped at its newest 100, and `list_changes` over MCP withholds the agent-reported values (`version`, `platform`, `hostname`, `interfaces`) in `agent` snapshots (§7.2, invariant 8).
- `cidr` is the subnet's network in its canonical spelling (`ipnet.canonical_cidr`, at most 18 characters for IPv4), whatever the subnet row holds. The owner API stores that spelling (brief §3.2); a subnet stored before it did may hold any spelling `ipaddress` takes, a prefix padded with zeroes to thousands of characters included, which the agent would refuse past its 64-character bound.
- `ranges` is the scan scope from §5.3, as inclusive start–end pairs inside `cidr`.
- `dns_servers` carries at most three servers (`agent_protocol.DNS_SERVERS_MAX`, the most the agent asks per lookup): the first of the subnet's, in the order listed, or none. The owner API takes at most eight for a subnet; a longer list stored before that bound is kept, and its jobs still carry three. So, with `cidr` canonical, the answer is bounded under the 1 MiB the agent reads (§5.6): the largest the server can build, a /20 scope split at every other address with every method and three servers, whatever the subnet stores, and the most forward-DNS names a job carries, each at its longest, is about 427 KB (about 105 KB before #20), and a test builds it from both sides' bounds, from a subnet stored with an over-long list and an over-long spelling of its CIDR. An answer over the limit would be refused by the agent and retried, and its leased job would never run.
- `fdns` (#20) is empty unless the job was issued `fdns`. Otherwise it names hosts of the subnet whose address is in the scope the job's `ranges` are and whose FQDN (the hostname, and the host's domain override, else the subnet's domain) is under the **subnet's own domain**, case-insensitively, with at least one label before it (invariant 5, §7.2): a host whose override is another domain, or a lookalike suffix (`evilhome.arpa` beside `home.arpa`), and every host of a subnet with no domain, are never sent. The FQDN must also be a DNS hostname in `agent_protocol.fdns_name`'s form, lowercase; any other is not sent. At most 1,024 names a job (`fdns.FDNS_JOB_MAX`), those never asked first, then those asked longest ago (`fdns_results.asked_at`, answered or not): the check-in answer must stay inside the agent's 1 MiB and the result set inside the 2 MiB cap beside a full /20 of observations (below), so a /20 of hosts is covered over four jobs. The lease keeps the pairs sent (`job_fdns`). The job's methods keep `fdns` whether or not any name can be sent. **No `PROTOCOL_VERSION` raise:** the job's `fdns` list and the result set's entries were part of protocol 2 from #100, an empty address list already meant a name that did not resolve, and the answer's shape is unchanged; an agent of protocol 2 built before #20 reads the same fields and sends the same empty list, and runs a job issued `fdns` as one with a method it cannot run (incomplete, `not run by this agent release: fdns`, liveness whole), which the server ingests as it would any other.
- `observations` lists **live addresses only**.

**How the agent answers a refused check-in** (the constants are in `agent_protocol.py`). A refused check-in authorises no scan: only a `200` carries jobs, and the agent sends no packet on the strength of any other answer. `429 RATE_LIMITED`, `503 UNAVAILABLE`, any other 5xx, and a request that got no answer at all are retried with a bounded back-off and jitter, since neither refusal carries `Retry-After`: retry *n* (from 0) waits a time drawn uniformly between 10 s, the gap the server enforces, and the smaller of 300 s and 10 × 2<sup>*n*+1</sup> s. An accepted check-in starts the count again. `401`, `403`, `409 PROTOCOL_MISMATCH`, `422` and any other 4xx are not retried in a tight loop: each needs the owner (a new token, re-enabling the agent, the matching release), so the agent waits 13.5–15 minutes before it tries again, and that try is how it sees the owner's fix. A result set that gets no answer, a 5xx, a 429, or a 200 that is not the results shape is retried on the same back-off while the job's lease could still be live (15 minutes from the check-in that issued it), and each attempt is cut off when that time runs out, an unfinished answer included; any other refusal of it is final.

A job the agent will not run is reported, not dropped. The agent refuses a job whose subnet is outside `ALLOWED_CIDRS`, whose ranges are not inside its subnet, whose addresses outnumber `OBSERVATIONS_MAX`, or that is otherwise malformed (§5.6). It sends no packet for it, and answers with a result set that has `complete: false`, no observations, and the reason in `error`, which the server keeps as the target's `last_scan_error` and which clears the lease.

Server-side ingest:

- The credential is checked again first: under SQLite's write lock, before anything is written, the agent must still be `active` and the presenting agent token still unrevoked, as check-in's claim requires. A result set that authenticated before a disable, revoke, delete or re-enrol exchange committed is `403` and stores nothing; the lease stays, and runs out.
- `job_id` must equal both the target's `current_job_id` and the reporting agent's own `current_job_id` (§5.1): the job is still current, and this agent was issued it. The target's current `agent_id` does not decide it, since a target reassigned mid-scan keeps its lease. A superseded job, a deleted target, and a second result set for the same job are refused whole with `409 JOB_NOT_CURRENT` and store nothing; a `subnet_id` that is not the job's is `422`. Lease expiry clears neither copy, so a late result for an expired lease is accepted until another job overwrites one. Every `ip` must fall inside the subnet's scan scope at ingest, so a range excluded mid-scan is refused. Anything else is rejected per record. Accepting a result clears both copies of the lease (the target's `current_job_id`, `job_issued_at`, `job_methods`; the agent's `current_job_id`, `job_issued_at`) in one transaction, each a compare-and-set on this job, and sets `last_scan_at` to the job's `job_issued_at`. `scan_requested_at` is left alone.
- **Per-record rejection.** A record is rejected, and listed in `rejected` with its `ip` when that is a short, ASCII, printable string (else null, since JSON can carry a lone surrogate that UTF-8 cannot encode), as `invalid` (not an object), `invalid_ip`, `invalid_mac`, `out_of_scope` (another address family included), `duplicate`, `mac_not_issued` or `rdns_not_issued`. A record carrying a name and `rdns_no_name: true`, or an `rdns_no_name` that is not a JSON boolean, is `invalid`. A rejected record is not stored, and the rest of the result set is.
- Each accepted address is upserted with `alive=true` and `last_seen_at` set.
- **Only when the liveness sweep completed and the job ran a liveness method** (`icmp` or `arp`, as issued by the server and kept in the target's `job_methods`, not as claimed by the agent), every other in-scope observation for the subnet is set to `alive=false`. From protocol 2 that is `liveness_complete: true`, whatever the PTR lookups did: a host that has left the network is marked dead by a scan in which no DNS server gave a usable answer, or that had none to ask, or whose lookups the deadline cut short. A result set of protocol 1 marks the dead only when `complete` is true. A sweep that was interrupted or timed out therefore never marks an address dead; it only adds what it saw. An address the result set named in a record it rejected is not marked dead either.
- **Names follow each record's own lookup** (#100). From a job issued `rdns`, a record's `rdns_name` (after sanitising) replaces the stored one. From protocol 2, a record without one clears the stored name only when it carries `rdns_no_name: true`: a DNS server answered that the address has no name (§5.2). A record with neither leaves the stored name, whatever the reason (no usable answer, a lookup cut off or not run, a name dropped by sanitising), and `complete` has no part in it. In a result set of protocol 1, which could not tell a lookup that found no name from one that got no answer or never ran, a record with no name clears the stored name only when `complete` is true, and leaves it in an incomplete one.
- Each `fdns` entry is upserted into `fdns_results`, with an empty address list recorded for a name that did not resolve. An entry is accepted only for a `host_id` the server sent in that job: the lease's `job_fdns`, read with the lease, so a host list or a scope changed mid-scan does not change what the job asked; the row's `fqdn` is the name sent. An entry is stored only while its host still exists, is in the job's subnet and is inside its scan scope under the write lock (a host deleted, moved or excluded mid-scan gets none), only when every address is an IPv4 address, and only once per host (a second entry is ignored). Dropped entries are neither counted in `accepted` nor listed in `rejected`. A name without an entry keeps its answer; every name the job sent whose host is still there and in scope has its `asked_at` set, answered or not. Rows whose host no longer exists are deleted. A list or an entry of another shape (over 4,096 entries or 32 addresses, a `host_id` over 36 characters) refuses the result set (`422`).
- `mac` only accepted when the job was issued with `arp` (`job_methods`), which the server does only when the subnet is L2-local to that agent; a later check-in's interfaces do not change it. A record carrying one from any other job is rejected (`mac_not_issued`), and so is a record carrying `rdns_name`, or `rdns_no_name: true`, from a job not issued `rdns`.
- `rdns_name` is **untrusted input**: any device can name itself, and these strings are later read by an LLM over MCP. Restrict to the DNS hostname character set, lowercase, cap at 253 characters, drop anything else. Concretely (`agent_protocol.rdns_name`): ASCII only; one trailing dot removed; dot-separated labels of 1–63 letters, digits and hyphens, neither starting nor ending with a hyphen. A name that fails is dropped whole, never repaired, and its record is still stored without it.
- `error` is stored on the target as `last_scan_error`: non-printable characters become spaces, whitespace runs collapse, and it is cut to 500 characters, so a traceback does not cost the results. It is excluded from audit snapshots (`changes._SNAPSHOT_EXCLUDE`), which MCP can read.
- Body size cap: 2 MiB, the one cap on every request body (`body_limit.BODY_MAX`, #60; brief §4.3), applied before routing, authentication and parsing on every route, check-in and `/mcp` included: a declared or streamed body over it is `413 PAYLOAD_TOO_LARGE`, unparsed, and the agent treats it as final. The same middleware bounds all bodies together and in time (#90; brief §4.3): the body bytes of every request in progress total at most 16 MiB (`body_limit.BODIES_MAX`), counted whether the middleware or the route reads them and until the request ends, since check-in's `Body` is parsed before `require_agent` runs; a chunk past that is `503 UNAVAILABLE`, which the agent retries on its back-off. A body not received whole within 60 s of its headers (`body_limit.BODY_TIMEOUT_S`, twice the agent's 30 s deadline for a whole request, so the agent gives up first) is `408 REQUEST_TIMEOUT`, which the agent would treat as final. Both close the connection, and so does any answer sent before its body was received whole (results' `401` and `403`, which come before the body is read). Below the app, the image's server (`python -m app.serve`, #132; brief §4.3) holds a request's line and headers to 64 KiB as received (`header_limit.HEADER_MAX`), refused with `431 HEADERS_TOO_LARGE` and `Connection: close`; closes without an answer a connection that has not delivered a request's head whole within 10 s (`header_limit.HEADER_TIMEOUT_S`) of opening or of its last response; queues at most one pipelined request; and drops a response, or a closed connection, whose client takes none of what is waiting for 60 s (`header_limit.STALL_TIMEOUT_S`). The agent sends its head whole at once and it is a few hundred bytes, sends one request at a time, and reads each answer at once into its 1 MiB, so none of these applies to it; were one to, the refusal rule below already covers it: a `431` is "any other 4xx", and a closed or dropped connection is a request that got no answer. Left to the reverse proxy or tunnel, which §8 lists with how to check each is in force, for the deployment guidance (#31): per-client connection and rate limits (the budget is shared, so a client that keeps it full holds other bodies off with `503`, and the server does not bound how many connections there are), reading each request's head within limits of its own, closing idle client connections, and passing a body of at least 2 MiB. A full result set for a /20 is about 1.3 MB. With forward-DNS answers (#20) the schema allows 4,096 entries of 32 addresses, which would not fit; the agent sends one entry per name the job sent, and a job sends at most 1,024, so the largest result set, every address of a /20 with a MAC and a 253-character name, the longest error and 1,024 answers of 32 of the widest addresses, is 1,942,467 bytes as the agent encodes it, under the cap (2,048 answers would be 2,598,851; `api/tests/test_fdns.py`). At most 4,096 records, every address of a /20. A refused result set is not recorded on the agent. The 90-day prune runs here, across all subnets.
- The answer is built and UTF-8-encoded before the commit, so neither step can fail after a result set is stored. That covers construction and encoding, not delivery: rendering and sending the response come after the commit, and a lost response leaves a stored result set whose retry is `409`. Should the pre-commit encoding fail, nothing is stored and the answer is `500 INTERNAL_ERROR` in the error shape, logged server-side. A write the database refuses is `503 UNAVAILABLE` (§4.2): both lease copies still name the job and the same result set may be sent again.
- Ingest writes observations and the target's last-scan columns only: nothing to `hosts` (invariant 3) and nothing to the change log.

Owner-facing (owner key):

- CRUD for `/agents` and `/scan-targets`; `POST /agents/{id}/revoke` (revokes every live token of the agent, §4.2, keeps the agent); `POST /agents/{id}/re-enrol` (M2b).
- `PATCH /subnets/{id}/reserved/{range_id}` to set `scan_excluded`, beside the existing `POST /subnets/{id}/reserved` and `DELETE /subnets/{id}/reserved/{range_id}`. `POST` also takes `scan_excluded`, so a range can be excluded from the moment it exists.
- `POST /subnets/{id}/scan` (request scan): `202` with the target; `429 COOLDOWN` inside the cooldown (§5.8); `409` when the subnet has no target, or it is disabled or unassigned.
- `GET /subnets/{id}/findings`, `POST /findings/accept`, `POST /findings/dismiss`; accept and dismiss take a list of finding keys.

### 5.8 UI and MCP

**UI**

- **Agents page:** Add agent, status dot from `last_checkin_at` (a time more than one check-in interval ahead of the browser's clock is shown as "clocks disagree" with the time itself, not as an age), version with an "update available" flag, reported interfaces, subnets covered, enable/disable, revoke, re-enrol. Pending enrolments are listed until used or expired, by the server's clock: the list answer gives each live enrolment token the seconds it has left (`expires_in_s`), and the page never compares an expiry with the browser's clock (#143). A disabled agent's enrolment token is not listed, since the exchange refuses it; its row says it is blocked until the agent is enabled. An agent's offers to scan the subnets on its link (§5.6, "Suggest, don't assume") are listed above the agents, each with Scan and Not now.
- **Subnet settings:** scanning section — agent, methods, interval, "Scan DHCP pool" checkbox (off by default, disabled when no pool is defined), "Scan now", last scan time and duration, and the error the agent reported with that scan (`last_scan_error`, rendered as text). The two messages of §5.2 ("MAC collection unavailable", "cannot be scanned by this agent") come from the scan-target response's `runnable_methods`: what a job would run on the target's agent now, computed on read by the check-in rule (`jobs.job_methods`) from the interfaces the agent last reported, `[]` when no job would be issued, null with no agent or before its first accepted check-in. They show whether or not a job is out; for null, neither shows. Beside either message the section says when the agent reported those interfaces, from the same response: `agent_checkin_at` (the agent's last check-in) and `agent_checkin_refused`. Only an accepted check-in reports interfaces, so after a refused one the section says they are from before it. With neither message it says this only when the report is not recent (refused, older than the Agents page's online window, or dated ahead). A time more than one check-in interval ahead of the browser's clock is freshness not known, by the same rule as the Agents page's status dot: the line stays and gives the time itself, never "0s ago". The fields are not reachable over MCP.
- **Reserved ranges:** a "Scan" checkbox per range (`.tlg-check`), on by default.
- **Subnet view:** findings count badge; a findings panel grouped by type with accept/dismiss per row and bulk accept (an `fdns_mismatch` row has Dismiss alone, #20); last-seen indicator on host rows, reading "not scanned" for hosts outside the scan scope (the scan-target response gives each scope range its bounds as integers, `start_int` and `end_int`, which the UI compares with the host's `ip_int`; no address is parsed in the browser); "show dynamic" filter, shown only when pool scanning is on.

**MCP** (keep the tool count small; update `EXPECTED_TOOLS` and the brief's tool table)

| Tool | Class | Purpose |
|------|-------|---------|
| `list_scan_findings(subnet_id?, type?, cursor?)` | read | Read findings, denormalised with host and subnet names, a page at a time |
| `request_scan(subnet_id)` | write | Mark a configured target due |

- `request_scan` has a **per-subnet cooldown** (default 15 minutes, applied to every caller including the UI button). Repeated scans are how someone with read access would turn "latest state" into a presence timeline.
- `request_scan` is classed as a write tool, so read-only remote grants (§6.5) cannot call it. The scope check arrives with remote grants, on every write tool at once (#28). Until then the only bearer `/mcp` accepts is the owner key, which carries `ipam:write`.
- `request_scan` returns the request (`subnet_id`, `scan_requested_at`, `next_request_after`), not the scan target, whose configuration stays off MCP. Inside the cooldown its tool error gives the time after which the subnet can be asked again.
- `list_scan_findings` returns each finding as `GET /subnets/{id}/findings` does, `proposed` and `fingerprint` included, plus `subnet_name`, `subnet_cidr`, and the recorded `host_name` and `host_fqdn` of the host at the address. Without `subnet_id` it covers every subnet. It leaves out `dynamic` findings: a scanned DHCP pool is where personal devices answer (§7.1).
- `list_scan_findings` returns a bounded page and does bounded work, never the whole network in one result (§7.2, invariant 9). A page is at most `findings.PAGE_SIZE` (25) findings, each at most `findings.FINDING_MAX` (5,000) bytes as compact UTF-8 JSON, in a `findings` array of at most `findings.PAGE_BUDGET` (45,000) bytes, brackets and commas included, with `next_cursor` and the `note` on every page. Every value a finding carries has a length bound (subnet name 120, hostname 253, PTR name 253, domain suffix 253, `ipnet.DOMAIN_MAX`, since #86); the largest finding they allow is 4,880 bytes. A host whose effective domain was stored longer before the domain limit is listed with `host_fqdn` null, never with a cut value. One call runs at most `findings.CALL_STATEMENTS` (100) SQL statements, each reading at most `findings.SCAN_CHUNK` (250) hosts and as many observations along an index on `(subnet_id, ip_int)`, passing over no row it does not return (inside a scanned DHCP pool, observations are read only at its hosts' addresses); a visited subnet's scope reads only its excluded reserved ranges, along their own index, and a subnet holds at most `schemas.SUBNET_RESERVED_RANGES_MAX` (100) reserved ranges on every write path, MCP's `add_reserved_range` included (one stored with more before that limit is read whole, the one read besides the subnet list whose cost follows stored data), but the one that lists the subnets that can hold a finding (with an observation, or with a scan target and a host). The work counted is SQLite's, the rows a statement reads or passes over, not the bytes it returns or Python's processing of them, so every read returns only the columns a finding uses, never a whole row: with `subnet_id`, the check that the subnet exists reads its id alone, because a subnet's notes have no length bound (#133). `next_cursor` is null once the listing has reached its end; otherwise it is a position in the listing's order (subnet name, CIDR and id, then address, then type): the page's last finding when the page is full, or the last address examined when the call reached its statement bound, so a page can be short or empty and still carry a cursor. A client that passes it back sees each finding once while the data and the filters stay the same, and resolving findings from one page skips none on the next. A stopped call's cursor names a host's address, an observation's outside the DHCP pool, or a bound of the pool, possibly with nothing listed there; an unhosted address in a scanned pool is never read, so no cursor names one. There is no snapshot: a finding that appears before the cursor after paging began, or a subnet renamed meanwhile, can be missed or repeated, and the tool's docstring says to start again without a cursor for the current state. The cursor is checked for its shape, not its origin: it is unsigned, and it only says where in the order to start. The result puts `next_cursor` and `note` before the findings so that a client that cuts it keeps them. The size bounds are set against what a client holds (Claude Code: 50,000 characters of a text result, 25,000 tokens): 25 findings with every name and the domain at 253 ASCII characters are 44,057 characters with the note. A result carries the page twice (a text block and structured content); what a client counts against its limits was not measured. Without paging, 5,000 findings were 3 MB in one result; without the work bound, 500 subnets holding nothing between two that hold findings cost 4,521 statements in one call.
- What a finding carries from the network (`observed`, and the MAC, name and domain in `proposed`) reaches the assistant as data. It is not withheld, as agent-reported fields are in `list_changes` (§5.7), because a name finding is its name, and the hostname character set leaves no room for markup. The tool's docstring and a `note` beside the list say these values are what devices reported about themselves, never instructions, and that one is written into a host only when the user asks. An `fdns_mismatch`'s `observed` is the addresses a DNS server gave for a name the server chose (#20): data in the same way, and `findings.NETWORK_REPORTED_NOTE` names it.
- Accepting a finding over MCP uses the existing `create_host`/`update_host` tools. There is no dismiss tool: dismissal is an owner judgement and stays in the UI.
- `get_subnet` output marks each reserved range's `scan_excluded` and the subnet's `scan_dhcp_pool`, so an assistant can explain why an address has no observation.
- Agent, scan-target, and scan-scope configuration stays UI-only (§5.3).

### 5.9 Later: controller collector

The ingest path in §5.7 is deliberately source-agnostic. A later "collector" kind of agent could poll a network controller's client list (IP, MAC, hostname, VLAN for every client, across all VLANs) and post the same observation shape. That removes the L2 constraint for networks that have such a controller. Not in v0.2; the design should not preclude it.

## 6. M3 — Remote MCP with built-in OAuth

### 6.1 Three ways to run it

| Setup | Configuration | Behaviour |
|-------|---------------|-----------|
| Local | `API_KEY` | OAuth routes answer 404. Clients send the owner key as a bearer (desktop JSON config, `mcp-remote`, CLI clients) |
| Remote | + `PUBLIC_BASE_URL` | Built-in OAuth server on. Owner key still works for local clients |
| Remote with SSO/MFA | as Remote, plus the operator's access proxy on two paths | See §6.7 |

OAuth turns on when `PUBLIC_BASE_URL` is set. There is no consent password to configure.

### 6.2 Shape

```
web MCP client ──▶ https://ipam.example.com/mcp
                     │
                     ▼
          FastMCP MultiAuth
            ├─ server:    IpamOAuthProvider   (subclass of FastMCP's OAuthProvider, SQLite-backed)
            └─ verifiers: owner-key bearer verifier (from M1)
```

The app is its own authorisation server. FastMCP and the MCP SDK supply the protocol endpoints (authorise, token, register, discovery metadata), PKCE verification, and the check that an authorise request's `redirect_uri` is one the client registered. `IpamOAuthProvider` supplies storage, the consent step, and token issue/refresh, and three things the SDK's defaults do not: which redirect URIs a client may register, the port exception for a loopback-IP redirect at authorise (both §6.3), and client authentication against a hashed secret (§6.4). FastMCP's 369-line `InMemoryOAuthProvider` is the reference for the method set; expect roughly 400 lines plus tests.

### 6.3 Linking flow

Linking a client needs a **link window**, opened by the owner from the private UI. Outside a window the server registers no clients and authorises nothing.

1. In the UI the owner chooses **Link a client**. If `MCP_REMOTE_WRITES` is on, the dialog has an "Allow this client to make changes" checkbox, off by default. The UI then shows a one-time **link code** and a 10-minute countdown. The window is open from here, before the URL is given to any client: step 2 says why.
2. The owner adds the server URL in the web client. The client discovers the server from `/.well-known/…` and registers itself (dynamic registration). Registration is a request of its own, and the client chooses when to send it: ChatGPT and Gemini register as soon as the URL is entered, 25 to 34 seconds before they authorise, and Claude.ai and Mistral only at **Connect** (§6.8). The window therefore has to be open for the registration and for the authorise request that follows it. A URL entered with no window open fails at registration, before the owner has seen a consent page.
3. The client sends the owner's browser to the authorise endpoint. The provider stores the pending request server-side and redirects to the **consent page** with an opaque transaction ID.
4. The consent page shows the client's self-declared name (marked as unverified), **the redirect host in prominent text**, and the access being granted (read-only or read-write, as chosen in step 1). The redirect host is the host of the `redirect_uri` in this authorise request, where the code will be sent, and not a property of the client: one client can register redirect URIs on several hosts (Gemini registers six, on three). It is derived from the validated URI and shown as escaped text, in its ASCII form (an internationalised name as `xn--…`): see **Redirect URIs** below. The owner types the link code.
5. On success the provider records the grant, with the `redirect_uri` it was approved for (§6.4), issues a single-use authorisation code, closes the window, and redirects to the client, which exchanges the code for tokens.

Link window rules:

- One window at a time. It closes on the first successful link, after 10 minutes, or when the owner cancels it.
- **A registration is not a link.** A link is the grant of step 5. Any number of registrations can arrive in a window, and none closes it or uses it up: Claude.ai registers twice for one link, 11 seconds apart, and never uses the first (§6.8). A client registered in one window can authorise in a later one, for as long as its registration is kept (§6.6).
- The code is 10 characters from an unambiguous alphabet, generated server-side, held hashed in memory, compared in constant time.
- **Five wrong codes burn the window.** The owner opens a new one. This bounds guessing to five attempts per window the owner chose to open, and there is no lockout an outsider can hold shut.
- Register and authorise requests outside a window are refused with a plain error page saying to start from the IPAM's own UI. Discovery metadata and the token endpoint always answer, so existing links keep refreshing.
- Window state and pending transactions are in memory. A restart cancels a link in progress and nothing else.
- Opening a window is audit-logged (`source="ui"`); a burned window and an issued grant are audit-logged (`source="oauth"`, `entity_type="link_window"` and `"grant"`).

Consent page requirements: served with `frame-ancestors 'none'`; no external assets; CSRF token bound to the transaction; the transaction expires with the window.

**Redirect URIs.** The SDK checks only that an authorise request's `redirect_uri` equals one the client registered. It registers any scheme: `http://client.example.com/cb` and `javascript:alert(1)` are both accepted by its registration route and then by its authorise route. The first would send the code over plain HTTP behind a consent page that shows the same host as HTTPS would, and the second has no host to show. So the policy is the provider's:

- Registration accepts only absolute `https` redirect URIs with a host, and `http` redirect URIs whose host is `localhost` or a loopback address, for local clients. A registration holding any other URI (another scheme, no host, plain HTTP to another host) is refused whole with the registration error `invalid_redirect_uri`.
- The authorise request must match a registered URI. For an HTTP loopback-IP URI (`127.0.0.1`, `[::1]`), any valid request port is allowed while every other URI component must match; the provider supplies this exception because the SDK's default client validation compares the complete URI. A local client listens on a port it is given when it starts, so it cannot register that port beforehand, and OAuth 2.1 requires the exception for IP literals. The full URI chosen at authorisation, including its port, is retained for consent, the code, the grant and the code exchange. Other URIs use the SDK's registered-URI check. That includes `http` to `localhost` by name: it keeps exact-port matching, as a stated policy, since the exception is required only for IP literals and a name is resolved by the client's host.
- The consent page and **Linked clients** derive the ASCII hostname from that validated URI, as parsed, and render it as escaped text. It is never taken from the client's name or from splitting the URI as a string.

**Resource indicator.** All four clients send an RFC 8707 `resource` on the authorise request, on the code exchange and on every refresh, and each sent exactly `PUBLIC_BASE_URL/mcp` (§6.8). The MCP authorisation specification requires that of a client, and requires a server to accept only tokens issued for it. Here that second rule holds without anything stored: the server is one resource, and its tokens are opaque values it looks up in its own database, so every token it accepts is one it issued, for `/mcp` (§6.5). The provider checks the value where it is handed it:

- An authorise request whose `resource` is present and is not `PUBLIC_BASE_URL/mcp` is answered with the OAuth error `invalid_target`, and no consent page is shown. The two are compared as URLs: scheme and host without regard to case, one trailing slash ignored. This turns a client that reached the server under another name, or a wrong `PUBLIC_BASE_URL`, into an error at linking.
- An authorise request without `resource` is accepted as naming this server.
- On the code exchange and on refresh, `resource` is not checked. The MCP SDK does not hand the token request's value to the provider, and no value there could change where the token works.

Cost of this design: the owner must be able to reach the private UI at the moment of linking. That is accepted; linking is rare, and it is what removes the standing secret.

### 6.4 Storage and lifetimes (additive tables)

| Table | Holds |
|-------|-------|
| `oauth_clients` | `client_id`, declared name (sanitised, §4.3), redirect URIs, `token_endpoint_auth_method`, SHA-256 hash of the client secret (null for a public client), `created_at`, `linked_at` |
| `oauth_grants` | one per approved link: `client_id`, `redirect_uri` (the one the link was approved through, §6.3 step 4), `can_write`, `created_at`, `last_used_at`, `revoked_at` |
| `oauth_tokens` | SHA-256 hash, `grant_id`, kind (`code`/`access`/`refresh`), `expires_at`, `rotated_at`, PKCE challenge for codes |

None of the three exists before M3, so these are the tables as first created.

- Authorisation code: 5 minutes, single use.
- Access token: 1 hour.
- Refresh token: 30 days, rotated on every use.
- **Retry window.** A refresh token presented again within 60 seconds of its rotation is treated as a retry (a lost response or two concurrent requests) and is answered with a new pair. Presented later than that, it is treated as theft and revokes the whole grant.
- These lifetimes stand after the spike (§6.8). All four refreshed successfully. Claude.ai and Mistral each refreshed twice, consistent with the in-memory provider's rotation on every use. Neither the 30-day lifetime nor the retry window was exercised.
- **Client authentication.** A client registers as confidential or public, and the server stores which (`token_endpoint_auth_method`). Of the four, Claude.ai, ChatGPT and Gemini register as confidential (`client_secret_post`) and Mistral as public (`none`). The token endpoint accepts both. A client that registered a secret gets no token without it: a code exchange or a refresh that omits the secret, or sends a wrong one, is refused and issues nothing. A public client has no secret; its code exchange is bound by PKCE, and its refresh token is protected by rotation and the retry window alone. A client secret does not expire, since a link is meant to outlive any expiry; the registration it belongs to ends by §6.6's rules.
- Tokens and client secrets are stored hashed only, and a secret appears in plain only in the registration response that issues it. All of this lives in the one SQLite file, so the existing backup covers it and links survive a restore.
- **The authenticator is the provider's own.** The SDK's client authenticator compares the presented secret with the plain one the provider returns for the client, and the provider's storage and exchange hooks are never handed the presented secret, so a hash cannot be checked through either. The provider overrides route construction to give the token handler a request-aware client authenticator. For a registered confidential client, it requires the registered authentication method and a secret, hashes the presented secret and compares it in constant time with the stored hash; failure returns `invalid_client` before any code or refresh token is consumed. A public client remains `none`. Returning a stored hash to the stock plaintext authenticator, or changing a confidential client to `none`, is not authentication. The same verifier applies to any other enabled endpoint that authenticates clients.
- **`last_used_at` is the client's last contact, not the owner's last use.** It is the last time one of the grant's tokens was accepted, on a request to `/mcp` or on a refresh. A client can do both with nobody using it: Mistral sends `server/discover` every 20 to 55 minutes and refreshes about hourly (§6.8). The **Linked clients** list labels it accordingly (§6.6).

### 6.5 Limits on what a remote grant can do

- **Scopes.** Two scopes exist: `ipam:read` and `ipam:write`. Write tools require `ipam:write` through FastMCP's scope checks (`require_scopes`, present in FastMCP 4.1.8) rather than hand-written tagging. The owner-key verifier returns both scopes.
- **Read-only by default.** `MCP_REMOTE_WRITES=false` is the default. A grant's `can_write` is fixed when the link window is opened.
- **The setting is honoured in both directions.** A token carries `ipam:write` only when the grant has `can_write` **and** `MCP_REMOTE_WRITES` is currently on; the provider applies this each time it loads a token. Turning the setting on later does not upgrade existing read-only links. Turning it off takes write access away from every grant at once.
- **A tool the caller lacks the scope for is hidden.** FastMCP 4.1.8's `require_scopes` leaves it out of `tools/list`, and a direct call answers `Unknown tool: '<name>'`: FastMCP's `NotFoundError`, an MCP tool error over HTTP 200, not a 401 or 403 (§6.8). To an assistant on a read-only grant a write tool therefore looks missing, not refused. This is FastMCP's behaviour and not this project's code, so a test holds it (§6.10) and an upgrade that changes it is seen.
- Because a hidden tool looks missing, no tool docstring and no server instruction tells an assistant to retry a tool that is not found. A read tool's docstring that names a write tool (`list_scan_findings` names `create_host` and `update_host`) says that the tool is absent on a read-only connection, and that the assistant then reports what it would have changed to the owner.
- A grant reaches `/mcp` only — never `/api/*`, the backup endpoint, or the SPA.

### 6.6 Abuse controls

| Control | Detail |
|---------|--------|
| Link window | Registration and authorisation only while the owner has a window open; five wrong codes burn it (§6.3) |
| Registration bounds | At most 50 registered clients, counting every registration, linked or not. A client may register more than once for one link (Claude.ai registers twice and uses the second, §6.8); each is a registration of its own, and the spare is never linked. At the cap, a new registration evicts the oldest reclaimable one rather than being refused. A registration with no unrevoked grant is reclaimable, including one whose last grant was revoked: its grant and audit records remain, and reclaiming it never makes a revoked token valid. Only when all 50 hold an unrevoked grant is there none to evict, and the registration is refused until the owner revokes a link. A registration not linked within 24 hours is deleted, which is what removes a spare |
| Visibility | A **Linked clients** list in the UI (name, redirect host, read/write, created, last contact) with revoke. The redirect host is the host of the grant's `redirect_uri`, the one the link was made through, not every host the client registered. **Last contact** is the grant's `last_used_at`, which a client can move with nobody using it (§6.4), so the list does not call it use. Every grant issue, refresh-reuse revocation, and manual revoke is audit-logged (`entity_type="grant"`) |
| Audit attribution | MCP writes from a grant record the client in `changes.actor` (§4.3) |
| Request body | Every request to the app, the `/mcp` mount and any OAuth route added under it included, is held to the one request-body cap (§5.7) before authentication or parsing, and to the budget on all bodies in progress and the 60 s deadline for receiving one |

### 6.7 Exposure and SSO

- Publicly routable: the `/mcp` mount (transport and OAuth routes) and `/.well-known/*` only. The SPA and `/api/*` stay private.
- An access proxy in front of the MCP transport, token, or register endpoints must pass traffic through without an interactive login; web MCP clients cannot complete one.
- **SSO or MFA without native OIDC:** only the owner's browser ever visits the authorise and consent pages. An operator can put their access proxy's login in front of just those two paths, in addition to the link code. This is a documentation page, not a feature.
- Well-known routes must be installed on the parent FastAPI app, before the SPA catch-all, which would otherwise answer them with `index.html`.
- Clients also ask for paths this server does not serve: `/.well-known/openid-configuration` (ChatGPT) and `/.well-known/mcp/server-card/mcp` (Mistral) in the spike (§6.8). Every path under `/.well-known/` that is not an installed route answers `404`, with OAuth on as with it off, and never the SPA's `index.html`: a `200` holding HTML is no answer to a client that asked for metadata. `HEAD /mcp` without a credential (Gemini sends it before discovery) is answered as `GET /mcp` is, with the `401` whose `WWW-Authenticate` names the protected-resource metadata.
- `PUBLIC_BASE_URL` is installation identity: issuer and callback URLs come from it, never from `Host` or `X-Forwarded-*`. Changing it invalidates every link.
- The existing `MCPPathRewriteMiddleware` must keep rewriting only the exact path `/mcp`; OAuth paths must 404 rather than redirect on a trailing slash.
- `/api/v1/agent/*` needs to be reachable by agents only. If agent and server share a LAN it is not public.

### 6.8 Client compatibility spike (done, #25)

This section is the record of the spike that was M3's first task. The rest of §6 carries what it found.

**What was asked.** FastMCP's support for metadata-document clients (CIMD) appeared to live in its `OAuthProxy` class, not in the `OAuthProvider` base class used here, so the built-in server would offer dynamic registration only. Earlier testing had seen Claude.ai and ChatGPT link by CIMD where a server offered it. Three questions followed:

- whether each of the four web clients links against a server that offers dynamic registration alone, and if Claude.ai or ChatGPT will not, FastMCP's `CIMDClientManager` is wired in before the rest is built;
- whether each client registers when the URL is added or only when it first authorises, which decides whether the link window must be open before the URL is entered;
- how FastMCP presents a tool the caller lacks the scope for.

**What was found.** Run on 2026-11-25 with FastMCP 4.1.8's `InMemoryOAuthProvider` behind a public HTTPS name, every token granted `ipam:read` alone.

- **CIMD is only in `OAuthProxy`.** `OAuthProvider` and `InMemoryOAuthProvider` have none, so the server offered dynamic registration alone. All four clients linked by it and none tried CIMD. `CIMDClientManager` is not wired in.

| Client | Links | Registers | Client authentication | Redirect URIs |
|--------|-------|-----------|-----------------------|---------------|
| Claude.ai | yes | at **Connect**, twice, 11 s apart; the first is never used | `client_secret_post` | 1 |
| ChatGPT | yes | when the URL is added, 34 s before it authorises | `client_secret_post` | 1 |
| Mistral | yes | at **Connect** | `none` (public client) | 1 |
| Gemini | yes | when the URL is added, 25 s before it authorises | `client_secret_post` | 6, on 3 hosts |

- **All four** use PKCE with `S256`, send `resource` (`PUBLIC_BASE_URL/mcp`, §6.3) on the authorise request, the code exchange and every refresh, ask for `ipam:read ipam:write` at authorise, and take a token granted `ipam:read` alone without complaint.
- **A tool the caller lacks the scope for is hidden** from `tools/list`, and no client showed it. Called directly, it answers `Unknown tool` (§6.5).
- **Refresh.** Used again about 3.5 hours after linking, all four refreshed with no reconnect prompt, each before sending a request with an expired token. Mistral and Claude.ai refreshed twice, consistent with the in-memory provider's rotation on every use (§6.4); ChatGPT and Gemini refreshed once. The log holds no token value, so it does not show which token a refresh presented.
- **Mistral contacts the server with nobody using it:** `server/discover` every 20 to 55 minutes, and a refresh about every hour (§6.4, `last_used_at`).
- **Gemini opens a new MCP session for every action.** After its access token expired it sent `DELETE /mcp` six times with that token, was refused `401` each time, and did not refresh for it.
- **Other requests:** `/.well-known/openid-configuration` (ChatGPT), `/.well-known/mcp/server-card/mcp` (Mistral) and `HEAD /mcp` before discovery (Gemini), answered `404`, `404` and `401` (§6.7). Within an hour of the name going public two crawlers asked for `/`, the first after 8 minutes, which is the case §6.7's public surface is drawn for.

The provider was the in-memory one: the link window, the consent page and the SQLite store are M3's own work and were not part of it. Neither the refresh token's 30-day lifetime nor the 60-second retry window was reached. The log shows requests and their answers; when a URL was added or **Connect** pressed, that no client asked to reconnect, and that nobody was using Mistral are the owner's report of the run.

The evidence is the findings comment on issue #25 and `.agents/spikes/25/`: the harness, its README and the raw log, in which the hostname and the per-connector IDs in redirect URIs are replaced by placeholders.

### 6.10 Acceptance

- Each of Claude.ai, ChatGPT, Gemini, Mistral links and completes `list_subnets`, and is still linked, with no reconnect prompt, after its first access token has expired.
- With no link window open, registration and authorisation are refused, and existing links keep working.
- A client that registers when its URL is added and authorises half a minute later links in the one window. A client that registers twice links with its second registration; the first neither closes the window nor outlasts 24 hours.
- A client registered in a window that ran out links in a later window with that registration; outside a window its authorise request is refused.
- A registration holding a redirect URI that is plain HTTP to a host other than loopback, has no host, or has a scheme other than `https` or `http` (`javascript:`, a custom scheme) is refused; `https` with a host and `http` to `localhost` or a loopback address register.
- An HTTP redirect registered on `127.0.0.1` or `[::1]` authorises with another valid port; changing its host, path or query is refused. One registered on `localhost` authorises only with the port it registered. The grant records the URI as authorised, port included.
- With 50 registrations, a new one evicts the oldest that holds no unrevoked grant, never linked or revoked alike; when all 50 hold an unrevoked grant it is refused. After a revoked client's registration is reclaimed, its grant and audit entries remain and its tokens are still refused.
- A wrong code issues nothing; the fifth wrong code burns the window; the burn appears in the audit log.
- A second client cannot link on a window that has already been used.
- For a client that registered redirect URIs on several hosts, the consent page shows the host of the authorise request's `redirect_uri`; the grant records that URI, and **Linked clients** shows its host. A host with an internationalised name is shown in its `xn--…` form, on both.
- An authorise request whose `resource` is present and differs from `PUBLIC_BASE_URL/mcp` is answered `invalid_target` and shows no consent page. One that differs only in the case of its scheme or host, or by one trailing slash, is accepted, and one without `resource` goes on to the consent page.
- A confidential client's code exchange and refresh succeed with its secret. Without it, or with a wrong one, each is answered `invalid_client`, issues nothing, and leaves the code or refresh token usable by the right secret. A public client links and refreshes with none. The database holds no client secret in plain, and a registration answer gives `client_secret_expires_at` as 0.
- A refresh moves the grant's `last_used_at`, as a request to `/mcp` does, and **Linked clients** shows it as **Last contact**.
- With `MCP_REMOTE_WRITES=false`, a grant's `tools/list` holds no write tool, and a direct call of `create_host` or `request_scan` answers `Unknown tool` and changes nothing; `list_hosts` works.
- A read-write grant loses write access when `MCP_REMOTE_WRITES` is turned off, without relinking.
- A refresh token reused within 60 seconds gets a new pair; reused after that, it revokes the grant.
- Revoking a client in the UI stops its next request.
- Links survive a container restart and a restore from backup.
- `mcp-remote` with the owner key as bearer still works with OAuth enabled.
- With OAuth unconfigured, `/.well-known/*` and the OAuth routes return 404.
- With OAuth on, `/.well-known/openid-configuration` and any other path under `/.well-known/` that the server does not serve return 404 and not the SPA; `HEAD /mcp` without a credential returns the `401` with `WWW-Authenticate`.
- A change made through a grant shows the client in `actor`, and a client name containing markup or instructions arrives sanitised.

## 7. Security model

### 7.1 Worst case: an attacker holds a grant

There is no standing consent secret to guess. A grant reaches an attacker by phishing the owner during an open link window, by theft of a client's stored tokens, or through a compromised client.

| The attacker gets | Limited by |
|-------------------|------------|
| A full, current map of the network: subnets, VLANs, gateways, hostnames, MACs, notes, live addresses | Nothing — this is the residual exposure of running remote MCP at all |
| Presence tracking by polling live state | The DHCP pool, where personal devices live, is not scanned by default; `request_scan` is a write tool and has a cooldown; no history is stored |
| Vandalism of host records | Read-only grants by default; audit log with the client in `actor`; backups |
| Stored prompt injection — text planted in notes or hostnames that the owner's own assistant later reads alongside more powerful tools | Read-only grants by default; `rdns_name` and client-name sanitisation |

| The attacker does not get | Because |
|---------------------------|---------|
| Any reach into the network | The agent is pull-only with a fixed method vocabulary; it does not proxy, tunnel, or execute |
| New scan targets, agents, or a wider scan scope | Configuration is UI/REST-only, and the grant cannot reach REST |
| The owner key, backup, or UI | Separate credential; `/api/*` and the SPA are not public |
| A second link | Linking needs a code from the private UI |

### 7.2 Invariants

Add these to `AGENTS.md` alongside the existing architecture invariants.

1. The agent never executes, downloads, or updates from anything the server sends. Agent code comes from the published release, never from the server.
2. MCP never gains agent, scan-target, or scan-scope configuration, and no MCP call can widen what is scanned.
3. Scan ingest never writes to `hosts`.
4. No packet is sent to an address outside the scan scope, and scan scope is computed in one place (`services/scans.scan_scope`).
5. `fdns` only resolves names under the subnet's effective domain: a job names a host only when its FQDN is under the subnet's own domain and its address is in scope (`services/fdns.names_for_job`, #20), and the agent asks only DNS hostnames.
6. Linking a client requires a one-time code minted from the private UI. There is no static consent secret.
7. Remote grants are read-only unless the operator opts in, and never reach `/api/*`.
8. Strings that originate from the network or from a client (`rdns_name`, agent-reported fields, OAuth client names) are sanitised at ingest and never interpolated into change summaries by the paths that carry them in: scan ingest writes no change entry, a check-in's summary names the fields that changed and not their values, and accepting a finding names the address and the finding type. A value the owner writes into a host is owner data from then on, whatever it was copied from: an MCP host write (`create_host`, `update_host`) whose hostname an assistant took from a finding's `proposed` is an ordinary write, and its summary names the host by that hostname, as every host summary does. The owner decided this (#79); the two tools' docstrings tell the assistant.
9. One MCP call does bounded work and returns a bounded result, whatever the stored data: `list_scan_findings` runs a fixed number of SQL statements, each reading a fixed number of rows (the subnet list and a scope's excluded ranges stored before their limit excepted, as §5.8 says), and returns a page of bounded size made of findings of bounded size, rows stored before a field's limit included (§5.8). It is held before `/mcp` is exposed (#86, before #26).

### 7.3 Likelier attacks than guessing

- **Consent phishing.** The link window narrows this to the minutes the owner has one open, but inside a window anyone can register a client named after a well-known assistant. The consent page's redirect-host display is the remaining defence; test it with a lookalike.
- **A vulnerability in the app.** The server sits on the operator's network behind a tunnel, so code execution there is a foothold on the LAN — worse than anything in §7.1. Deployment guidance: unprivileged container, its own VLAN or firewall rules allowing only what it needs, non-root process.

## 8. Deployment guidance to document

- Unprivileged container or LXC, isolated as in §7.3, included in the backup schedule.
- Tunnel or reverse proxy publishes only the paths in §6.7.
- One uvicorn worker.
- A reverse proxy or tunnel in front of the server holds what the server cannot (brief §4.3, #132). Each line says what to set and how an owner checks it from outside, against the public name, and what the server answers when the proxy does not: the proxy's own refusal page or status is the sign it is in force, and the app's JSON error body (`{"error": {"code": …}}`) is the sign the request reached the server. Every directive, default and quotation below is from each proxy's own documentation ([nginx](https://nginx.org/en/docs/), [Caddy](https://caddyserver.com/docs/caddyfile/options), [cloudflared](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/origin-parameters/)), read for #132; no check here has been run against a proxy. What the server itself sends (the `X-Accel-Buffering` header and the 15 s comment lines of an event stream, the `401`, `431` and timings) was measured against the image's server.
  - **Per-client limits: requests.** nginx: `limit_req` on `$binary_remote_addr` bounds a client's request rate (set `limit_req_status 429`; the default is `503`), and `limit_conn` bounds how many of its requests are in progress at once, a body still being uploaded included. nginx counts a connection for `limit_conn` "only if it has a request being processed by the server and the whole request header has already been read", so it counts requests, not sockets (next line). Caddy has neither built in (a rate-limit module adds one). Cloudflare: a rate-limiting rule. Check `limit_req`: send requests faster than the rate and get the proxy's `429`. Check `limit_conn`: open one more connection than the limit, each sending a complete `POST /mcp` head with `Content-Length: 1000000` and then a byte of body a second, and see the last refused by the proxy (`503` by default); without the setting nginx accepts it too, and holds its body while it trickles.
  - **Per-client limits: sockets without a complete head** (silent, or trickling one). nginx's `http` module has no per-client limit on these: `limit_conn` does not count them. nginx sends a request on to the server only once its head is complete, so they never reach the server, and what bounds them at nginx is `client_header_timeout` ("If a client does not transmit the entire header within this time, the request is terminated with the 408 (Request Time-out) error"; default 60 s; set it to the server's 10 s or less), `large_client_header_buffers` (their size) and `worker_connections` (default 512 per worker, every connection of every client together, so one client can take them all). Caddy: the server's `read_header` timeout (default 1 min) and no per-client count either. Client sockets to Cloudflare end at its edge and never reach the tunnel. A per-client cap on sockets, where one is wanted in front of nginx or Caddy, is a per-source connection limit in the firewall (nftables `ct count` keyed on `ip saddr`, iptables `connlimit`, whose default group is the source address). It counts by the packet's source address, so it is per client only on the host the clients connect to directly with their own addresses: put it on the proxy's host. Behind a tunnel or another proxy the source is that hop's address, every client shares one count, and a cap there limits them all together. Check `client_header_timeout` (or Caddy's `read_header`): open a connection, send half a head (`time openssl s_client -quiet -connect <name>:443`, then type `GET /mcp HTTP/1.1` and no blank line) and see the proxy end it at the configured time (nginx with `408`), not at its default. Check a firewall cap: from one address, open more connections than it allows and send nothing; the excess never complete the handshake or are refused, while another address still connects.
  - **Request heads read within a size limit of the proxy's own.** nginx: `large_client_header_buffers` (default `4 8k`: a header line over 8 KiB is `400`, a request line over it `414`). Caddy: `max_header_size` (default 16 KiB, `431` past it). Cloudflare reads heads at its edge, up to 128 KB. Check, against `/mcp` (the published path, §6.7): send a header larger than the proxy's limit, from a file because a command-line argument that long is refused by the shell (`{ printf 'X-Pad: '; head -c 200000 /dev/zero | tr '\0' a; } > pad.txt`, then `curl -H @pad.txt https://<name>/mcp`), and get the proxy's refusal, not the server's `431` with `HEADERS_TOO_LARGE`. Through Cloudflare, a header under 128 KB and over 64 KiB reaches the server and gets that `431`, which shows the server's own limit in force.
  - **Clients that read slowly.** Two kinds of response, and a limit meant for one must not end the other.
    - *Finite responses* (a static file, a backup, a large answer). The server drops one whose client takes nothing of it for 60 s; a client that keeps taking a little holds it as long as it does. nginx: `proxy_buffering on` (the default) so nginx takes the response from the server at its own speed, and `send_timeout` (default 60 s; "set only between two successive write operations, not for the transmission of the whole response"). Caddy: the server's `write_idle` (default 1 min: how long one write to a client may stall). Neither bounds a client that keeps reading slowly; nginx has no minimum rate, and Caddy's `write_idle <min_rate>` must not be used where `/mcp` is served (below).
    - *Event streams* (`/mcp`'s `GET` and its streamed answers, held open as long as an assistant's session lasts). The server sends `X-Accel-Buffering: no` with each, which turns nginx's response buffering off for it, and a comment line (`: ping`) every 15 s. nginx's `send_timeout` and `proxy_read_timeout` (default 60 s, "between two successive read operations") are measured between writes and reads, so a stream is unaffected while they stay above 15 s. Caddy flushes `text/event-stream` at once and `write_idle` is per write, so a stream whose writes progress is unaffected. Do not set Caddy's `write` ("a hard limit on the whole response": any finite value ends every MCP stream at that age) or a `write_idle` minimum rate (Caddy's documentation advises against it for long-lived streaming responses) on the server that serves `/mcp`. Both are server-wide `timeouts` options, applied to every request the server takes. Caddy's experimental `timeouts` directive sets idle `read_timeout` and `write_timeout` for matched requests only, ahead of the server-wide `read_body_idle` and `write_idle`, but its own documentation says the server-wide `write` "still caps" the whole response, so a server-wide `write` ends a stream whatever a route sets. No nginx timeout on the whole response belongs on `/mcp` either.
    - Check, both at once: open an MCP event stream through the proxy (`curl -N` with the bearer, the session's `Mcp-Session-Id` and `Accept: text/event-stream`) and hold it for twice the longest timeout configured; it stays open and shows a `: ping` line every 15 s. Beside it, through the same proxy, ask for a response larger than the proxy's and the kernel's buffers can hold (several MiB: on a proxy that serves the UI, a backup with the owner key once the database holds data, or a large static file) and stop reading it entirely, which piping `curl` into a process that never reads does (`curl -s … | sleep 600`); the proxy closes it at its stall limit (nginx's `send_timeout`, Caddy's `write_idle`) while the stream stays open. A small response may fit the buffers and never stall, and a client that keeps taking a little resets both limits, so this check shows the stall limit is in force and the stream is spared, not any minimum transfer rate: no setting named here bounds a client that keeps reading slowly.
  - **Forwarded headers.** Behind a proxy on another address, set `UVICORN_FORWARDED_ALLOW_IPS` (or `FORWARDED_ALLOW_IPS`) to that address, so the server's log shows clients' addresses and not the proxy's; never `*` unless the server is reachable only through the proxy. The image honours it, and every other `UVICORN_*` setting but the six it pins (brief §4.3). Check: the access log shows a client's address for a request made through the proxy.
  - **Idle connections.** nginx: `keepalive_timeout` for clients (default 75 s). For its own connections to the server, when it keeps them (the `upstream` block's `keepalive` connection cache; see nginx's `upstream` documentation for when it is on), an upstream `keepalive_timeout` (default 60 s) under the server's 5 s, so nginx never reuses one the server is closing. cloudflared: `originRequest.keepAliveTimeout` (default 1m30s) under 5 s. Caddy: `idle` (default 5 min) for clients. Check: make one request through the public name on a kept-alive connection, then send nothing (`time openssl s_client -quiet -connect <name>:443`, a request, then wait); the proxy closes it at its own limit. The server closes a connection to it that sends nothing at 10 s, or at 5 s after a response, which bounds what one costs, not how many there are.
  - **Bodies of at least 2 MiB.** nginx: `client_max_body_size 2m` or more (the default, 1 MiB, refuses a full result set or a full import), with `proxy_request_buffering on` (the default: "the entire request body is read from the client before sending the request to a proxied server"), and `client_body_timeout` (default 60 s, between two reads) long enough for the slowest legitimate upload's pauses. Caddy: `request_body { max_size … }` (experimental, from Caddy 2.10) and the server's `read_body` or `read_body_idle` timeouts. Check: post a 1.5 MiB body to `/mcp` without a bearer and get the server's `401` (`WWW-Authenticate: Bearer`), not the proxy's `413`.
- Agents: one per VLAN, single-homed, on an existing host or a small container; `ALLOWED_CIDRS` reviewed, not left at default, if the network uses unusual ranges.
- Scan scope: leave DHCP pools unscanned unless static leases inside them need tracking; exclude any reserved range holding devices that should not be probed.

## 9. Decisions
