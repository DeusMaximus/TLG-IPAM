# TLG-IPAM — Homelab-First IP Address Manager
### Project Brief & Build Specification · v1.1 · June 2026

---

## 1. Purpose & goals

TLG-IPAM is a clean, modern IP address manager designed for homelabs. It replaces phpIPAM without inheriting its complexity, and avoids Netbox's enterprise scope entirely. The product should feel fast, obvious, and pleasant to use — a tool you actually want to open.

**Design target:** a homelab operator with 4–12 VLANs, 50–300 hosts, and zero tolerance for configuration overhead. Every workflow should complete in ≤3 clicks from the dashboard.

**Non-goals — explicitly out of scope for v1:**
- BGP / MPLS routing tables
- Multi-user / RBAC (single-user, API-key auth only)
- Discovery agents or active network scanning
- Rack diagrams or physical layer mapping
- IPv6 (out of scope for v1, but all IP handling uses Python's `ipaddress` module and avoids `/24`-shaped assumptions, so IPv6 is a feature later — not a rewrite)

## 2. Architecture overview

### 2.1 Stack

| Layer | Technology |
|---|---|
| Frontend | React 19 + Vite + Tailwind CSS 4 |
| Backend API | Python 3.12 + FastAPI |
| Database | SQLite via SQLAlchemy 2 (async, `aiosqlite`) |
| MCP server | FastMCP 4.x (locked at 4.1.8, MCP SDK 2.3.0) — curated tools, mounted at `/mcp` in the same process |
| Container | Docker — **single container**: FastAPI serves the API, MCP, and the built SPA |
| Reverse proxy or tunnel | Optional. For remote MCP it publishes the `/mcp` and discovery paths alone (§5.5); `docs/deployment.md` gives Cloudflare Tunnel and nginx configurations |

### 2.2 Container layout

One container. FastAPI serves the built Vite `dist/` as static files with an SPA fallback, so `/`, `/api`, and `/mcp` share a single origin — no nginx config, no CORS, one port to tunnel. SQLite lives in a named volume.

**One uvicorn worker, by design.** The image's `CMD` is `python -m app.serve`, which runs uvicorn's command line with one worker pinned (`workers=1`) and the limits below the app that its options cannot set (§4.3, #132). The single process does not depend on the environment: `WEB_CONCURRENCY`, `UVICORN_WORKERS` and `UVICORN_RELOAD` change nothing (`test_the_image_runs_one_worker_whatever_the_environment_says`; the `CMD` before #132 passed `--workers 1`, which takes precedence over `WEB_CONCURRENCY`, measured in #43). It must stay that way: no other worker count, no replicas behind a load balancer. The MCP server runs stateful Streamable HTTP, so a session's state lives in the memory of the process that opened it, and a request carrying that session id that reached another process would not find it. SQLite is a single file with one writer at a time; one process is what the `busy_timeout` queueing in §9 is sized for. Startup (create tables, add missing columns, seed device types) runs once per process with no coordination between processes: two workers starting on a fresh database sometimes fail to come up with `database is locked`. Scale-out is not a goal for a homelab tool.

```yaml
services:
  ipam:
    build: .
    volumes: [ipam-data:/data]
    environment:
      - API_KEY=${API_KEY:?set API_KEY in .env}
      - DB_PATH=/data/ipam.db
      - PUBLIC_BASE_URL=${PUBLIC_BASE_URL:-}          # empty: remote MCP off (§5.5)
      - MCP_REMOTE_WRITES=${MCP_REMOTE_WRITES:-false} # true: a link may be made read-write (§5.5)
      - UVICORN_FORWARDED_ALLOW_IPS                    # passed in only when set (§4.3)
    ports: ["8080:8080"]
volumes:
  ipam-data:
```

**Not root** (v0.2 spec §7.3, #173). The image runs the server as `ipam`, uid and gid 10001, fixed in the `Dockerfile` rather than a build argument, so a volume's owner does not depend on the build; the code it runs stays root's. The image's `/data` belongs to that user, mode 0700, and a new `ipam-data` volume takes it. Nothing in the image runs as root at start. A volume made by an image before #173 belongs to root (its directory, `ipam.db` and its `-wal`/`-shm`, often mode 0600, and any `before-restore-*` directory), and is given to the user once by the owner: `docker compose run --rm --no-deps --user root --entrypoint chown ipam -R 10001:10001 /data`, then `… --entrypoint chmod ipam 700 /data`, the mode a new volume has, since the root image left it `755` (README, "Upgrading from an image that ran as root"). SQLite opens a database it cannot write read-only, without an error, so a server started on such a volume would answer reads and refuse every write. The server checks first, when `app.database` is imported: the database's directory must be writable, and each of `ipam.db`, `-wal` and `-shm` that exists readable and writable, by the process's ids (`database.storage_problem`, `os.access`); otherwise it exits before it serves anything, with a message that gives the two commands for its own ids, the directory one shell word (`shlex.quote`); any control character in a path is shown as an escape, and a directory that holds one gets no ready-to-run command, since the escaped spelling names another path. `DB_PATH` is a filesystem path or `:memory:` (the empty name opens in memory too), and only those two are not checked (`database.on_filesystem`). `config.load_settings` refuses anything else before anything is served, in a fixed message ("DB_PATH must be a filesystem path or :memory:."): a `file:` name in any case, URI or not, and anything SQLAlchemy's URL would read otherwise than as the path (a `?` query such as `?mode=ro&uri=true`, a `%` escape), since the file checked would not be the file opened (`config.db_path_problem`). The restore script in `docs/backup-and-restore.md` runs every step in the volume as that user too, and copies the snapshot in through standard input, so the restored file is the user's whoever owns the snapshot on the host. CI's `server-image` job builds the image and starts it with no network (`.github/scripts/check-server-image.sh`): the process's ids, a new volume, and a volume as a root image left it, refused, then given over and made 0700, keeping its data and taking writes.

**The scan agent is a second image** (`agent/`, v0.2 spec §5.6), run on a Linux host on the VLAN it sweeps with host networking and `CAP_NET_RAW`, not beside the server in this compose file. It connects out to the server's `/api/v1/agent/*` over HTTPS with TLS always verified (plain `http` only to its own loopback), checks in every minute, and runs the jobs it is given one at a time: an ICMP echo sweep of the job's ranges, then an ARP sweep when the job is issued `arp` (a broadcast request from a raw `AF_PACKET` socket on the interface whose network contains the subnet, and one retry for each address still silent after a second; a reply is taken only from an address it asked, and gives the address's MAC), then PTR lookups for the addresses either found (one UDP query per DNS server, at most three servers, no retransmission or TCP, truncated replies unused; the servers are the subnet's `dns_servers`, else the addresses in the agent host's `/etc/resolv.conf`, read again for every job, in a thread so a stalled read cannot hold the agent: a path that is not a regular file or is over 64 KiB when the agent looks at it is not opened, and gives none, as does a read not done within a second, or by the job's deadline; a read that stays stuck needs the agent restarted, unless the subnet lists its own servers; with the agent's own `ALLOWED_DNS_SERVERS` set, a server outside it, whichever named it, is never sent a query, the job's error says how many were left out, and with none left no lookup is made and the scan is incomplete, so stored names are kept, #93), every datagram and frame the agent sends for all three paced together at up to `MAX_PPS` (default 200) a second, from one job into the next: each is handed to the kernel in the step its slot is granted in or not at all (a DNS query or ARP request the socket cannot take at once is a failed send, never sent later), and the next slot comes no sooner than `1/MAX_PPS` after that step has ended, so no two are handed over closer than that, with nothing caught up after a late wake or a late hand-off, and the rest of the agent runs between any two slots (the ARP the kernel itself sends before an echo request to an on-link address, up to 3 for an address that does not answer, is outside that budget), inside a 10-minute timeout after which it reports what it saw as incomplete; a scan still running 30 s past its timeout is stopped and reported as an agent error. Before any packet it refuses a job whose subnet is outside its own `ALLOWED_CIDRS` (default RFC 1918 and CGNAT), whose ranges leave the subnet, or that holds more than 4,096 addresses, and reports the refusal, which the server keeps as the target's `last_scan_error` (§3.10). The agent's own address on that interface is reported alive with the interface's MAC, without a request (the kernel answers none of its own). Then, for a job issued `fdns` (#20), A lookups for the names the job sent, through the same servers, limit, path and budget (one UDP query per server for A records only, the reply read for the question's name along its CNAME chain as a PTR reply is, the same size and record limits): a name a server answered resolves to its addresses, or does not resolve (NXDOMAIN, or no A record); one no server gave a usable answer has no entry, so the server keeps what it has; the job's error counts those in their own words, and they are the first counts given up when the error would pass 500 characters. They run after the PTR lookups, and not at all after those timed out or could send nothing. The agent cannot tell whether a name is under the subnet's domain (the server's rule, §4.5), so it refuses a job naming anything but DNS hostnames, and more than 1,024 of them, the most the server sends (`protocol.FDNS_JOB_MAX`, held equal to the server's). A job issued `arp` on an agent with no interface on the subnet that has a MAC, or one issued a method the agent cannot run (none since #20), runs the rest and is reported incomplete, so it marks nothing dead. So is a job whose PTR lookups had no DNS server to ask (the subnet names none and the host's `resolv.conf` lists none it can use), with the error `rdns not run: the agent has no DNS server to ask (…)` and no DNS packet sent, or one of whose lookups tried and could send its query to none of its servers, which also cancels the lookups still running (no query is handed to a socket after it; one already handed over may still go out): a lookup not made is not one that found no name, so the stored names stay (spec §5.2). A refused check-in starts no scan: `429`/`503`/5xx are retried after 10 s to 5 min of jittered back-off, `401`/`403`/`409`/`422` every 13.5–15 min (spec §5.7). Every request to the server has a 30-second deadline covering the whole answer, which is read undecoded into at most 1 MiB, never holding more, and acted on only in its route's shape; the agent logs status codes and validated counts, never the server's text, and redacts its own token from its log. The agent never runs, downloads or installs anything the server sends (spec §7.2, invariant 1). Running it: the README's "Scan agent" section.

### 2.4 Releases

The server and the agent are one version (#24, spec §5.6): `VERSION` in `api/app/version.py` and the agent's `__version__`, the same string, a PEP 440 public version in normal form (`0.2.0` at a release, the next release's `.dev0` on `main` between releases). `GET /health` reports it, the Agents page pins its install commands to it, and an agent older than it is flagged. A tag `v<version>` on a commit of `main` runs `.github/workflows/release.yml`, which builds the agent's wheel and its image (`linux/amd64` and `linux/arm64`), checks both (the versions and the tag, the wheel's name, metadata and files, the image's start-up on each platform with no network), and publishes them under exactly the names the commands use: `ghcr.io/deusmaximus/tlg-ipam-agent:<version>` and `tlg_ipam_agent-<version>-py3-none-any.whl` on the GitHub release `v<version>`. It then fetches both with no credential, as the commands do. Neither publish job writes until the registry or GitHub has answered what the version already holds: a read that does not say is retried, then stops the job with nothing written (#159). A failed publish is finished by re-running the failed jobs while the build's artefact remains (configured for 7 days; that a re-run attempt can download the artefact an earlier attempt uploaded was measured on the first release, `.agents/releases.md`); once the image is published, a version past that is spent, never rebuilt, and the next one is released. A pull request or a run by hand builds and checks and publishes nothing. The agent's image is built from a base named by digest (`agent/Dockerfile`, `python:3.13-slim@sha256:…`, the tag's multi-platform index; #94), so two builds of a commit start from the same operating-system layer and the tag records which one a release shipped; the digest is moved forward by hand (`AGENTS.md`, Commands), at the latest before each release, and the release's build warns when the tag has moved on from it. The server itself is built from the tag, not published as an image, and its `Dockerfile` names its bases by tag alone: it is built where it runs, so each build takes the base's current fixes. The checklist is `.agents/releases.md`.

## 3. Data model

### 3.1 Section

Top-level grouping. Maps to a network segment or physical location.

| Field | Type / notes |
|---|---|
| `id` | UUID, primary key |
| `name` | str — e.g. `Home LAN`, `Homelab`, `IoT`, `VPN` |
| `description` | str, nullable |
| `colour` | hex string for UI badge, nullable |

### 3.2 Subnet

A CIDR block, always belonging to one Section.

| Field | Type / notes |
|---|---|
| `id` | UUID, primary key |
| `section_id` | FK → Section |
| `cidr` | str — e.g. `10.10.30.0/24`. Validated on write, and stored in its canonical spelling (`ipnet.canonical_cidr`, `str` of the parsed network): `10.10.30.0/255.255.255.0`, `10.10.30.0/0.0.0.255` and `10.10.30.0/0024` are all stored, answered and logged as `10.10.30.0/24`, and a refusal names the network that way too. A subnet stored with another spelling before #97 keeps it until an update sends `cidr` (the UI's edit form resends it on every save), which stores the canonical one; that entry's snapshots show both. Every comparison is of networks, never of strings (the overlap rule below; a CIDR edit to another spelling of the same network changes nothing else). A scan job (§4.5) and `list_scan_findings` (§5.2) carry the canonical spelling whatever is stored |
| `vlan_id` | int, nullable — VLAN tag number (1–4094) |
| `name` | str — friendly label |
| `domain` | str, nullable — default domain suffix for hosts in this subnet (e.g. `lab.home.arpa`) |
| `gateway` | str, nullable — IP within subnet |
| `dns_servers` | JSON array of IP strings, nullable. At most 8 on write (`schemas.SUBNET_DNS_SERVERS_MAX`): a longer list is `422` "dns_servers: a subnet may list at most 8 DNS servers, not N". A subnet stored with a longer list before that bound keeps it: an update that leaves `dns_servers` out, or resends the stored list unchanged (as the UI's edit form does), is applied and keeps it; an update that changes it must meet the bound. A scan job carries the first three (§4.5) |
| `dhcp_start` / `dhcp_end` | str, nullable — inclusive bounds of the DHCP pool. Both within the subnet; allocation skips this range. |
| `notes` | text, nullable |

**Overlap rule:** overlapping or duplicate CIDRs are allowed *across* sections (useful for VPN vs LAN views of the same space) but rejected *within* a section.

### 3.3 ReservedRange

A block of IPs within a subnet that automatic allocation skips — e.g. addresses held for network gear not yet installed. Manual host creation inside a reserved range is still allowed. A subnet can have any number of these.

| Field | Type / notes |
|---|---|
| `id` | UUID, primary key |
| `subnet_id` | FK → Subnet |
| `start_ip` / `end_ip` | str — inclusive bounds, both within the subnet CIDR, start ≤ end |
| `description` | str, nullable — e.g. `network gear` |
| `scan_excluded` | bool, nullable — `true` takes the range out of its subnet's scan scope (§3.10). Null or `false` means scanned, and responses return `false` for null. Ranges from before the column existed gain it, null, on startup, so they read as scanned. Set on create over REST, or later with `PATCH`; never over MCP |

### 3.4 Host

A single IP assignment within a Subnet.

| Field | Type / notes |
|---|---|
| `id` | UUID, primary key |
| `subnet_id` | FK → Subnet |
| `ip` | str — must be within parent subnet CIDR |
| `ip_int` | int — integer form of `ip`, kept for range queries and returned in API responses as the numeric sort key so clients never parse address strings |
| `hostname` | str, nullable |
| `domain` | str, nullable — per-host domain-suffix override; null inherits the subnet's `domain`. API responses include a computed `fqdn` (hostname + effective domain). |
| `mac` | str, nullable — stored normalised (lowercase colon-separated) |
| `device_type` | str — must match a DeviceType name (see 3.5); matched case-insensitively and stored canonically |
| `status` | enum: `active` \| `reserved` \| `dhcp` \| `offline` |
| `owner` | str, nullable — e.g. `proxmox`, `personal` |
| `notes` | text, nullable — at most 4,096 characters (`schemas.HOST_NOTES_MAX`, #91), on every write that sends notes (§3.7) |
| `last_seen` | datetime, nullable — the stored column is set by hand: writable, and cleared by writing null (`clear_fields: ["last_seen"]` over MCP). A value sent with a UTC offset is converted to UTC before it is stored. Responses show the later of the stored value and the `last_seen_at` of the observation at the host's subnet and address (§3.11), derived on read: scan ingest never writes hosts. Clearing the stored value therefore still shows the scan time if the address has been seen |
| `last_seen_source` | output only: `manual` (the stored value), `scan` (the observation; also on a tie), or null when neither exists. Taken from the observation's `last_seen_at`, never from `alive`, so an address a later sweep missed still shows when it last answered |
| `created_at` / `updated_at` | datetime, auto-managed. `updated_at` moves only when a write changes a stored field: a `last_seen` that is the stored instant, sent with or without an offset, is not a change |

### 3.5 DeviceType

User-customisable device types (managed in Settings). Seeded on first boot with: `server`, `vm`, `lxc`, `network`, `iot`, `desktop`, `laptop`, `phone`, `other`.

| Field | Type / notes |
|---|---|
| `id` | UUID, primary key |
| `name` | str, unique — display name, e.g. `Raspberry Pi` |
| `icon` | str — identifier from the curated icon set (~28 Lucide icons) |

Rules: renaming a type cascades to all hosts using it (one transaction). A type in use cannot be deleted. `other` is the fallback default for new hosts — it cannot be renamed or deleted, but its icon can change.

### 3.6 Change (audit log)

A record of every write, never edited, with one deletion: an agent's own check-in entries (`source="agent"`) are capped at its newest 100, so the older ones are deleted (§4.5); owner entries are never deleted. Because Claude can write to this system via MCP, you need to be able to review what it did. Also powers the dashboard "recent activity" feed.

| Field | Type / notes |
|---|---|
| `id` | UUID, primary key |
| `ts` | datetime, auto |
| `entity_type` | enum: `section` \| `subnet` \| `host` \| `device_type` \| `agent` \| `token` \| `scan_target` \| `grant` (an OAuth grant, §3.15) \| `link_window` (§5.5). Reserved-range writes, a range's scan exclusion included, are logged as `subnet` updates |
| `entity_id` | UUID of the affected record |
| `action` | enum: `create` \| `update` \| `delete` \| `revoke` (`revoke` is for tokens and grants) \| `open` \| `wrong_code` (`open` and `wrong_code` are for link windows) |
| `summary` | str — human-readable one-liner, e.g. `host pbs-01 created at 10.10.20.45` |
| `before` / `after` | JSON snapshots, nullable |
| `source` | enum: `ui` \| `api` \| `mcp` \| `agent` \| `oauth` — MCP, `agent` and `oauth` are server-assigned; REST uses the advisory `X-TLG-Client: ui` hint, so `ui` versus `api` is a UX label rather than trusted provenance. `agent` is the agent's own write: a check-in that changed what the agent reports (§4.5), or its enrolment exchange (§4.8); each agent keeps its newest 100 such entries on its agent record (token entries are not capped), and over MCP the reported values in `agent` snapshots are withheld. `oauth` is the built-in OAuth server's own write (§5.5): a grant issued, a grant revoked because a refresh token was used again after it had been replaced, and a link window's first wrong link code, once a window (`link_window`, whose opening is the owner's `ui` or `api` entry); over MCP a `grant` snapshot's `redirect_uri`, which the client chose, is withheld. Not logged: heartbeats (`tokens.last_used_at`, `agents.last_checkin_at`, `oauth_grants.last_used_at`), job scheduling (the lease columns), scan results ingest (observations and the target's last-scan columns, §4.6), and of the OAuth server a client's registration (not a link: it comes from a caller with no credential and grants nothing) and the issue, rotation and pruning of codes and tokens |
| `actor` | str(80), nullable — who acted, when that is narrower than `source`. Null is the owner key, whether over REST or MCP. An agent's own write records `agent:<agent name>`; an OAuth grant's entries record `grant:<client name>`, or null when the client's declared name was not kept (§3.14); the name is the sanitised one, so it is ASCII letters, digits, spaces, `-` and `_`, and a past entry keeps the name it was written with. An MCP write made with a grant's token (§5.5, remote writes) records `grant:<client name>` too, and `grant-id:<grant id>` when the name was not kept: never null, so it is never taken for the owner's, and under a prefix no declared name can produce. It is a field of its own and never part of `summary`. Databases created before it gain the column, null in existing rows, on startup. |

### 3.7 Validation constraints

- Subnet CIDR must be valid — reject on write, return 422 with message.
- Subnet CIDRs must not overlap within the same section (see 3.2).
- Host IP must fall within its subnet's CIDR — enforce at API layer.
- No duplicate IPs within a subnet — enforced by `UNIQUE(subnet_id, ip)` in the database, not just the API layer.
- `dhcp_start`/`dhcp_end` must both be set or both null, both within the CIDR, start ≤ end.
- Reserved ranges must be within the subnet CIDR, start ≤ end. A subnet holds at most 100 of them (`schemas.SUBNET_RESERVED_RANGES_MAX`, #86), excluded from scanning or not, on every path that adds one (the UI and `POST /subnets/{id}/reserved`, MCP `add_reserved_range`): adding the 101st is refused (`reserved_ranges: a subnet holds at most 100 reserved ranges; delete one before adding another`). The limit exists because each visit of `list_scan_findings` reads a subnet's excluded ranges to build its scope, and `get_subnet` returns them all, and MCP adds one per call. A subnet stored with more before the limit keeps them; editing and deleting them works, and adding one is refused until it holds fewer than 100. The owner may set the limit elsewhere; it is one constant.
- Changing a subnet CIDR must preserve every child invariant: existing hosts must remain assignable (including network/broadcast rules), and reserved ranges must remain within the new CIDR.
- Update requests may omit fields they do not change. Explicit `null` is accepted only for nullable fields; required fields return `422 VALIDATION_ERROR` rather than reaching a database constraint.
- Domain suffixes normalised to lowercase, leading/trailing dots stripped, charset-validated, and at most 253 characters (`ipnet.DOMAIN_MAX`, the longest DNS name), on every write that sends one, a bulk import's rows included (a longer one is that row's `error`). Until #86 only the request-body cap bounded a domain: a row stored before then keeps a longer one until a write sends its domain, which must then meet the limit (the UI's forms resend every field, so saving such a subnet or host from the UI means shortening or clearing its domain in the same form).
- A host's `notes` is at most 4,096 characters (`schemas.HOST_NOTES_MAX`, #91), checked by `services/hosts` on every write that sends notes: create, update and next-free allocation (`422` `notes: a host's notes may be at most 4096 characters, not N`, which never repeats the value), and each row of a bulk import, where a longer one is that row's `error` and the other rows import, from the UI, REST and MCP alike. Until #91 only the request-body cap bounded notes: a host stored before then keeps longer ones. An update that resends them unchanged is let through (the UI's host form resends every field, so such a host can still be edited and loses nothing, as with a subnet's DNS servers, §3.2); one that changes them must meet the limit. A subnet's `notes` has no limit of its own.
- MAC addresses normalised to lowercase with colons on write.
- VLAN IDs 1–4094 only.
- Deleting a section requires no child subnets. Deleting a subnet requires no hosts, unless `force=true` is passed (cascades to hosts and reserved ranges; the UI requires explicit confirmation). Either way the subnet's scan target is deleted with it, with its own change-log entry.
- A scan target needs a subnet of `/20` or a longer prefix, and its subnet's CIDR cannot then be changed to a shorter one.

### 3.8 Agent

A scan agent (v0.2 spec §5.4). The owner creates it over REST with an enrolment token; the agent exchanges that for its agent token over `/api/v1/agent/enrol` (§4.8), checks in over `/api/v1/agent/checkin` (§4.5) and reports scans over `/api/v1/agent/results` (§4.6). The Agents page arrives with v0.2 M2a.

| Field | Type / notes |
|---|---|
| `id` | UUID, primary key |
| `name` | str. 1–74 printable characters, trimmed: `agent:<name>` is the audit `actor` for the agent's own writes and must fit `changes.actor` (80). Unique case-insensitively (`409`) |
| `name_key` | str, unique — `name.casefold()`, so the database itself refuses two names that differ only in case, even from racing requests. Internal: not returned, not in audit snapshots |
| `state` | enum: `pending` (has never held an agent token: created, not yet enrolled) \| `active` \| `disabled`. An agent is created `pending` with an enrolment token, and becomes `active` when it exchanges one (§4.8) |
| `version`, `platform`, `hostname`, `interfaces` | nullable; reported by the agent at check-in, and null until its first (the first three may also be reported at enrolment, §4.8). Trimmed, printable characters only, at most 40, 120 and 253 characters; `interfaces` is up to 64 `{name, cidr, mac}` (name at most 15 characters; `cidr` an address with its prefix length, normalised, no IPv6 scope id; `mac` normalised or null). A check-in that fails these checks changes none of them |
| `last_checkin_at` | datetime, nullable — set by every check-in that takes its slot (§4.5), including one then refused for its protocol or a field (`409`, `422`). A check-in refused by the rate limit (`429`), or because the agent was disabled or its token revoked after it authenticated (`403`; §4.5 gives which of the two a request gets), does not set it |
| `current_job_id`, `job_issued_at` | nullable, read-only — the job the agent was last issued, and when (§4.5). The agent is busy while that lease is live, whatever has since happened to the target. Databases created before them gain the columns on startup |
| `last_error` | text, nullable — why the last check-in was refused (protocol mismatch, or the first field that failed validation, by name and never by value). Cleared by a check-in that succeeds |
| `created_at` | datetime, auto |
| `update_available` | response only, never stored (`agents.agent_out`, #23) — whether the `version` the agent last reported is older than the server's own (`GET /health`), compared as PEP 440 versions (`0.2.0.dev0` is older than `0.2.0`). Null when either is unknown or not a version. A newer agent is not flagged |
| `protocol_mismatch` | response only, never stored — whether `last_error` is check-in's protocol refusal (it starts `Protocol mismatch:`, `agents.PROTOCOL_MISMATCH_PREFIX`). The agent then gets no job until a check-in on the server's protocol is accepted, which clears it |
| `enrol_refusal` | response only, never stored in the database (#175) — the last enrolment refused for the agent's protocol, `{code, refused_at}`: `code` `AGENT_TOO_OLD` or `AGENT_TOO_NEW` (§4.8), `refused_at` the server's time. Kept in process memory by enrolment token (`agents.enrol_refusals`, at most 1,024 entries), so the refusal writes nothing, and given for the agent's current enrolment token (`agents.current_enrolment`, by identity, never by issue time): its one live enrolment token, else, for an agent that has never held an agent token, its one neither used nor revoked (an expired one, no re-enrol since); null when there are two or more of either, when that token has none, while the agent is disabled, and after a restart until the agent's next attempt |

Rules: disabling an agent refuses its token without revoking it, and enabling it accepts the token again. Deleting an agent revokes its unrevoked tokens (each logged as a `token` `revoke`), sets `agent_id` to null on its scan targets (each logged as a `scan_target` update; their settings are kept), then deletes the agent and its token rows.

### 3.9 Token

A credential bound to an agent (v0.2 spec §4.2). An agent token is `tlga_` followed by 43 URL-safe random characters (256 bits); an enrolment token is `tlge_` and 43 more. That form, the prefix and 43 characters of the URL-safe base64 alphabet, is part of the agent wire contract (`agent_protocol.AGENT_TOKEN_FORM` and `ENROL_TOKEN_FORM`, #140): an agent stores only an agent token of exactly it. A server that issued another would raise `PROTOCOL_VERSION`, and since #165 that is what protects an agent of an earlier release: the enrolment body states the agent's protocol (none meaning 2), and an exchange on another is refused `409` before the token is spent (§4.8). A form changed without raising `PROTOCOL_VERSION` would still have an earlier agent's enrolment answered `200` and its enrolment token spent on a token it refuses. An enrolment token is single-use, expires an hour after it is issued, and reaches one route, `POST /api/v1/agent/enrol` (§4.8), which exchanges it for the agent token.

| Field | Type / notes |
|---|---|
| `id` | UUID, primary key |
| `kind` | enum: `agent` \| `enrol`. "Add agent" and re-enrol issue `enrol` tokens; only the enrolment exchange issues an `agent` token |
| `agent_id` | FK → Agent |
| `token_hash` | SHA-256 of the token, hex, unique. Never returned and never in an audit snapshot |
| `token_prefix` | the first 13 characters (`tlga_` or `tlge_`, and 8 more), for display |
| `created_at`, `last_used_at` | `last_used_at` is set by a request the route serves — a check-in that takes its slot, an accepted result set — in that request's transaction, when the stored time is unset or at least 10 seconds old (`agents.LAST_USED_GRANULARITY`; the condition is in the SQL `UPDATE`, so racing requests write it once). A request refused before it takes its check-in slot, and a refused result set, never set it, so a token used at request rate drives no writes; a check-in refused after it took its slot (`409`, `422`) has set it, with `last_checkin_at` and `last_error` (§3.8) |
| `expires_at`, `used_at` | enrolment tokens only; null for agent tokens. `expires_at` is an hour after `created_at` (`agents.ENROL_TOKEN_LIFETIME`); the token is accepted strictly before it. `used_at` is set by the exchange that spends it, and is the only record the enrol route keeps of a token's use: it writes no `last_used_at`, on either token |
| `revoked_at` | datetime, nullable |
| `expires_in_s` | response only, never stored (`agents.expires_in_s`, computed by `agents.agent_out`, #143) — the whole seconds, rounded down, a live enrolment token (unrevoked, unused, unexpired: `agents.live`) has left by the server's clock when the answer was built; null for one that is not live and for an agent token. It does not look at the agent's state: a disabled agent's token is still live, though the exchange refuses it until the agent is enabled. The Agents page counts it down by the browser's monotonic clock from when it requested the list, never comparing `expires_at` with the browser's clock (§6.2) |

Rules: the plain token appears in exactly one response, the one that issues it (create or re-enrol for an enrolment token, the enrol exchange for an agent token); it cannot be recovered afterwards. An agent holds at most one unrevoked `agent` token, enforced by a partial unique index, and at most one enrolment token that can still be exchanged (re-enrol revokes the one before). A token is live while it is unrevoked and, for an enrolment token, unused and unexpired: revoke and delete revoke the live ones only, so a spent or expired enrolment token is never revoked. Token create, use (the exchange) and revoke are audit-logged with `entity_type="token"`. The owner's writes have a null `actor`; the exchange is the agent's own write, with `source="agent"` and `actor` `agent:<name>` (§4.8).

### 3.10 ScanTarget and scan scope

A subnet the owner has chosen to scan, and how (v0.2 spec §5.3, §5.4). At most one per subnet. Configured over REST only; no MCP tool reads or writes it. Check-in hands out jobs for it (§4.5), and results ingest records them (§4.6).

| Field | Type / notes |
|---|---|
| `id` | UUID, primary key |
| `subnet_id` | FK → Subnet, unique. Fixed once created |
| `agent_id` | FK → Agent, nullable. Null = unassigned: nothing is scanned until an agent is chosen |
| `enabled` | bool, default `true` |
| `methods` | JSON list — a subset of `icmp`, `arp`, `rdns`, `fdns` that includes `icmp` or `arp` (the liveness methods). Stored de-duplicated in that order. Default `["icmp", "arp", "rdns"]` |
| `scan_dhcp_pool` | bool, default `false` — whether the subnet's DHCP pool is in scope |
| `interval_minutes` | int, nullable — 5 to 10080 (a week); null = manual only |
| `scan_requested_at` | datetime, nullable, read-only — when a scan was last requested (`POST /subnets/{id}/scan`). Never cleared: it also times the cooldown |
| `current_job_id`, `job_issued_at`, `job_methods` | nullable, read-only — the job lease, set when check-in issues a job (§4.5); `job_methods` is what the job was issued with. Databases created before `job_methods` gain it on startup |

| `last_scan_at`, `last_scan_duration_ms`, `last_scan_complete` | nullable, read-only — the last-scan record, written by an accepted result set (§4.6). `last_scan_at` is when that job was issued, by the server's clock, so it also keeps the attempt time scheduling orders by; `last_scan_duration_ms` is the agent's own `finished_at − started_at`; `last_scan_complete` whether the agent swept every range |
| `last_scan_error` | text, nullable, read-only — the `error` the agent reported with its last result set, or null. Agent text: non-printable characters become spaces, whitespace runs collapse, at most 500 characters. Kept out of audit snapshots, which `list_changes` serves over MCP. Databases created before it gain the column on startup |
| `created_at` | datetime, auto |
| `runnable_methods` | response only, never stored — the methods a job for the target would run on its agent now, from the interfaces the agent reported at its last accepted check-in. Computed on read by `services/jobs.job_methods`, the rule check-in issues jobs by (§4.5): `arp` dropped when no reported interface is on the subnet's link. `[]` when no liveness method is left: the target cannot be scanned by this agent, and check-in issues it no job. Null when that is not known: no agent assigned, or one that has never reported its interfaces (no check-in of it has been accepted; a refused one stores none). A disabled agent is judged by what it last reported. The agent's next check-in changes it without a write to the target |
| `agent_checkin_at`, `agent_checkin_refused` | response only, never stored — how old the evidence for `runnable_methods` is: the agent's `last_checkin_at` (the same time `GET /agents` serves) and whether that check-in was refused (`409` or `422`, read from the agent's `last_error`, which only a refused check-in sets and an accepted one clears). Only an accepted check-in reports interfaces, so when the last check-in was accepted they are from `agent_checkin_at`; when it was refused they are from an earlier accepted one, whose time is not stored. Both null when `runnable_methods` is. The stored time is the server's clock; the UI does not read a time more than one check-in interval ahead of the browser's clock as an age (§6.2) |

**Scan scope** is the set of addresses a scan may send packets to. It is computed in one place, `services/scans.scan_scope(subnet)`, as inclusive address ranges: the subnet's usable addresses (no network or broadcast for `/30` and shorter), minus the DHCP pool unless `scan_dhcp_pool` is set, minus every reserved range with `scan_excluded`. Exclusion wins: an address in both an excluded and a scanned reserved range is excluded. A subnet without a scan target has the default scope (pool not scanned). Scan-target responses carry it as `scope: [{start, end, start_int, end_int}]`: each range's addresses, and the same bounds as integers of the subnet's family, so the UI places a host by its `ip_int` without parsing an address. A job's `ranges` carry the addresses only (§4.5).

Rules: one target per subnet (`409`, also enforced by `UNIQUE(subnet_id)`). Unknown subnet or agent: `404`. A method outside the four, or a set without `icmp` or `arp`: `422`. Every create, update and delete is audit-logged as `scan_target`; an update that changes nothing writes no entry.

**Leaving scope deletes observations, finding dismissals and forward-DNS answers** (§3.11, §3.12, §3.13). A write that can narrow the scope deletes the subnet's observations and dismissals outside the scope as it then stands, and the forward-DNS answers of its hosts whose addresses are outside it, in the same transaction: turning `scan_dhcp_pool` off, deleting the target (the default scope leaves the pool out), excluding a reserved range or adding one excluded, and editing the DHCP pool or the CIDR (`services/scans.drop_out_of_scope`). The write itself is logged as usual; the deleted rows are not. The deletion judges the scope as committed, under SQLite's write lock, so a pool another request moved, or an observation an ingest stored, after the edit first read the subnet is not undone by it.

### 3.14 OAuthClient

A client registered with the built-in OAuth server (v0.2 spec §6.4, #26), by dynamic registration (§5.5). A registration is not a link: it grants nothing until the owner approves a grant for it. Table `oauth_clients`.

| Field | Type / notes |
|---|---|
| `client_id` | str(36), primary key — the UUID the registration handler draws |
| `client_name` | str(60), nullable — the client's own claim about itself, sanitised at registration (v0.2 #29, `services/oauth.sanitise_name`): of the first 256 characters declared, an accented letter keeps its base letter, every character but an ASCII letter, a digit, a space, `-` or `_` becomes a space, runs of spaces become one, the ends are trimmed, and the result is cut to 60. A result with no letter or digit is no name (null): a name wholly in another script (Cyrillic, CJK) is not kept. So a stored name holds no `.`, `:`, quotation mark, symbol or emoji. `ChatGPT`, `Claude`, `Google` and `mistral-mcp-client` are stored as declared. Names stored by an earlier version are stored again by this rule when the server starts. It appears in `actor` (§3.6), never in a summary |
| `redirect_uris` | JSON list of 1 to 16 URIs, each at most 2,048 characters: `https` with a host, or `http` to `localhost` or a loopback address (§5.5) |
| `token_endpoint_auth_method` | `client_secret_post`, `client_secret_basic` or `none` (a public client) |
| `client_secret_hash` | str(64), nullable — the SHA-256 of the client secret; null for a public client. The plain secret appears once, in the registration answer. Never in an audit snapshot or a response |
| `grant_types`, `scope` | of the server's grant types (`authorization_code`, `refresh_token`) and scopes (`ipam:read`, `ipam:write`), the ones the client registered for |
| `created_at`, `linked_at` | datetimes; `linked_at` is when its first grant was approved, null while it has never been linked |

Nothing else a client declares (`client_uri`, `logo_uri`, `software_id`, …) is stored. **At most 50 registrations exist** (v0.2 spec §6.6), counted under the write lock: at the cap a new one takes the place of the oldest that holds no unrevoked grant, never linked or its links revoked alike, and when all 50 hold an unrevoked grant it is refused (§5.5). A reclaimed registration's grants and audit entries stay (§3.15). **A registration never linked is deleted once it is 24 hours old** (v0.2 #29): it is gone to every read from that moment (it cannot authorise, and a request of it still pending is told to start again), and its row is deleted at the next registration or approval, or when the server starts, under the write lock. One that was ever linked (`linked_at` set) is never deleted by this rule, whether or not its grants have been revoked. This is what removes the spare registration of a client that registers twice for one link. **A request pending for a registration does not spare it** at the cap (v0.2 #190): the order is `created_at` (then `client_id`) alone, and the pending store is not read. Preferring to keep such a registration would raise an outsider's cost only where reclaiming it is cheaper than pushing its request out of the store, and only up to the store's 32 authorise requests, which still end the request; that was judged too little benefit (§5.5, wrong codes). **A link never completed** (the owner approved it, the code expired unexchanged) keeps its registration: its grant is unrevoked and `linked_at` is set (§5.5). A registration is reclaimable only once every one of its links is revoked, and one registration can hold several, so revoking a marked link frees the place only when its registration holds no other unrevoked link. Registrations are not audit-logged, stored, deleted or reclaimed (§3.6).

## 4. REST API

### 4.1 Auth

Single static API key passed as a header:

```
X-API-Key: <value from API_KEY env var>
```

All endpoints except `GET /health` and the agent-facing `/api/v1/agent/*` (enrolment included) require this header. Return `401` if missing, `403` if wrong. The key is compared in constant time (`hmac.compare_digest`, in `auth.is_owner_key`). Key is set at container start — no key rotation UI needed in v1. The server refuses to start unless `API_KEY` is set, non-empty (not only whitespace), free of whitespace at either end and not `change-me`, the placeholder `.env.example` ships: `config.load_settings` runs when `app.config` is imported, so uvicorn exits with a message that names `API_KEY` and says how to generate a key, before it serves anything (under `--reload`, the reloader stays up and its server process exits). A key with a leading or trailing space, tab or newline is refused, not trimmed: most HTTP clients cannot send such a header value, a raw one can, and trimming would leave two candidate keys. The message is fixed and never contains the key. Separately, `is_owner_key` never matches an empty value, so an empty `X-API-Key` is refused (`403`) whatever the setting holds. REST does not accept the key as a bearer, and `/mcp` does not accept `X-API-Key` (§5.1).

Agent-facing routes, `/api/v1/agent/*` but `enrol`, take an agent token instead (§3.9), as `Authorization: Bearer tlga_…`, authenticated through the `auth.require_agent` dependency and nothing else. It accepts only an unrevoked `agent` token of an `active` agent, and only reads: the route that serves the request records `last_used_at` in its own transaction (§3.9), so a refused bearer never writes it, nor does a request refused before its check-in slot or a refused result set. A check-in then revalidates the agent's state and the token's revocation in its claim, under the write lock (§4.5), and so does results ingest before it touches the lease (§4.6). If the database refuses a write of an agent route (locked past SQLite's 5-second busy timeout, a read-only file, a full disk), the route's transaction is rolled back and the request gets `503 UNAVAILABLE`, safe to retry, and nothing of it is written. The message says "busy" only for a lock, and the server logs the operation and SQLite's error name, never SQL, parameter values or the bearer. A failed rollback, a failure of the authentication read itself, and a database error that is not an `OperationalError` (an integrity or programming error, say) are a bare 500. The token is found by the SHA-256 of the presented value, so the stored secret is never compared. Refusals use the REST error shape: `401 UNAUTHORIZED` when no bearer is sent (including `X-API-Key` alone), `403 FORBIDDEN` "Invalid agent token" for any bearer that is not a usable agent token — the owner key, an unknown, revoked or `enrol` token, or the token of a disabled or deleted agent. The owner routes refuse an agent token (`403` as `X-API-Key`, `401` as a bearer), and so does `/mcp` (`401 invalid_token`). The router for `/api/v1/agent/*` carries `require_agent` itself, so a route added to it is guarded too, and it is mounted apart from the owner routers, so the owner key never reaches it. The routes are check-in (§4.5) and scan results (§4.6). The one exception is `POST /api/v1/agent/enrol` (§4.8), on a router of its own that holds nothing else (`routers/agent.enrol_router`): it takes an enrolment token, `Authorization: Bearer tlge_…`, checked by `services/enrolment` behind its own throttle, and neither the owner key nor an agent token.

### 4.3 Standard response shapes

```json
// Success — 200 / 201
{ "data": { ... } }             // single object
{ "data": [ ... ], "total": N } // collection

// Error — 4xx / 5xx
{ "error": { "code": "VALIDATION_ERROR", "message": "IP 10.10.30.300 is invalid" } }
```

**Datetimes are UTC and carry their offset**, in every REST response and every MCP tool result: ISO 8601 with `+00:00` (`"2026-11-16T06:38:44.765279+00:00"`), the same string in the response to the write that created a row and in every later read of it. SQLite reads a stored datetime back without its zone, so the response models give it back (`schemas.UtcDatetime`). `last_seen`, the one datetime a client writes, is taken as UTC when sent without an offset (§3.4), and compared as an instant with the stored column (not the later of it and a scan's time, which is what a response shows), so re-sending it unchanged in another form does not move `updated_at`. A change's `before`/`after` snapshots carry the offset too; audit entries written before it did hold their datetimes without one, still UTC, and the UI reads an offset-less value as UTC. The agent routes keep their own shapes (§4.5, §4.6).

**Request bodies are capped at 2 MiB** (2,097,152 bytes, `body_limit.BODY_MAX`, the one place the limit is defined), on every route: owner, agent, and `/mcp` (§5.1). `BodyLimitMiddleware` wraps the whole app, so the cap runs before routing, before any authentication check and before any body is parsed. A larger body is `413 PAYLOAD_TOO_LARGE` "The request body may be at most 2097152 bytes", with `Connection: close`, whatever credentials it carries or lacks:

- a declared `Content-Length` over the cap is refused with nothing read; one within it is left to the route to read, and the HTTP server delivers no byte past it. The length is taken as the HTTP server passes it on: uvicorn's httptools parser, the one the image runs, accepts spaces or tabs after the digits and any number of leading zeroes, so both are dropped (`Content-Length: 2097153 ` and a length padded with 4,500 zeroes are refused unread like `2097153`, and a padded length within the cap is served), and the digits are compared with the cap by their count, never converted whole (#89). h11 strips the whitespace itself and refuses the zeroes with `400`;
- any other body is read and counted, and refused at the chunk that would pass the cap: one sent without a `Content-Length` (chunked), and any request with a `Transfer-Encoding` header whatever its `Content-Length` says, since a server that accepts both frames the body by the chunks (uvicorn's h11 does; httptools refuses such a request with `400`). One that fits is handed to the route whole, so up to 2 MiB of such a body is held before authentication refuses it, within the budget and the deadline below.

The limit was chosen from the largest legitimate requests (#60): an agent's result set for a full /20, 4,094 records each with a MAC and a 253-character PTR name, is about 1.3 MB, and about 1.94 MB with the most forward-DNS answers a job can ask for (§4.6, #20); a bulk import of 1,000 hosts, the most one import takes, with every length-bounded field but `notes` at its maximum (253-character hostname and domain, 120-character owner of 4-byte characters, 40-character device type) is 1,151,011 bytes as the UI encodes it. The figures are for measured rows, not a ceiling on a row. `full_rows` in `test_length_limits.py` builds them with every field written in ASCII but the owner: an address of 15 characters (an IPv4 address in a padded spelling is refused, so that is its longest), hostname and domain of 253, a MAC of 17 characters as it is normalised, a device type of 40, status `reserved` (the longest of the four). The limits count characters, and a hostname and a device type accept ones outside ASCII: 1,000 rows with 233 four-byte characters of notes, a hostname of 253 four-byte characters and a device type of 40 are 2,973,011 bytes, over the cap. A MAC's punctuation, a domain's leading white space and trailing dots, and a `last_seen`'s extra fractional digits are accepted and dropped on normalising, so no row is the largest one accepted. A device type of 5 characters (`other`) is 35 bytes a row less, so 1,000 rows are 1,116,011. The limits on a domain (253 characters), a device type (40) and on `notes` (4,096, #91) bound one host, not an import: they do not make every 1,000-row import fit. With every other field at its maximum, 1,000 rows fit only with at most 233 four-byte characters of notes each (1,295 ASCII characters with an ASCII owner); with notes at the limit the same rows are 17,546,011 bytes (5,258,011 in ASCII), and at most 119 such rows fit one request (398 with ASCII notes, 428 with an ASCII owner as well, that JSON writes one byte a character; a quote, a backslash or a control character such as a line break or a tab takes two bytes or more, so notes of them fit fewer rows: the size is the encoded bytes, never the character count). An import past the cap is refused whole with the `413`, to be split into several imports: the import dialog measures the request before sending it and, over the cap, says how many rows to split the file at (§6.2), and the `bulk_create_hosts` docstring tells an assistant how large a call may be (§5.2). `test_length_limits.py` holds these figures. A client that escapes non-ASCII as `\uXXXX` (Python's `json` by default) spends 12 bytes on a 4-byte character, so its worst case is larger than the UI's: the `bulk_create_hosts` example's 400 rows (§5.2), with 4,096 ASCII characters of notes, are 1,965,771 bytes as `json.dumps` writes the call with an ASCII owner and 2,493,771 with an owner of 120 characters outside the BMP (2,103,359 as the UI encodes it), which the real `/mcp` route refuses with `413`.

**All the bodies being received are bounded together, and in time** (#90). The cap bounds one body, and one worker serves everything (§2.2), so the same middleware holds two more limits:

- **Budget.** The body bytes of every request in progress, whether the middleware or the route reads them, total at most 16 MiB (16,777,216 bytes, `body_limit.BODIES_MAX`, eight bodies at the cap). A chunk that would pass it is refused with `503 UNAVAILABLE` "The server is receiving too many request bodies; retry the request" and `Connection: close`, and a request gives its bytes back when it ends. Authentication does not end the count: FastAPI parses a `Body` before the route's dependencies run, so check-in and every owner route with a body read it, a declared length included, before the credential is checked, and a request that has authenticated still holds its body while it is served. The cap is checked first, so a body too large for any request is `413`, never `503`. What a body costs is its bytes, not the number of chunks it was sent in: the middleware keeps a body it reads in one buffer, and hands a route that reads its own body blocks of at least 64 KiB (the last excepted), so the route's list of them stays short (100,000 one-byte chunks took 8.9 MB for a 100 KB body before #90's review, under 0.4 MB after).
- **Deadline.** A body must arrive whole within 60 s of its request's headers (`body_limit.BODY_TIMEOUT_S`), with a declared length or without one; otherwise it is `408 REQUEST_TIMEOUT` "The request body was not received within 60 s", with `Connection: close`. A body trickled a chunk at a time is timed as a whole, not per chunk. Once a body is whole, the route's later reads (a streamed response waiting for the client to leave) are not timed. 60 s is twice the agent's own deadline for a whole request (30 s), so an agent always gives up first; it admits a body at the cap sent at 35 KB/s and a full result set at 21 KB/s.
- **The connection closes** with every refusal, and with any response sent before its request's body was received whole (a bearer refused before the body is read, as on `/mcp` and on results): uvicorn would otherwise keep the connection to read and discard the rest of the body for as long as the sender trickles it. When the middleware refuses a body a route is reading, its refusal is the answer and the route is told the client has gone.

Measured on #90 with 32 unauthenticated connections that each sent 1.75 MiB of a body and stalled, against a loopback uvicorn: before the budget and the deadline the worker grew by 68 MiB (chunked to `/mcp`) and by 60 to 63 MiB (a declared length to check-in), on both parsers. With them it held nine bodies (the 16 MiB), refused the other 23 at once (`503`, or a reset for a client still sending), grew by 17 to 21 MiB, refused the nine with `408` at 60 s, and answered `/health` throughout.

**Request heads, idle connections and clients that stop reading are bounded below the app** (#132). uvicorn calls the app only once a request's head (its request line, header lines and the blank line that ends them) is complete, so nothing in the app, the body limits included, can see a head that is still arriving, a connection that has sent nothing, or a client that has stopped taking what it asked for. The image starts the server with `python -m app.serve` (§2.2), which runs uvicorn's httptools parser, the one it ran before, through `header_limit.HeaderLimitProtocol`, which adds:

- **Size.** A head may be at most 64 KiB (65,536 bytes, `header_limit.HEADER_MAX`) as received, whatever its spelling (a space after each colon or none, whitespace around values): its bytes from the first one after the request before it ended to the end of its blank line. A head that passes the limit is refused with `431` `{"error": {"code": "HEADERS_TOO_LARGE", "message": "The request line and headers may be at most 65536 bytes"}}` and `Connection: close`, and the app is not called; the server parses at most one byte past the limit of an unfinished head before it refuses. A head is counted exactly however the bytes are split into reads, on a fresh connection or a reused one: the server hands the parser each read in pieces of at most 4 KiB, cut where a head ends (once per head, since the parser skips blank lines before a request line) and where a body with a declared length ends, because the parser says that a request has ended, not where. The one exception is a head that follows a chunked body in the same piece, which is counted from the start of that piece, at most 4 KiB over. Cutting a chunked body at each CRLF CRLF would remove the exception, but its sender chooses how many there are: a 1.9 MB body of them took the worker 1.3 s to parse and delayed another client's `/health` by half a second. So the parser is handed one piece per read, as uvicorn does, plus at most one per 4 KiB and three per request, whatever the bytes hold. A head over the limit that arrives while another request on the connection is still being answered (pipelined behind an MCP event stream, say), finished or not, drops the connection with no answer, so no refusal is written into that response or waits behind it. 64 KiB is far above what the UI, the agent or an MCP client sends (under 2 KiB) with a proxy's own fields added, above what nginx passes by default (32 KiB in all), and the size of the buffer uvicorn already holds for a body the app has not read. Cloudflare passes heads of up to 128 KB, so one between the two is refused here, which only a client sending that much meets.
- **Time for a head.** A connection has 10 s (`header_limit.HEADER_TIMEOUT_S`) from when it opens, and again from when its last request has been received whole and answered, to deliver the next request's head whole. One that has not is closed without an answer, whether it sent nothing, part of a head, or a byte at a time. The time stops when the head is complete: the body then has its 60 s (above), and a response in progress, an MCP event stream held open included, is never timed by it. After a response, uvicorn's keep-alive timeout still closes a connection that sends nothing within 5 s (`serve.KEEP_ALIVE_S`, uvicorn's default); it alone was not enough, because uvicorn arms it only after a first response and the first byte that arrives cancels it.
- **One request ahead.** While a request is queued behind the one being answered (pipelined), the server parses and reads nothing more on that connection; what has arrived waits unparsed. uvicorn alone parsed every request a read held and queued them all. The piece a chunked body ended in is the one place a second request can complete before the parse stops; the connection then takes no more requests: those taken are answered, the newest with `Connection: close`, and the rest is discarded unanswered.
- **A refusal by the parser.** uvicorn answers malformed bytes, in a request's head or its body, with `400` and closes at once, in front of any earlier answer still owed: a chunked owner write followed in one write by a request with a malformed chunked body committed, and its client got only the `400`, on plain uvicorn as on this server before #132's fourth round. One rule now: uvicorn's `400` is written only when the refused request is the only one the connection owes an answer for. Otherwise, wherever the malformed bytes fall (in place of the next head, inside a head, inside a body, behind a second valid request), the connection takes no more requests, the refused request is dropped without running, and every earlier answer is sent in order, the connection closing after the last. That last answer carries `Connection: close` if it has not started; one whose head has already gone (a streamed answer) finishes its frame, and the connection closes at its end. Nothing more is read meanwhile: uvicorn resumes reading whenever a request being answered asks for its body, and the server holds that back.
- **A client that stops reading** (`header_limit.STALL_TIMEOUT_S`, 60 s). uvicorn pauses a response once 64 KiB of it is waiting to be sent; one that stays paused for 60 s, the client taking none of it, is dropped (the connection is aborted), and so is a connection the server has closed whose client takes nothing of what it still holds for 60 s (a close otherwise waits for a flush that never comes). A client has to take 48 KiB in that time, under 1 KB/s, for a response to resume. An MCP event stream the client reads is never paused, so never dropped, however long it is held. Static files need no credential, so before this a client could ask for one and hold the connection and the response's task for ever.

The image runs with uvicorn's WebSocket support off, since the app serves none, so no request leaves the HTTP protocol these limits belong to. `python -m app.serve` is uvicorn's own command line with six settings pinned: one worker, no reloader, the parser above, no HTTP/2, no WebSocket and the 5 s keep-alive. Every other setting it takes from its options or from the environment as `uvicorn` did when it was the `CMD`: `UVICORN_FORWARDED_ALLOW_IPS` (or `FORWARDED_ALLOW_IPS`), `UVICORN_PROXY_HEADERS`, `UVICORN_ROOT_PATH`, `UVICORN_LOG_LEVEL` and the rest, so a deployment that set them needs to change nothing. `UVICORN_WORKERS`, `UVICORN_RELOAD`, `UVICORN_HTTP`, `UVICORN_HTTP2`, `UVICORN_WS` and `UVICORN_TIMEOUT_KEEP_ALIVE` are ignored, as `UVICORN_HOST` and `UVICORN_PORT` were before (the `CMD` names both). `UVICORN_LIMIT_CONCURRENCY` still applies; see below for why it is not set. The development command (`uvicorn app.main:app --reload`) runs without these limits. Each has tests in `test_header_limit.py`, in process for how bytes are counted across reads, and against the image's server on loopback.

Measured at `7063421` against a loopback uvicorn 0.54 (macOS, one run each). Before: httptools took 8 MiB of one unfinished header and the worker grew by 119 MiB (h11 refused it past its 16 KiB with `400`); a connection that sent nothing, and one that sent a header a byte every 2 s, were both still open after 75 s, on both parsers. 1,000 connections that had sent nothing cost the worker 6 to 7 MiB, and 1,000 holding 60 KiB of unfinished head each 71 MiB (h11: 22 MiB, refusing them all). With the limits, the 8 MiB header was refused with `431` once 64 KiB of it had arrived (the worker grew by 0.3 MiB), and the other two were closed at 10 s; 1,000 connections holding 60 KiB each, under the limit, still cost 70 MiB, but for 10 s at most. Twenty connections that each sent 64 KiB of pipelined requests and read nothing grew the worker by 78 MiB on plain httptools and by 8 MiB with one request ahead; a client that asked for a 64 MiB static file and read nothing was still holding it after 75 s on plain httptools, and was dropped at 60.6 s. The UI in a browser, before and after 12 s idle, an agent's check-in and a full result set, a 1,000-row import and an MCP session with its event stream held open for 30 s were served as before (#132's PR has the run). No concurrency limit is set: uvicorn's `--limit-concurrency` counts open connections, idle ones included, and answers `503` to every request past it, so at a limit of 32, 32 connections that had sent nothing turned `/health` into `503`. It would give whoever holds the connections the server, without bounding what they cost.

**Left to the reverse proxy or tunnel** (`docs/deployment.md`, "What the proxy holds", gives each with how to check it is in force; v0.2 spec §8 holds the detail). The server's limits bound what one connection and one body cost and for how long, not how many there are or whose they are. The body budget is shared by every client, so one that keeps it full (16 MiB sent again each minute, from eight connections or more) holds every other body off with `503`, small ones included; the agent retries a `503` on its back-off. Each connection costs the worker about 7 KiB, and up to 64 KiB of head for at most 10 s, or one queued request and a read, or a paused response for at most 60 s, plus the kernel's socket buffers, and nothing in the server bounds their number. A client that reads a response at just over 1 KB/s holds it as long as it keeps reading. The server cannot tell clients apart behind a proxy, whose address is all it sees. A proxy or tunnel in front of the server is expected to:

- limit each client's request rate and requests in progress (nginx's `limit_req` and `limit_conn`; `limit_conn` counts a connection only once its whole head has been read, so it does not count silent or trickling sockets);
- read each request's head itself, within a size and a time limit of its own, and send it on whole, so a slow or oversized head ends at the proxy and never takes a connection to the server; nginx has no per-client limit on sockets without a complete head (they are bounded by its header timeout and its worker's connection limit), so a per-client cap on sockets, where one is wanted, is the firewall's, on the host clients connect to directly: it counts by source address, which behind a tunnel or another proxy is that hop's, shared by every client;
- close idle client connections, and keep its own idle connections to the server open for less than the server's 5 s keep-alive, so it never reuses one the server is closing;
- read the server's responses at its own speed and bound how long a client may leave one stalled (a timeout between writes, such as nginx's `send_timeout` or Caddy's `write_idle`), so a slow reader holds the proxy's buffer, not the server's; never a timeout on the whole response (Caddy's `write`) or a minimum rate where `/mcp` is served, since either ends a healthy MCP event stream, which the server keeps alive with a comment line every 15 s;
- pass a body of at least 2 MiB (nginx's default `client_max_body_size`, 1 MiB, is smaller than a full result set or a full import), preferably buffering it so that the server receives it at the proxy's speed, and give a client at least the time its slowest legitimate upload needs.

`503 UNAVAILABLE` means the request was not served and wrote nothing, and the same request may succeed if retried. Agent routes return it when the database refuses a write (§4.1): "Database busy; retry the request" for a lock, "Database unavailable; retry later" for anything else, which needs the owner. Any route returns it while the bodies being received fill the budget (above). `500 INTERNAL_ERROR` is a failure the server caught before committing anything (§4.6).

### 4.4 Free-IP and allocation semantics

An IP is **free** iff all of the following hold:
- within the subnet's usable range — network and broadcast addresses are never free (special case: /31 and /32 have no network/broadcast exclusion)
- not the subnet's gateway
- not within the DHCP pool (`dhcp_start`–`dhcp_end`), if one is set
- not within any reserved range
- no host record exists for it

Manual host creation (`POST /hosts`) only rejects the network/broadcast addresses — placing a host at the gateway, inside the DHCP pool, or inside a reserved range is deliberate and allowed.

`next-free` allocates the lowest free IP and creates the host record in a single transaction. The `UNIQUE(subnet_id, ip)` constraint is the backstop against races: if a concurrent writer claims the chosen IP first, allocation re-reads the free list and rolls to the next candidate (up to 5 attempts) rather than surfacing a conflict.

Gateway, DHCP, reserved-range, and allocated-address exclusions are represented as clipped, merged integer intervals. Utilisation counts interval lengths, and free-IP iteration skips blocked spans rather than materialising every address in a range.

### 4.5 Agent check-in and jobs

`POST /api/v1/agent/checkin` (agent token, §4.1). The request and response shapes live in `api/app/agent_protocol.py`, the contract the agent package is built against (v0.2 spec §5.7). It depends on the standard library and pydantic only.

```json
// request
{ "version": "0.2.0", "protocol": 2, "hostname": "scanner-20", "platform": "linux",
  "interfaces": [{ "name": "eth0", "cidr": "10.0.20.5/24", "mac": "02:00:00:00:00:05" }],
  "capabilities": [] }
// 200
{ "data": { "checkin_interval_s": 60,
            "jobs": [{ "job_id": "…", "subnet_id": "…", "cidr": "10.0.20.0/24",
                       "ranges": [{ "start": "10.0.20.1", "end": "10.0.20.99" }],
                       "methods": ["icmp", "arp", "rdns", "fdns"], "dns_servers": ["10.0.20.1"],
                       "timeout_s": 600,
                       "fdns": [{ "host_id": "…", "fqdn": "nas.home.arpa" }] }] } }
```

- **Rate limit first.** An agent may check in once every 10 seconds (`jobs.MIN_CHECKIN_GAP`; its own interval is 60). A check-in inside that gap is `429 RATE_LIMITED` before the body is looked at, and changes no row: not `last_checkin_at`, not the token's `last_used_at`, nothing in the change log. Inside the gap it is refused from the agent row loaded at authentication, with no write statement at all; check-ins that race are refused by the claim, a compare-and-set on `last_checkin_at` whose losing statements match no row. The agent waits `checkin_interval_s` and tries again.
- **The claim.** That compare-and-set is the check-in's first write, and it also requires the agent `active` and its token unrevoked: a disable, revoke or delete the owner commits after a check-in authenticated refuses it with `403` "Invalid agent token", and nothing of it is written. The order is fixed: a check-in whose agent row, as loaded at authentication, took its slot inside the gap is refused `429` from that row at once, with no statement at all, whatever the owner has committed since: a disable, revoke or delete that lands in that window is met by the agent's next request, which fails authentication with `403`. A check-in the loaded row lets through goes to the claim, which re-checks the agent's state and the token's revocation under SQLite's write lock: `403` if the owner's change has landed (even when another check-in has also taken the slot), otherwise `429` if one has. Nothing is served and nothing is written on any of them. The token's use (§3.9) is recorded in the claim's transaction, and the agent row is then read again whole, so the check-in's audit snapshots and `actor` carry the name and state as committed. Everything a check-in writes is that one transaction: if the database refuses a write, it is rolled back and the check-in gets `503 UNAVAILABLE` (§4.1).
- **Protocol first.** `protocol` is checked before anything else in the body, since another protocol may shape the rest differently. Anything but the integer `PROTOCOL_VERSION` (2; 1 until #100) is `409 PROTOCOL_MISMATCH` with a message naming both protocols; it issues no job, stores none of the body, and is recorded in the agent's `last_error`.
- **Then the fields** (§3.8). The first that fails is `422 VALIDATION_ERROR` "Check-in refused: <field>: <reason>", recorded in `last_error` the same way; the reported fields keep their earlier values. Unknown fields are ignored. `capabilities` (up to 16 tokens of `a-z0-9_-`) is checked and not yet used.
- **A good check-in** stores the reported fields and `last_checkin_at`, clears `last_error`, and returns at most one job.
- **Audit.** A check-in that changes `version`, `platform`, `hostname`, `interfaces` or `last_error` writes one `agent` update with `source="agent"` and `actor="agent:<name>"`, naming the changed fields in the summary and their values only in the snapshots. A check-in that changes nothing else is not logged (as `last_used_at` is not), and neither is issuing a job. An agent keeps only its newest 100 entries of its own (`source="agent"`); older ones are deleted when a new one is written, and the owner's entries are never touched. Together with the rate limit, that bounds what one agent token can add to the log.
- **Agent text stays out of assistant context.** `list_changes` over MCP replaces the values of `version`, `platform`, `hostname` and `interfaces` in every `agent` snapshot with a placeholder (`changes.assistant_view`), whoever wrote the entry; the field names, summary, source and actor stay. Owner REST (`GET /api/v1/changes`) shows them.

**When a target is due.** It is enabled, assigned to this agent, not under a live lease, and either a scan was requested after its last scan started (`scan_requested_at` > `last_scan_at`), or it has an interval and has never been scanned or its last scan started at least `interval_minutes` ago. Among due targets, a request no job has been issued for since it was made goes first; every other due target, a request already tried once included, goes by when a job for it last started (`last_scan_at` or `job_issued_at`, whichever is later), oldest or never first. A target whose jobs keep timing out therefore goes to the back each time and cannot starve the agent's others; a request still stands until a completed scan serves it.

**Leases.** Issuing a job sets `current_job_id`, `job_issued_at` and `job_methods` (the methods issued). The lease is live for 15 minutes (the 10-minute job timeout plus a margin); a target under a live lease is not issued again, and once it expires the target is due again. The write is a compare-and-set on the lease the check-in read, so two check-ins never lease one target twice. The same lease is recorded on the agent (`agents.current_job_id`, `job_issued_at`), and an agent whose lease is live gets no new job: it runs one job at a time. Because the record is on the agent, reassigning, disabling or deleting the target (or its subnet) mid-scan does not free an agent that is still scanning; nothing is sent to cancel a job. A reassigned target keeps its lease until it expires or its result arrives, so the new agent waits for that target only.

An accepted result set clears both copies of the lease (§4.6). Expiry clears neither: the next job issued overwrites them, so a late result for an expired lease is still accepted until then.

**The job.** `ranges` is the subnet's scan scope from `services/scans.scan_scope` (§3.10); a target whose scope is empty gets no job. `methods` are the target's, minus `arp` when the subnet is not on the agent's link. The subnet is on the agent's link when one reported IPv4 interface's network contains the whole subnet. A target left with neither `icmp` nor `arp` gets no job, and is not leased. `dns_servers` are the first three of the subnet's, in the order listed, or empty: three is `agent_protocol.DNS_SERVERS_MAX`, the most the agent asks per lookup, so a subnet that lists more, or holds a longer list stored before the owner API bounded it (§3.2), costs the answer nothing. `timeout_s` is 600.

**The names a job sends** (`fdns`, #20; `services/fdns.names_for_job`). Empty unless the job was issued `fdns`. Otherwise a host of the subnet is named only when its address is inside the scan scope the job's ranges are, and its FQDN (`hostname` and the host's domain override, else the subnet's domain; §3.4) is under the **subnet's own domain**: it ends with `.` and that domain, compared case-insensitively. That is v0.2 spec §7.2's invariant 5: a host whose FQDN is outside it, by its own override (`nas` with `example.com` in a `home.arpa` subnet) or a lookalike suffix (`evilhome.arpa`), or any host of a subnet with no domain, is never sent, so whoever can edit a hostname or a host's domain cannot make the agent resolve a name of their choosing. A sub-domain override (`lab.home.arpa`) is under it, and sent. The FQDN must also be a DNS hostname in the agent's rule (`agent_protocol.fdns_name`: `rdns_name`'s, §3.11, already lowercase), so a hostname with a space or an underscore, which the hosts service allows, is not sent; the name is sent lowercased. A job names at most 1,024 hosts (`fdns.FDNS_JOB_MAX`): those never asked first, then those asked longest ago (`asked_at`, set for every name a job sent once its result set is accepted, answered or not, so a batch that never gets a usable answer does not hold its place; Codex on #185), then by address, so a subnet with more is covered over several jobs (a full /20 in four). The bound is set by both requests a job shapes: the check-in answer (below) and the result set, whose answers must fit the 2 MiB body cap beside a full /20 of observations (§4.6). The lease keeps the pairs sent (`scan_targets.job_fdns`), which is how ingest knows what the job asked (§4.6). A target issued `fdns` with no name to send runs as any other job.

`cidr` is the subnet's in its canonical spelling (§3.2), at most 18 characters, whatever the subnet row holds: a subnet stored before #97 may hold any spelling `ipaddress` takes, a prefix padded with thousands of zeroes included, which the agent refuses past 64 characters, so such a subnet was never scanned.

**The answer fits the agent.** The agent reads at most 1 MiB of an answer and retries a larger one, so a job that made the answer larger would never run. The largest the server can build is a /20 target (the largest allowed) whose scope is split at every other address, issued every method, with three servers, whatever spelling of its CIDR and however many DNS servers the subnet stores, and a host at each of its 2,047 scanned addresses with an FQDN of 253 characters, of which the job names 1,024: 426,520 bytes, and 428,297 with every address in it, the CIDR written at its longest and 1,024 names of the longest host id and FQDN (`agent/tests/test_answer_limit.py`, which fails if either side's bounds move it past the limit). Before #20 the same answer without names was 104,978 bytes; a job naming every host of a /20 (4,094) would be about 1.4 MB, past the limit. Before the job's servers were bounded, the same subnet holding 65,000 of them sent 1,153,843 bytes; before the job's CIDR was canonical, the same subnet stored as `192.168.240.0/` with its prefix padded by 4,298 zeroes sent 109,276 bytes, past that bound, for a job the agent refused.

### 4.6 Scan results

`POST /api/v1/agent/results` (agent token, §4.1), one result set per job. Shapes in `api/app/agent_protocol.py`; the service is `services/results.ingest`.

```json
// request
{ "protocol": 2, "job_id": "…", "subnet_id": "…",
  "started_at": "2026-11-16T10:00:00Z", "finished_at": "2026-11-16T10:00:12Z",
  "complete": true, "liveness_complete": true,
  "observations": [{ "ip": "10.0.20.7", "mac": "00:1b:21:3a:4f:9c", "rdns_name": "nas.home.arpa" },
                   { "ip": "10.0.20.8", "rdns_no_name": true },
                   { "ip": "10.0.20.9" }],
  "fdns": [{ "host_id": "…", "addresses": ["10.0.20.7"] }], "error": null }
// 200
{ "data": { "accepted": 1, "rejected": [{ "ip": "10.0.20.150", "reason": "out_of_scope" }] } }
```

- **Body.** At most 2 MiB, the cap on every request body (§4.3): a larger declared or streamed body is `413 PAYLOAD_TOO_LARGE`, refused before the agent token is checked and unparsed. A body with a declared length is read only after the token is checked. Not JSON, not an object, or a field that fails validation is `422` "Result set refused: <field>: <reason>", never quoting the value: `complete` must be a JSON boolean, both times must carry a zone and `finished_at` must not precede `started_at`, `observations` holds at most 4,096 records, `fdns` entries are `{host_id, addresses}`. `protocol` is an integer the server ingests (`agent_protocol.RESULTS_PROTOCOLS`, 1 and 2), and absent means 1, which carried none; from 2, `liveness_complete` is a required JSON boolean, never false while `complete` is true. Unknown fields are ignored. Refusals are not recorded on the agent: the agent logs them, and the lease runs out.
- **The credential, again.** Under SQLite's write lock, before anything is written, the agent must still be `active` and the token that authenticated the request still unrevoked. A result set that authenticated before the owner disabled, revoked or deleted the agent, or before a re-enrol exchange revoked its token, is `403` "Invalid agent token" and nothing is stored: the lease stays where it was, so a job issued under an old token runs out with its lease.
- **The job.** Accepted only while it is current on both copies of the lease: `job_id` equals the reporting agent's `current_job_id` and a target's `current_job_id`, whatever the target is assigned to now. Otherwise `409 JOB_NOT_CURRENT` and nothing is stored: the job was re-issued after expiry, the agent was given another, the target or its subnet was deleted, the token is another agent's, or a result set for the job was already accepted. A `subnet_id` that is not the job's is `422`. Accepting clears the target's `current_job_id`, `job_issued_at` and `job_methods` and the agent's `current_job_id` and `job_issued_at` in one transaction, each a compare-and-set on this job, so of two racing result sets one is accepted. It sets `last_scan_at` to the job's `job_issued_at`, records the duration, `complete` and `error` (§3.10), and leaves `scan_requested_at` alone, so a scan requested while the job ran is still due. The agent can be issued its next job at its next check-in.
- **Each record** is judged on its own and a bad one never costs the others. A record is rejected, with its `ip` quoted back when that is a short, ASCII, printable string (null otherwise: JSON can carry a lone surrogate that UTF-8 cannot), for: `invalid` (not an object), `invalid_ip`, `invalid_mac`, `out_of_scope` (outside the subnet's scan scope at ingest, another address family included), `duplicate` (already in this result set), `mac_not_issued` (a MAC from a job not issued `arp`), `rdns_not_issued` (a name, or `rdns_no_name`, from a job not issued `rdns`). A record carrying both a name and `rdns_no_name: true` is `invalid`, and so is one whose `rdns_no_name` is not a JSON boolean. What a job could collect is `job_methods`, the methods the server issued, not what the agent says it ran or a later check-in's interfaces. A rejected record is not stored. An `rdns_name` that is not a hostname is not a rejection: it is dropped, and the address is stored without it (§3.11).
- **Each result set is judged by the rule of its `protocol`** (#100). An agent of protocol 1 reporting a job leased before the server was upgraded is still ingested by protocol 1's rule, below; it is given no new job (§4.5).
- **Alive and dead.** Each accepted record is upserted `alive=true` with `last_seen_at` now. Only a result set whose liveness sweep completed, from a job issued `icmp` or `arp`, marks every other observation in the subnet's scope `alive=false`; an address the result set named, even in a rejected record, is not marked. From protocol 2 that is `liveness_complete: true`, whatever the PTR lookups did: a host that has left the network is marked dead by a scan in which no DNS server answered, or that had none to ask, or whose lookups the deadline cut short. In protocol 1 it is `complete: true`. A job whose liveness sweep did not complete only adds what it saw.
- **Names.** From a job issued `rdns`, a record's name (after sanitising) replaces the stored one. From protocol 2, a record without one clears the stored name only when it carries `rdns_no_name: true`, which the agent sends when a DNS server answered that the address has no name (`NXDOMAIN`, or a `NOERROR` without a PTR record whose authority holds the SOA of a zone that contains the name, or that carries no record at all); `complete` has no part in it. The agent reads a reply against its question (v0.2 spec §5.2, #144): a PTR record counts only at the question's name or at the end of the CNAME chain the reply gives for it, and one there is the name whatever else the reply holds; a PTR record at any other owner is never the name, and when the reply has none at the chain's end it makes the reply no usable answer rather than "no name" (#149). An SOA counts only for a zone that contains that name. A record with neither leaves the stored name, whatever the reason: no server gave a usable answer (silence, `SERVFAIL`, `REFUSED`, a malformed, truncated or mismatched reply, one longer than the 1,232-byte payload the query advertised or whose header claims more than one question or more than 32 records, neither of which is parsed, a referral, after a CNAME or not, as in a classless reverse delegation, a CNAME the reply leaves unresolved, a PTR record at some other owner with none at the chain's end, or an SOA only for zones that do not contain the name; the next configured server is asked after each), the lookup was cut off or never ran, or its name was not a hostname and was dropped. So a resolver outage, or a firewall that drops port 53, leaves every stored name as it was, and a stale one stays until a server answers again. The agent follows neither a CNAME nor a referral itself, so a subnet whose only DNS server does not recurse and answers with an alias it leaves unresolved (classless reverse delegation served elsewhere) reports "no DNS server gave a usable answer" on every scan, and a stale name there never clears. That is by design (#100), not a fault; the remedy is to point the subnet at a recursive resolver, or at a server that also serves the alias's target zone. Of the lookups without a usable answer, the job's error also counts those whose server sent a reply the agent refused unread, for its size and for its header's counts, in lookups, by count only, a limit that refused none left out, and after a timeout those of the lookups that returned (v0.2 spec §5.2, #164); a lookup a later server answered is not in those counts, and the counts are stored whole or not at all. The lookups a later server answered after such a refusal are counted apart, by limit in the same words, in a notice the error ends with (#170): it leaves the scan complete and the names as the answers make them, says that an earlier server's replies are costing a query each before they cost a name, and is the first part given up when the error would not fit the 500 characters stored. A scan with no refused reply has the error it had before. Both limits are the agent's and are not settings: the remedy is a resolver that sends minimal responses, or, behind a forwarder, the upstream that produces the PTR answer. In protocol 1, which could not tell those apart, a record with none clears it only when the result set is `complete`.
- **Forward-DNS answers** (`fdns`, #20; `services/fdns.store`). An entry is `{host_id, addresses}`, at most 32 addresses, at most 4,096 entries; a list or entry of another shape refuses the result set (`422`). An entry is stored only for a host the job was sent (the lease's `job_fdns`, read with the lease), under the name that was sent, and only while that host still exists, is in the job's subnet, is still at the address it had when the job was issued, and is inside its scan scope as read under the write lock: an entry for a host the job did not name, one whose addresses are not all IPv4 addresses, and a second entry for one host are dropped, and so is an entry for a host deleted, moved to another address (in scope or not) or excluded while the job ran. An edit of a host's address deletes its row in the same transaction (`hosts.update_host`), since the answer was judged against the old address; the next job asks again (round 1 of #185's briefed review). A stored entry replaces the host's row (`fdns_results`, §3.13), its addresses each once and sorted, `checked_at` now; an empty list records a name that does not resolve. A name the result set has no entry for got no usable answer from any DNS server, or was not looked up, and its answer stays as it was, as a stored PTR name does. Every name the job sent whose host is still there, in the subnet and in scope has its `asked_at` set to now, answered or not (a host asked for the first time and not answered gets a row with `asked_at` alone, which raises no finding). Dropped entries are not counted in `accepted` or listed in `rejected`, which are about observations. Then every row whose host no longer exists is deleted. The largest result set an agent sends, every address of a /20 with a MAC and a 253-character name, the longest error, and 1,024 answers of 32 of the widest addresses, is 1,942,467 bytes as the agent encodes it, under the cap; 2,048 answers would be 2,598,851, which is why a job names at most 1,024 (`api/tests/test_fdns.py`). The agent asks for A records only (v1 is IPv4-only), so a name with only AAAA records is a name that does not resolve.
- **Prune.** Every ingest deletes observations, in any subnet, unseen for 90 days.
- **The answer before the commit.** The `200` answer is built and UTF-8-encoded before the result set is committed, so neither step can fail for a stored result set. That covers the answer's construction and encoding, not its delivery: rendering and sending the response come after the commit, and an agent that loses the response gets `409` on a retry. Should the encoding fail, the transaction is rolled back and the answer is `500 INTERNAL_ERROR` in the error shape, logged server-side.
- **Database failures.** The lease release, the observations, the forward-DNS answers, the prunes and the token's use (§3.9) are one transaction. If the database refuses a write, it is rolled back and the result set gets `503 UNAVAILABLE` (§4.1): both lease copies still name the job, nothing is stored, and the same result set is accepted once the database is writable. A refused result set (`409`, `422`) writes nothing, the token's use included.
- **Nothing else.** Ingest never writes `hosts` and writes nothing to the change log.

### 4.7 Findings

Where what a scan saw and what the owner recorded disagree (v0.2 spec §5.5). Computed on read in `services/findings.py` from the subnet's hosts and observations, only for addresses inside its scan scope (§3.10): a host in an excluded range, or in an unscanned DHCP pool, raises none. Nothing is stored but dismissals (§3.12), and nothing is applied until the owner accepts it.

```json
// GET /api/v1/subnets/{id}/findings
{ "data": [{ "subnet_id": "…", "ip": "10.0.20.7", "type": "name_mismatch", "observed": "storage.home.arpa",
             "ip_int": 167777287, "host_id": "…", "dynamic": false, "proposed": { "hostname": "storage" },
             "fingerprint": "3f9c…" }],
  "total": 1 }
```

| Type | Raised when | `observed` | Accepting writes (`proposed`) |
|---|---|---|---|
| `unknown_host` | the observation is `alive` and no host is recorded at the address | the MAC, or empty | a new host: `mac`, and `hostname` (and `domain`, see Names) from the PTR name; `status` `active`, or `dhcp` when `dynamic` |
| `mac_missing` | the host has no MAC, the observation has one | the MAC | `mac` |
| `mac_mismatch` | both have one, and they differ | the MAC | `mac` |
| `name_missing` | the host has no hostname, the observation has a PTR name | the PTR name | `hostname`, and `domain` when the name is outside the effective domain |
| `name_mismatch` | the PTR name differs from the host's FQDN, case-insensitively | the PTR name | the same |
| `fdns_mismatch` | the subnet's scan target has `fdns`, the host's forward-DNS answer (§3.13) is for the name a job would send for it now (§4.5), and its addresses do not include the host's IP; a name that does not resolve counts | the addresses, sorted, joined with `, `, the first 12 and then `and N more`; or `unresolved` | nothing: informational. Accept is refused (`error`); dismiss it, or correct the host or its DNS record |
| `stale` | the host is `active`, the subnet has a scan target, and the host's `last_seen` (§3.4) is more than 30 days old | that `last_seen`, as an ISO-8601 UTC time, or `never` | `status` `offline` |

- **The key.** A finding is identified by `(subnet_id, ip, type, observed)`, and every finding carries all four. `ip_int` is the sort key, `host_id` the host at the address (null for `unknown_host`).
- **The fingerprint.** The key does not say everything an accept writes (an `unknown_host`'s name and status, a hostname that depends on the domain), so each finding also carries `fingerprint`, a digest the server computes from the key, `host_id` and `proposed`. Accept needs it; a later scan, a domain or pool edit, or a new host at the address changes it.
- **No MAC finding for a randomised MAC** (`mac_randomised`, §3.11).
- **Names.** Accepting a name makes the host's FQDN the PTR name. Under the effective domain (the host's override, else the subnet's), `hostname` is the part before it, nested labels included (`a.b.home.arpa` → `a.b`). Outside it, the bare domain included, `hostname` is the first label and `domain` the rest, as an explicit override in `proposed`: `nas.example.com` in a `home.arpa` subnet becomes `nas` + `example.com`, FQDN `nas.example.com`. A single-label PTR name is a relative hostname. `name_mismatch` compares FQDNs, so a PTR name outside the effective domain always differs.
- **Stale and never seen.** `last_seen` is the rule host responses use: the later of the value set by hand and the observation's `last_seen_at`, never `alive`. A host with neither is stale (`never`) only when both the scan target and the host record are more than 30 days old, so switching scanning on does not make every host stale. A subnet without a scan target raises no `stale`.
- **Dynamic.** An `unknown_host` inside the DHCP pool, possible only when the pool is scanned, has `dynamic: true` and is left out unless `?include_dynamic=true`.
- **Accept** takes each key with its `fingerprint`, recomputes the finding under SQLite's write lock and, only if it still exists with the same `observed` and `fingerprint`, writes `proposed` through the hosts service (`create_host`/`update_host`), whose validation and audit entry apply unchanged. Otherwise the record is `skipped` with reason `changed` and nothing is written; a key without a fingerprint is an `error`. A dismissed finding can still be accepted. The audit summary names the address and the finding type, never the hostname or MAC that came from the network: `host created at 10.0.20.7 in lab from scan finding unknown_host`, `host at 10.0.20.7 updated from scan finding name_mismatch`. The snapshots carry the values, as for any host write.
- **Dismiss** recomputes the same way and stores the key only for a finding that exists as listed (a fingerprint is checked if sent, and not stored). The finding stays hidden until its observed value changes. The audit entry's summary is a count (`2 scan finding(s) dismissed in lab`); the keys are in its `after`.
- **Forward DNS.** An answer for a name the host no longer has (renamed, or moved by a domain edit since) raises nothing until a job asks for the new one, and neither does any answer while the target does not have `fdns`. An answer can hold 32 addresses, so the observed value lists 12 and a count, which keeps it inside the 253 characters a key's `observed` takes (214 at most). Accepting one is refused with an `error` naming the type, and writes nothing: there is no host field to set from it.
- **Observed values are data.** A MAC comes only from a job issued `arp`; a PTR name is whatever a device calls itself, kept only if it is a valid hostname (§3.11), which says nothing about what it means; forward-DNS addresses are what a DNS server answered for a name the server chose.
- **Audit summaries.** What reaches a change summary depends on the path a value takes. Scan ingest writes no change entry (§4.6). Accepting a finding (here, and in the web UI's findings panel) names the address and the finding type, never the network's hostname or MAC. An MCP host write (`create_host` or `update_host`, the tools an assistant resolves a finding with) is an ordinary owner write even when the assistant copied its values from a finding's `proposed`: once written, a hostname is owner data, and the summary names the host by it as every host summary does (`host nas created at 10.0.20.7 in lab`), which `list_changes` returns. The owner chose this (#79); the `create_host` and `update_host` docstrings say so to the assistant.
- Over MCP, `list_scan_findings` lists findings a page at a time, read-only (§5.2), `fdns_mismatch` among them.

### 4.8 Agent enrolment

`POST /api/v1/agent/enrol` (v0.2 spec §4.2, §5.6, §5.7; `services/enrolment`) exchanges an enrolment token, presented as `Authorization: Bearer tlge_…`, for the agent's long-lived agent token. It is the only agent route reachable without a long-lived token, so it is not behind `require_agent` (§4.1). The body is `{protocol?, version?, hostname?, platform?}`, each optional; the three report fields are checked as check-in checks them (trimmed, printable, at most 40, 253 and 120 characters; unknown fields ignored) and `{}` is a valid body. `protocol` (#165) is the agent's `PROTOCOL_VERSION`, an integer; absent or null it is 2, the protocol of every agent release before it, which sent none, and it keeps that meaning whatever the server's protocol becomes. It is judged before the rest of the body and never stored. A server before #165 ignores it and enrols as before; adding it did not raise `PROTOCOL_VERSION`. The answer is `200 {"data": {"agent_id", "agent_token"}}`, the only response that carries the agent token.

- **What the exchange writes**, in one transaction: the enrolment token's `used_at` (a compare-and-set that requires it unused, unrevoked and unexpired at a time read once the exchange holds the write lock, after its body has arrived and its wait for the writer is over, and its agent not disabled, so two exchanges of one token cannot both pass and an owner's revoke, re-enrol or disable that commits first refuses it); the revocation of any agent token the agent held (re-enrol); the new agent token; the agent's `state` → `active`; and each report field sent (a field omitted or sent as null leaves the stored value as it is). It writes no `last_used_at` on either token: the new agent token's first is its first check-in's. It touches no scan target and no lease: the agent keeps its id, name and scan targets, and a job leased under the old token runs out with its lease (15 minutes), since the old token can no longer report it.
- **Audit**: three entries, or four on a re-enrol, all `source="agent"`, `actor` `agent:<name>`: the enrolment token `update` ("enrolment token tlge_… of agent X exchanged"), the old agent token's `revoke` ("… revoked (re-enrolled)") when there was one, the new token's `create` ("token tlga_… issued to agent X (enrolment)"), and the agent `update` ("agent X enrolled"). Summaries name the agent by its owner-given name and never a reported value; over MCP the reported values are withheld from the agent snapshots, as for a check-in's. The agent entry counts towards the cap on the agent's own entries (§4.5) and the exchange prunes to it in its own transaction; the token entries are not capped.
- **Refusals**, in the REST error shape, in this order: `429 RATE_LIMITED` while the throttle is full; `401 UNAUTHORIZED` with no bearer; `403 FORBIDDEN`, with one message, for any bearer that is not an enrolment token that can be exchanged now (unknown, used, expired, revoked, an agent token, the owner key, or one whose agent is disabled or deleted); `409 AGENT_TOO_OLD` or `409 AGENT_TOO_NEW` for an integer `protocol` lower or higher than the server's `PROTOCOL_VERSION`, the rule check-in applies, with a fixed message that names neither protocol (an agent of another protocol could check in to no avail; it is told which side to update before its token is spent, and enrols with the same token once they match); `422 VALIDATION_ERROR` for a body that is not JSON or not that shape (a `protocol` that is not an integer included), naming the field and never the value. The `409` and the `422` come before the claim and leave the token usable; `503 UNAVAILABLE` for a write the database refused, rolled back whole. The body is read only once the token is found usable. Nothing is written on any refusal. A `409` is remembered in process memory, per enrolment token (code, time), for the Agents page (`enrol_refusal`, §3.8, #175).
- **Throttle**: at most 10 attempts that did not enrol in any 60 seconds, across every caller (`enrolment.THROTTLE_ATTEMPTS`, `THROTTLE_WINDOW_S`). Every refusal but the throttle's own counts; an attempt that enrols does not. While the window is full every attempt is `429` before its token is looked up or its body read, a good token included, and a throttled attempt does not lengthen the wait. Global because the route sits behind whatever proxy the owner runs, where a client's address means nothing; in memory, since the server is one process, so a restart empties it. A token has 256 random bits, so the throttle does not protect it from guessing: it bounds the work and the log noise of the one unauthenticated agent route. Anyone who can reach the route can keep the window full and so hold enrolment off; an agent already enrolled is not affected.
- **The agent enrols itself** (#22; v0.2 spec §5.6): the container on its first start, from `IPAM_ENROL_TOKEN`, storing the agent token in its volume (`/var/lib/tlg-ipam-agent/token`, which then always wins over `IPAM_ENROL_TOKEN`), and the systemd install in `tlg-ipam-agent install`, which writes it owned by the service user, mode 0600. A refused exchange is retried after 13.5–15 minutes, never in a loop, so one agent with a spent token does not hold the throttle full. For `AGENT_TOO_OLD` and `AGENT_TOO_NEW` the agent and `install` say which release to install and that the token was not spent. The Agents page's guided install (#23, §6.2) renders both commands; an exchange by hand, with the agent token given as `IPAM_AGENT_TOKEN`, still works.

## 5. MCP server

### 5.1 Overview

The MCP server runs in the same FastAPI process, mounted at `/mcp` (Streamable HTTP transport), implemented with **FastMCP 4.x** (`fastmcp>=4.1,<5`, locked).

Tools are **hand-curated, not auto-generated** from the OpenAPI schema. Auto-generated REST-shaped tools are worse for Claude: generic names, HTTP-flavoured parameters, paginated CRUD responses instead of answers. Since Claude Desktop usage is the headline feature, the tools are first-class citizens.

**No sync risk:** REST routers and MCP tools are both thin wrappers over the same `services/` layer. Business logic (validation, allocation, audit logging) lives in services and is written exactly once.

```python
# mcp_server.py
from fastmcp import FastMCP
mcp = FastMCP("TLG-IPAM")

@mcp.tool
async def get_free_ips(subnet_id: str, limit: int = 20) -> dict:
    """Return unallocated IP addresses in a subnet. ..."""
    ...calls services.subnets.free_ips(...)

# main.py
mcp_app = mcp.http_app(path="/")
app = FastAPI(lifespan=mcp_app.lifespan, ...)
app.mount("/mcp", mcp_app)
```

Auth for `/mcp` is the same owner key (`API_KEY`), sent as a bearer token: `Authorization: Bearer <API_KEY>`. FastMCP enforces it through its own `auth=`: `OwnerKeyVerifier` in `auth.py` compares the token in constant time and grants the scopes `ipam:read` and `ipam:write`. `X-API-Key` is not accepted on `/mcp`, and an empty bearer is never the owner key (§4.1). With `PUBLIC_BASE_URL` set, an access token of an OAuth grant is accepted beside the owner key, which keeps working unchanged (§5.5).

**Write tools require the `ipam:write` scope** (#26), through FastMCP's own check (`require_scopes`): `add_reserved_range`, `delete_reserved_range`, `create_host`, `allocate_next_ip`, `bulk_create_hosts`, `bulk_delete_hosts`, `update_host`, `delete_host` and `request_scan`. Every tool is registered as a read tool or a write tool (`mcp_server.ipam_tool`, `ipam_write_tool`), with OAuth on or off. The owner key carries both scopes, whatever the settings. To a caller whose token lacks the scope a write tool is not listed by `tools/list`, and calling it answers `Unknown tool: '<name>'` (an MCP tool error over HTTP 200): FastMCP's behaviour, held by a test. An OAuth grant's token carries `ipam:write` only when the grant has `can_write` and `MCP_REMOTE_WRITES` is on (§5.5); otherwise `ipam:read` alone. Because a hidden tool looks missing, the server's `instructions` say that a read-only connection offers no write tools and that the assistant then tells the user what it would have changed, and the descriptions of the read tools that name a write tool (`list_device_types`, `list_scan_findings`) say that tool is absent on a read-only connection; nothing tells an assistant to retry a tool it cannot find.

A request refused for its credentials gets FastMCP's RFC 6750 response, not the REST error envelope; one refused for its size gets the REST envelope, before its credentials are looked at:

| Request | Status | Response |
|---|---|---|
| No `Authorization: Bearer` header (none, `X-API-Key` only, or another scheme) | `401` | Empty body; `WWW-Authenticate: Bearer`. With `PUBLIC_BASE_URL` set the header also names the protected-resource metadata, which is what starts a client's discovery: `Bearer resource_metadata="<PUBLIC_BASE_URL>/.well-known/oauth-protected-resource/mcp"`. `HEAD` is answered as `GET` is |
| A bearer that is not the owner key (nor, with `PUBLIC_BASE_URL` set, an unexpired access token of an unrevoked grant) | `401` | `WWW-Authenticate: Bearer error="invalid_token", error_description="…"` (and `resource_metadata` as above); JSON body `{"error": "invalid_token", "error_description": "…"}` |
| A body over 2 MiB, with or without a bearer | `413` | `{"error": {"code": "PAYLOAD_TOO_LARGE", "message": "…"}}`; `Connection: close` (§4.3) |
| A body that would take the bodies being received past 16 MiB, with or without a bearer | `503` | `{"error": {"code": "UNAVAILABLE", "message": "…"}}`; `Connection: close` (§4.3) |
| A body not received whole within 60 s (a chunked one before the bearer is looked at; one with a declared length once it is accepted) | `408` | `{"error": {"code": "REQUEST_TIMEOUT", "message": "…"}}`; `Connection: close` (§4.3) |
| A request line and headers over 64 KiB, before the bearer is looked at | `431` | `{"error": {"code": "HEADERS_TOO_LARGE", "message": "…"}}`; `Connection: close` (§4.3) |
| A connection that has not delivered a request's head whole within 10 s | none | The connection is closed (§4.3) |
| A response the client takes nothing of for 60 s with the send buffer full | none | The connection is dropped (§4.3) |

Both `/mcp` and `/mcp/` behave the same.

**`/mcp` is under the request-body cap (§4.3), not exempt from it.** A tool call carries its arguments in the body. The largest is `bulk_create_hosts` with up to 1,000 rows, the same batch as the REST import plus the JSON-RPC envelope: 1,000 rows with every field but `notes` at its maximum fit (`test_the_largest_mcp_bulk_call_is_served`), and rows with long notes need smaller calls (§4.3, and the tool's row in §5.2); every other tool takes one host, one range or a few ids. The cap is checked before the bearer, so an oversized body is `413` even without one, and so are the budget and the deadline (§4.3) for a body without a declared length; a refused bearer's `401` closes the connection, so a body sent after it is never read. The MCP SDK has a 4 MiB limit of its own, but it sits behind FastMCP's authentication and so bounds only clients that already hold a credential; `/mcp` is the route that becomes internet-facing with remote MCP (v0.2 M3), where a limit that holds before authentication matters most.

| `list_scan_findings` | Scan findings (§4.7), for one subnet or, with `subnet_id` omitted, every subnet (by subnet name, then address), optionally of one `type`, a page at a time: `list_scan_findings(subnet_id?, type?, cursor?)` returns `{next_cursor, returned, note, findings}`: at most 25 findings (`findings.PAGE_SIZE`), each at most 5,000 bytes as compact UTF-8 JSON (`findings.FINDING_MAX`), and a `findings` array of at most 45,000 bytes, brackets and commas included (`findings.PAGE_BUDGET`). Every value a finding carries has a length bound (subnet name 120, hostname 253, PTR name 253, domain 253, an `fdns_mismatch`'s observed value 214), and the largest finding they allow, with the names in control characters that JSON writes in 6 bytes each and the address at IPv4's widest (`192.168.255.254`), is 4,880 bytes; a host whose effective domain was stored longer before the domain limit is listed with `host_fqdn` null, never with a cut value, and its record keeps the domain. The work of one call is bounded too: at most 100 SQL statements (`findings.CALL_STATEMENTS`), each reading at most 250 hosts (with each one's forward-DNS answer, joined by its unique `host_id`) and 250 observations (`findings.SCAN_CHUNK`) and the dismissals at those addresses along an index on `(subnet_id, ip_int)` (created on start-up in an existing database), passing over no row it does not return (inside a scanned DHCP pool, observations are read only at its hosts' addresses); the scope each visited subnet needs reads only that subnet's excluded reserved ranges, along their own index, at most 100 of them (a subnet stored with more before that limit is read whole: the one read besides the subnet list whose cost follows what is stored, about 6 SQLite instructions a range), but the one that lists the subnets, which reads the order key of each subnet that can hold a finding (one with an observation, or with a scan target and a host); a subnet with neither costs nothing. That work is SQLite's, counted as the rows a statement reads or passes over, not the bytes it returns or Python's processing of them, so every read returns only the columns a finding uses, never a whole row: with `subnet_id`, the check that the subnet exists reads its id alone, since a subnet's notes have no length bound (#133). `next_cursor` is null once the listing has reached its end. Otherwise it is a position, and the assistant calls again with the same `subnet_id` and `type` and `cursor` set to it; the docstring says not to call the list complete until it is null. The cursor is the page's last finding when the page is full, or, when the call reached its statement bound, the last address the call examined, so a page can be short or empty and still carry a cursor. Such a cursor names a host's address, an observation's outside the DHCP pool, or a bound of the pool, possibly with nothing listed there; an unhosted address in a scanned pool is never read, so no cursor names one. The cursor and note come first so that a client that cuts a long result keeps them. The cursor's position is subnet name, CIDR and id, address, type, as an opaque string, so findings resolved between calls move nothing later in the order. A cursor that is not well-formed is refused (`cursor: malformed; …`); the check is of its shape only, because the cursor is unsigned and a well-formed position a client made up is read as a position. Each call reads the data as it is then: following the cursor sees each finding once while the data and the filters stay the same, but a finding that appears before the cursor after paging began, or a subnet renamed meanwhile, can be missed or repeated, and the docstring tells the assistant to start again without a cursor to see the current state. Both size bounds are set against what a client can hold: Claude Code keeps at most 50,000 characters of a text result and 25,000 tokens. An ordinary page is about 10,000 characters, and a page of 25 findings with every name and the domain at 253 ASCII characters is 44,057 characters of text with the note. A result carries the page twice, as a JSON text block and as structured content, so the whole MCP result is about twice the page; what a client counts against its limits, and its tokenizer, were not measured. Before #86 the issue's case (500 subnets holding nothing, between two that hold findings) cost 4,521 statements in one call; it now costs 17, as many as without them. `note` is on every page. Each finding is the REST one (key, `ip_int`, `host_id`, `dynamic`, `proposed`, `fingerprint`) plus `subnet_name`, `subnet_cidr` (in its canonical spelling, §3.2, as is the cursor's CIDR, whatever the subnet stores), and the recorded `host_name` and `host_fqdn` of the host at the address (null for `unknown_host`). `dynamic` findings are left out. Beside the list, `note` says that `observed` and `proposed` are what the network reported (a MAC, a reverse-DNS name, or the addresses a DNS server gave for a host's name), to be read as data; the docstring says so too, and tells the assistant to write one into a host only when the user asks. Read-only. There is no accept or dismiss tool: an assistant resolves a finding with `create_host`/`update_host`, which the fingerprint does not bind, and dismissal stays in the UI. |
| `request_scan` | Ask for a scan of one subnet now (`POST /subnets/{id}/scan`, §4.2), logged with `source = mcp`. Returns `{"scan_request": {subnet_id, scan_requested_at, next_request_after}}`, not the target. Inside the 15-minute cooldown, which every caller shares, the tool error says when to ask again, rounded up to the second so that asking then succeeds (the REST `429` gives the same time): `A scan of subnet lab was requested less than 15 minutes ago; request another after 2026-11-16T12:15:00+00:00`. A subnet with no scan target, a disabled one, or one with no agent is refused, and so is an unknown subnet. A write tool: when remote grants arrive (M3), it needs `ipam:write`. |

All MCP writes are recorded in the change log with `source = mcp`, and `actor` naming the grant when the caller is a linked client (§3.6), and each of the nine tools that write requires the `ipam:write` scope (§5.1). No tool creates, configures or lists agents, tokens or scan targets, and no tool can widen a subnet's scan scope (v0.2 spec §7.2, invariant 2). `request_scan` sets one column of a configured target, `scan_requested_at`, so the agent scans the scope the owner set sooner; it changes no setting and reveals none.

Set `TLG_IPAM_KEY` in your shell environment (e.g. `~/.zshenv`). The `mcp-remote` package handles Streamable HTTP → stdio translation for Claude Desktop.

- "What device is at 10.10.10.1?" → `list_hosts` with `q=10.10.10.1`

### 5.5 Remote MCP: the built-in OAuth server

Web MCP clients (Claude.ai, ChatGPT, Mistral) cannot send a static key, so with `PUBLIC_BASE_URL` set the server is its own OAuth 2.1 authorisation server for `/mcp` (v0.2 spec §6, M3). Without the setting none of this exists: the routes below answer 404 and `/mcp` takes the owner key alone.

**Supported web clients:** Claude.ai, ChatGPT and Mistral. **Gemini** can be linked but is unreliable: it is not supported and not recommended (#198). The server does not refuse it or treat it differently. What was seen, with its date, and what is only inferred from it are in [v0.2 spec §6.8](docs/v0.2-spec.md#gemini-is-not-supported-added-2026-11-27-198).

**`PUBLIC_BASE_URL`** is the server's public origin, `https://ipam.example.com`. Every URL the server publishes is built from it and never from `Host` or `X-Forwarded-*`. It is taken only in the one spelling the server would publish: `https://`, a lowercase host in its ASCII form, a port only when it is not the default. The server refuses to start (`config.load_settings`, as for `API_KEY`) with a path, a trailing slash, a query, a fragment, credentials, whitespace, an upper-case letter, `:443` or port 0, in one fixed message that repeats nothing of the value. Plain `http://` is taken only for `localhost`, `127.0.0.1` and `[::1]`, to test on one machine. Empty is unset.

**`MCP_REMOTE_WRITES`** (#28, v0.2 spec §6.5) decides whether a linked client may write. `true` or `false`, in any case; unset or empty is `false`, the default. Any other value (`1`, `yes`, `on`, a value with a space) stops the start, in one fixed message that repeats nothing of the value, rather than being read as either. It is read once, at start (`config.load_settings`), and handed to the OAuth provider, from which both of its rules take it:

- **The token rule** (`services/oauth.grant_scopes`): a grant's token carries `ipam:write` only while the grant has `can_write` and the setting is on, judged each time a token is loaded (the bearer check on `/mcp`, the code exchange and every refresh). Scopes are never stored, so turning the setting off (a restart) takes write access from every grant at once, with no relink, and a refresh keeps working with `ipam:read`; turning it on gives none to a grant linked read-only. A grant linked read-write writes again once the setting is back on: `can_write` is the owner's choice, kept. One link is stopped by revoking it on the **Linked clients** page (§6.2; `POST /api/v1/linked-clients/{id}/revoke`, §4.2, #30); leaving the setting off stops every read-write link writing at once, and the page then shows a link made read-write as read-only.
- **The link window** (`link_window.writes_may_be_allowed`): a window may be opened for a read-write link only while the setting is on, and `GET /api/v1/link-window` says which (`remote_writes`, §4.2). A window lives in process memory and the setting is read at start, so no window outlives the setting it was opened under: turning it off is a restart, which ends the window and its requests.

Without `PUBLIC_BASE_URL` the setting changes nothing. The owner key carries both scopes either way.

| Route | Purpose |
|---|---|
| `GET /.well-known/oauth-protected-resource/mcp` | RFC 9728: the resource is `<PUBLIC_BASE_URL>/mcp`, its authorisation server `<PUBLIC_BASE_URL>/` |
| `GET /.well-known/oauth-authorization-server` | RFC 8414: issuer `<PUBLIC_BASE_URL>/`, the three endpoints below, PKCE `S256`, scopes `ipam:read` and `ipam:write` |
| `POST /mcp/register` | Dynamic client registration (RFC 7591). Only while a link window is open |
| `GET`/`POST /mcp/authorize` | The authorise endpoint the owner's browser is sent to. Only while a link window is open |
| `GET`/`POST /mcp/consent` | The consent page the authorise endpoint sends the browser to, and its form: the owner types the link code. Answers while a window is open, and says why not otherwise |
| `POST /mcp/token` | Code exchange and refresh. Always answers |

Authentication is FastMCP's `MultiAuth`: the OAuth provider (`oauth_provider.IpamOAuthProvider`, over `services/oauth`) with the owner-key verifier beside it. A bearer is tried as an access token first, and only a value in the form the server issues is looked up (§3.16), so the owner key costs no database read.

**The link window** (v0.2 spec §6.3). Linking a client is opened by the owner from the private UI (`POST /api/v1/link-window`, §4.2), which gives the one-time **link code**: 10 characters from an alphabet with no `0`, `O`, `1`, `I`, `L` or `U`, held only as its SHA-256 in the server's memory and compared in constant time. The window lasts 10 minutes, one at a time (opening another replaces it), and ends on the first link, or when the owner cancels or replaces it: no wrong code closes or shortens it. Only while one is open does the server take registrations and authorise requests; outside one both answer `403` before anything of the request is read, the first with `{"error": "access_denied", "error_description": "…"}` and the second with one plain sentence for the browser, and nothing is stored. A registration neither closes nor uses up a window (a client may register twice and link with the second), and a client registered in one window can authorise in a later one. The window and the requests pending in it are process memory: a restart cancels a link in progress and nothing else, and every end of a window, and every opening, drops the pending requests. Cancelling or replacing waits for an approval in flight, so the owner's answer is true of what happened, and no grant follows it. A window may allow writes only once remote writes exist (#28); until then `can_write: true` is refused and every grant is read-only.

**Wrong codes.** The fifth wrong code typed for one authorise request ends that request (the client starts again); the window stays open, and the right code links whatever wrong codes other requests have had. Guessing is bounded by the code (30¹⁰ ≈ 5.9 × 10¹⁴ values) against what the server can take in ten minutes: about 1,040 wrong codes a second at most on the machine it was measured on (spec §6.3), a chance of about 1 in 10⁹ a window. The owner sees the window's `wrong_codes`, and the change log one entry a window, at its first wrong code (`link_window` / `wrong_code`, `source="oauth"`), written only while the window is current, so never after its end. An open window is not an approval attempt: while one is open an outsider can still push the owner's pending request out of the 32 held, or reclaim the owner's client's unlinked registration at the cap (§3.14), as often as it likes, and each time the owner sees it and starts the client again. The first takes at most 32 authorise requests on any one registration (one, when the store is already full and the owner's request is the oldest); the second as many registrations as there are free places, plus the reclaimable ones older than the owner's client's, plus one (at most 50 less the linked places; one, from a full registry, when the owner's is the oldest reclaimable). #190 decided to spare no registration for its pending request: as a preference it raises the cost only where the second route is the cheaper, to at most the first's 32 requests, which was judged too little; as a rule it would let 32 pending requests of an outsider's refuse the owner's client a registration (v0.2 spec §6.3). A per-client request rate in front of the server is what bounds such a flood (§4.3).

**Consent** (`/mcp/consent?txn=…`). The page shows, in this order: **the host the code is sent to**, in large type (the host of this request's validated `redirect_uri`, parsed, in ASCII form, so an internationalised name reads `xn--…`; plain `http` to a loopback address is said to be a program on the browser's computer); the name the client gave, as the client's claim and not the server's words: the **unverified** label first, then "The client calls itself" and the name in quotation marks, not in bold and in the muted colour ("no name this server keeps" when none was kept, §3.14; the name holds no character that could close the quotation or spell a host); the access (read-only, or read and write); and the code field, with how many wrong codes this request may still have and the minutes left. It is built from fixed templates with every inserted value HTML-escaped, loads nothing (`Content-Security-Policy: default-src 'none'`, its stylesheet allowed by hash), cannot be framed (`frame-ancestors 'none'`, `X-Frame-Options: DENY`), is not cached, and sends the client no referrer. The form carries a token bound to the request (an HMAC under a key drawn for the window), and a post whose `Origin` is not `PUBLIC_BASE_URL` is refused; neither refusal checks or counts a code, and nor does a value that is not in the code's form (ASCII only; case, spaces and hyphens are ignored). The right code approves the request (`services/oauth.approve`: the grant, the code, the audit entry), closes the window and sends the browser back to the client with `303`. Every other answer is a page of the server's own, never a redirect to the client: no window (`403`), a request ended by its five wrong codes (`403`), a request no longer pending (`410`), a refused form (`403`), a wrong code (`403`, the form again), not a code (`400`), and **start again from the client** (`409`) when the client's registration was reclaimed while the request waited, or turned 24 hours old unlinked (§3.14), which links nothing and leaves the window open, as does a grant the database refuses (`503`); an approval that fails otherwise ends the window (`500`, `ended: failed`). **Do not link** drops the request and leaves the window open.

**Registration** (while open) takes only redirect URIs that are `https` with a host, or `http` to `localhost` or a loopback address (an IP literal in `127.0.0.0/8`, or `[::1]`). Any other URI (plain `http` to another host, `javascript:`, a custom scheme, one with credentials or a fragment, one over 2,048 characters), or more than 16 of them, refuses the whole registration: `400` `invalid_redirect_uri`, naming the URI by its place in the list. The declared name is sanitised (§3.14) and the answer's `client_name` is the stored one, absent when none was kept. Registrations never linked are deleted at 24 hours (§3.14), before the cap is counted. The 51st registration takes the place of the oldest with no unrevoked grant (§3.14); when all 50 are linked it is refused, `403` `access_denied`, until the owner revokes a link. A confidential client's secret is stored as its SHA-256 only (§3.14); the answer gives it once, with `client_secret_expires_at` 0 and `Cache-Control: no-store`, and says what was registered where that is less than what was sent.

**Authorise** (while open). The request's `redirect_uri` must be one the client registered, compared whole, with one exception: a registered `http` URI on a loopback IP literal matches the same address, path and query on any port, since a local client listens on a port it is given when it starts. `localhost` by name and every `https` URI match only as registered. An RFC 8707 `resource` that is present and is not `<PUBLIC_BASE_URL>/mcp` (scheme and host compared without regard to case, one trailing slash ignored, nothing else) is answered `invalid_target` at the client's redirect URI, and nothing is held; absent, it is accepted. A request that passes is held in memory (at most 32, each for 10 minutes; a restart drops them) and the browser is sent to `<PUBLIC_BASE_URL>/mcp/consent?txn=…` (above). Approving it (`services/oauth.approve`, the consent handler's call) records the grant with the redirect URI as authorised, port included, and issues the code.

**Tokens.** A code lasts 5 minutes and is single-use; an access token 1 hour; a refresh token 30 days and is rotated on use (not in its first five minutes, below). A token request is authenticated first (`oauth_provider.HashedSecretAuthenticator`): a confidential client must present its secret the way it registered to (in the form for `client_secret_post`; in `Authorization: Basic` for `client_secret_basic`, where the client id may be in the header alone), which is hashed and compared in constant time; a public client presents none. A missing or wrong secret, or an unknown client, is `401` `invalid_client` before the code or refresh token is looked at, so both stay usable by the right secret. Each exchange is decided under SQLite's write lock, and a code is claimed with a compare-and-set. **A refresh token presented again within 60 seconds of its rotation** is a retry (a lost answer, two requests at once) and gets the same pair the rotation gave, again, with the access token's remaining time; **presented later, it revokes the whole grant**, which deletes its tokens and is audit-logged (§3.6). A retry can be answered again, with only hashes stored, because a replacement is derived and not drawn: `HMAC-SHA256` of the presented token under a random salt on its row (§3.16), which neither the database alone nor the token's holder alone can compute. So a grant has one chain of refresh tokens, and two holders of one token cannot each keep a chain of their own: the second to refresh, more than a minute after the first, revokes the grant. **A refresh token is not rotated in its first five minutes**: presented younger, it is answered `200` with the pair it was issued in and nothing is written, which is what bounds the table (§3.16). No client meets an error for refreshing often. A grant's token carries what `MCP_REMOTE_WRITES` and the grant's `can_write` allow now (above), whatever was asked; the answer's `scope` says so. `resource` is not checked at the token endpoint.

Refusals on these routes are OAuth's own shapes, not the REST envelope (§4.3): `{"error": "<code>", "error_description": "…"}` from the token (`400`; `401` for `invalid_client` and `invalid_grant`), register (`400`, `403`) and authorise endpoints, or a redirect to the client's validated redirect URI carrying `error` and `state`. Three answers there are in the REST shape: a body over the cap, budget or deadline (§4.3), which is refused before the route; a write the database refuses on the register or token endpoint, `503 UNAVAILABLE` with nothing spent; and the 404 of an unserved `/.well-known/` path.

A grant's token is a credential for `/mcp` and nothing else: the REST API, the backup and the agent routes refuse it.

**What is published** (v0.2 spec §6.7, §8; `docs/deployment.md`). A tunnel or reverse proxy in front of the server publishes `/mcp` (with or without the trailing slash), `/mcp/authorize`, `/mcp/token`, `/mcp/register`, `/mcp/consent`, `/.well-known/oauth-authorization-server` and `/.well-known/oauth-protected-resource/mcp`, each matched exactly. The SPA, every `/api/` route (the link window's among them), the backup and `/health` stay private, and `/api/v1/agent/*` needs to be reachable by agents only. The server does not enforce this split: it serves everything on one port to whoever reaches it, with each route's own credential as the only other guard (the SPA's files, `/health` and the API docs have none), so the proxy is what keeps the private paths private. A proxy that normalises a path before matching it and forwards the original does not: the server resolves no dot segment, so such a path can match a published one and reach an `/api/` route (spec §8).

**SSO or MFA** is the operator's access proxy in front of `/mcp/authorize` and `/mcp/consent`, which only the owner's browser visits; the server has no OIDC support and nothing to set. The other five are requested by clients, which cannot complete an interactive login, and pass through untouched. The login guards the making of a link, not a link already made. Through it, the consent form's post must carry no `Origin` but `PUBLIC_BASE_URL` (above): an access proxy that serves the page under another host, rewrites `Origin`, or adds `Referrer-Policy: no-referrer` (with which a browser sends `Origin: null`) gets the form refused, and the page's Content-Security-Policy blocks what a proxy injects into it.

**Ending links.** One link is ended by revoking it on the **Linked clients** page (§6.2; `POST /api/v1/linked-clients/{id}/revoke`, §4.2, #30): its codes and tokens are deleted, so the client's next request is refused. There is no OAuth revocation endpoint, so removing a connector in the client revokes nothing here. The server also revokes a grant itself when a rotated refresh token is reused (above), and for no other reason. **A link never completed** (#190), approved by the owner but whose client never exchanged its code before the code's five minutes ran out, is left for the owner: it holds no token and can get none, **Linked clients** marks it (`never_completed`), and its registration keeps its place among the 50 while any link of that registration is unrevoked: revoking the marked link frees the place only when the registration holds no other unrevoked link, which the page says from the list (v0.2 spec §6.6). The server does not revoke it: an unexchanged code is no sign of theft, revoking changes nothing a client can do, and freeing the place in time for the cap would mean revoking from a registration, which would let a caller with no credential write the change log (v0.2 spec §6.6). Two settings stop every link at once and end none: leaving `MCP_REMOTE_WRITES` off stops every link writing, and each still reads; starting without `PUBLIC_BASE_URL` refuses every grant's token and removes the OAuth routes, while the grants stay stored, listed and revocable, and those not revoked work again once it is set, a read-write one writing if the setting is on then. Changing `PUBLIC_BASE_URL` or `API_KEY` revokes no grant. With Compose, a change to either setting in `.env` is applied by `docker compose up -d`; `docker compose restart` keeps the old values.

Whether a token is open, and its time left, come from the server's `expires_in_s` (§3.9), counted down from when the list was requested by the browser's monotonic clock (`performance.now()`), never its wall clock, so a browser clock set wrong or stepped neither drops a live token nor keeps an expired one, and an answer slow to arrive is not shown with more time than it has. The countdown is scheduled on its own, apart from the 30-second refresh: a token leaves the page when its time runs out, whether or not a refresh succeeds. **Suggested scans**, above that, lists `GET /scan-targets/suggestions`: "Scan *subnet* *CIDR* with *agent*?", with **Scan**, which creates the subnet's scan target for that agent with the server's defaults (`POST /scan-targets` with the subnet and the agent alone: `icmp`, `arp`, `rdns`, the DHCP pool left out, on request only) and then asks for one scan (`POST /subnets/{id}/scan`), saying which of the two failed if one does, and **Not now**, which sets the offer aside while the page is open. Nothing is set up or scanned until the owner clicks. **Add agent** names the agent and then shows the guided install (spec §5.6): its `tlge_…` enrolment token once, with when it expires, and two tabs, each with its prerequisites and its commands, pinned to the server's version (`GET /health`; a version that is not a PEP 440 release version in normal form, or none, gives `<version>` and a note instead of a guessed artefact name). **Container**: `docker run -d --name tlg-ipam-agent --restart unless-stopped --network host --cap-add NET_RAW -v tlg-ipam-agent:/var/lib/tlg-ipam-agent -e IPAM_URL=<this origin> -e IPAM_ENROL_TOKEN=tlge_… ghcr.io/deusmaximus/tlg-ipam-agent:<server version>`. **systemd**: `sudo python3 -m venv /opt/tlg-ipam-agent`, `sudo /opt/tlg-ipam-agent/bin/pip install https://github.com/DeusMaximus/TLG-IPAM/releases/download/v<version>/tlg_ipam_agent-<version>-py3-none-any.whl` and `sudo /opt/tlg-ipam-agent/bin/tlg-ipam-agent install --url <this origin> --enrol-token -`, which asks for the token shown above: the token is never an argument. No command holds an agent token (`tlga_…`), which the page never sees, and only the container command holds the enrolment token. `web/src/utils/install.test.js` reads the spec's two tables and holds every rendered command to their shapes. The commands use the page's origin only when it is `https`, or plain `http` on a loopback host (the agent's own rule for `IPAM_URL`, `install.agentServerUrl`); a page served over plain `http` from any other host gets `https://<server>` in its place and a warning, so no command it shows sends a token across the network in clear. On such a page the Add agent form and the re-enrol confirmation say, before the token is issued, that the server's answer will bring the enrolment token to the browser in clear, and still issue it when the owner goes on; the steps after say that it has crossed, and that the agent token, which the exchange returns, crosses only over a plain-`http` exchange, which the commands never make. The same rule (`install.agentServerUrl`) decides which pages are warned at every step (#92). The token lives only in that dialog: nothing closes the dialog while the create request is in flight, a backdrop click does not close the token step, the list reloads from `GET /agents` (which never carries a token), and once the dialog closes nothing on the page can show the token again. Row actions: Disable / Enable (`PUT` `enabled`), Revoke (enabled while the agent holds a live token, its agent token or an enrolment token it has not exchanged; with a confirmation that says a revoked token cannot be reissued, so the agent is re-enrolled for a new one), **Re-enrol** (disabled for a disabled agent, which the server refuses; a confirmation, then `POST /agents/{id}/re-enrol` and the same guided install with the new token, the same protections, and in each tab the commands that remove the old token from a host that still holds it first: `docker rm -f tlg-ipam-agent` and `docker volume rm tlg-ipam-agent`, or `tlg-ipam-agent uninstall`), Delete (with a confirmation naming how many subnets are left unassigned)
- **Linked clients** (`/linked-clients`, v0.2 spec §6.3, §6.6, #30) — the web assistants linked through the built-in OAuth server, and **Link a client**. The page's intro names the three supported web clients (§5.5): Claude.ai, ChatGPT and Mistral. Gemini can be linked but is unreliable, is not supported and is not recommended; the page does not treat a link from it differently. Without `PUBLIC_BASE_URL` the page says remote MCP is not configured, what to set, and that `/mcp` takes the API key alone until then; **Link a client** is disabled, and links made while it was set are still listed, with a note that they do not work while it is unset (their tokens are refused), and can be revoked. The list is a table: the **redirect host** first and largest (monospace); under it, smaller and muted, the client's name as its own claim, as the consent page shows it: an "unverified" tag, then "calls itself" and the name in quotation marks and italic, never bold, or "no name this server keeps" (the consent page's words), or "registration deleted", and the link's short id (the start of the `grant-id:` actor its MCP writes carry); the access (read-only, read and write, or "read-only now" with a note for a link made read-write while `MCP_REMOTE_WRITES` is off); when it was linked; **Last contact**, with a note that a client contacts the server on its own, so it is not use, and under it, for a link the server marks `never_completed` (#190), a note that, as of that list, it was never completed (the code from the approval expired without the client exchanging it), so it holds no token and cannot get one, with a pointer to refresh to confirm (an exchange finishing at that moment shows on the next list), never worked out in the page from the times; and what revoking it does to the place, from the list alone (its `client_id` among the unrevoked links): it frees the registration's place when no other unrevoked link of that registration is listed; frees none when one is; and none is held when the registration is gone. The note is kept short and advises linking again in no case (`docs/deployment.md` says when to); and **Revoke**, which asks first (its tokens stop working at once, the client's next request is refused, it must be linked again with a new code). Revoked links are listed under **Recently revoked** (the newest 20) with when. The page refreshes the list and the window state every 15 s. **Link a client** opens a dialog: what a link window is and that it must be open before the URL is entered in the client (some clients, ChatGPT for one, register at once); the "Allow this client to make changes" checkbox (`.tlg-check`, off) only when the window state's `remote_writes` is true, else a line that the link will be read-only; and **Open link window**. The opened window shows the link code in two groups of five, the URL to give the client (`mcp_url`, with a copy button), the steps (add a custom connector with that URL, connect, check the host on the consent page and type the code), and a countdown from `expires_in_s` by the browser's monotonic clock from when the answer was asked for, never from `expires_at` ("Closing…" at zero until the server says it closed). The code is held in the dialog's state alone, never in storage or the URL: no window the dialog opened is left open once the dialog no longer shows its code: closing it while its window is open cancels the window, so does leaving the page, and a dialog dismissed while its open request is in flight cancels that window when the answer arrives; each of these names the dialog's own window (`DELETE /link-window?window_id=`), so a window that replaced it, from another tab or the API, is left open; the banner's **Cancel window** names the window it showed, too. A reload loses the code, so the page shows a window open without its dialog as a banner that says its code cannot be shown again, with **Cancel window**. While open the dialog asks `GET /link-window` every 2 s and stops when its window is no longer the open one, the code removed with the panel that showed it. It says how the window ended only from an end that names it (`ended_window_id`): linked; or ran out, cancelled elsewhere or replaced, each with "nothing was linked by it", which the server's lock between ending a window and approving a link makes true. Otherwise it says the outcome is not known here and sends the owner to the list and the change log: when the approval failed (possibly after its commit), when another window is open, and when the end the state reports is another window's or none (after a restart). Wrong codes typed on the window's consent pages are shown with the count: a wrong code shows that consent page again, the fifth on one request ends that request, none closes the window, and the owner may cancel and open a new one.
- **Settings** — API key display (masked), device type management (add/rename/re-icon/delete with a curated icon picker), SQLite backup download, app version

When no API key is stored in the browser, the SPA shows an in-app API-key connection gate. The key is stored only in that browser. A reverse proxy / Cloudflare Access layer may provide an additional outer access-control boundary.

## 9. Key decisions & rationale

| Decision | Rationale |
|---|---|
| SQLite not Postgres | Zero ops overhead. A homelab IPAM will never have sustained write contention. Backup = copy one file. Connections run with `journal_mode=WAL` and `busy_timeout=5000` so the occasional simultaneous UI/MCP write queues instead of raising "database is locked". |
| FastAPI not Flask | Native async, automatic OpenAPI schema generation, Pydantic validation built in. |
| FastMCP with curated tools, not OpenAPI auto-generation | Hand-written tools have better names, parameters, and denormalised answers — materially better Claude ergonomics. Shared `services/` layer eliminates the drift risk that auto-generation was meant to solve. FastMCP is the actively-maintained de facto standard. |
| Streamable HTTP not stdio | Works with mcp-remote for Claude Desktop. Also compatible with any future MCP client without modification. |
| One uvicorn worker, enforced by the image (`python -m app.serve` passes `workers=1`) | MCP session state is per-process memory and SQLite has one writer; the session state is not shared between processes, and a second process adds no capacity a homelab needs (see §2.2). |
| Single container, FastAPI serves the SPA | One origin (no CORS), no nginx config, one port to tunnel, `docker compose up` is the whole story. |
| Audit log from day one | Claude writes to this system; you need to be able to review what it did. Also free "recent activity" UI. |
| React + Vite not Next.js | No SSR needed. Vite builds faster, static output served straight from FastAPI. |
| Single API key not JWT | Homelab single-user context. Web MCP clients, which cannot send a static key, are linked through the server's own OAuth for `/mcp` alone (§5.5); the REST API keeps the one key. OIDC is not built in: SSO or MFA is an access proxy in front of the two browser paths. |
| No discovery/scanning in v1 | Keeps scope sane. Manual + MCP-driven allocation is the primary workflow. Scanning can be added later. |

## 10. Acceptance criteria

### Core functionality
- Can create sections, subnets (with VLAN tag, gateway, DNS, DHCP pool), and hosts via both UI and API.
- IP validation rejects out-of-subnet addresses with a clear error message.
- "Allocate next free IP" finds the next unallocated address — skipping network, broadcast, gateway, DHCP pool, and reserved ranges — and creates the host record atomically.
- Hosts inherit the subnet's default domain suffix; a per-host override wins, and clearing the override re-inherits. API responses expose the computed FQDN.
- Reserved ranges block automatic allocation but not manual host creation.
- Overlapping CIDRs rejected within a section, allowed across sections.
- Search returns results across hostname, IP, and MAC.
- Subnet utilisation is accurate (allocated / total usable addresses).
- Every write appears in the change log. MCP provenance is authoritative; UI/API attribution is advisory because REST clients share one API key and can set `X-TLG-Client`.
- An agent's `tlga_…` token appears in exactly one response, the enrol exchange's, and an enrolment token (`tlge_…`) in exactly one, the create or re-enrol response that issued it; each is stored only as its SHA-256 and display prefix. Each token's create, use and revoke has a change-log entry.
- A used or expired enrolment token is refused; after a re-enrol exchange the agent's old agent token is refused and its scan targets are unchanged; the enrol throttle engages after repeated bad tokens (`api/tests/test_enrolment.py`).
- The owner key is refused on agent routes; an agent token is refused on owner routes and on `/mcp`. A revoked token, and the token of a disabled agent, are refused.
- A subnet's scan scope leaves out network and broadcast, the DHCP pool unless pool scanning is on, and every excluded reserved range; an address in both an excluded and a scanned range is excluded. Ranges from a database made before scan exclusion existed read as scanned.
- Scan targets are refused for prefixes shorter than `/20` and for method sets without `icmp` or `arp`. Deleting a subnet deletes its scan target; deleting an agent unassigns its targets. Every scan-target and scan-exclusion change is in the change log.
- A scan target is issued to its agent at check-in when its interval has passed or a scan was requested, and is not issued again while its lease is live; an expired lease makes it due again. A job's ranges are the scan scope, and `arp` is dropped for a subnet that is not on the agent's link; a target with no liveness method left gets no job.
- The Agents page's install, update and re-enrol commands match the shapes in v0.2 spec §5.6 and hold no agent token (`web/src/utils/install.test.js`); an agent older than the server is flagged `update_available`, one refused for its protocol `protocol_mismatch`, an enrolment refused for its protocol is given as `enrol_refusal` with nothing written (`api/tests/test_enrolment.py`), and an agent on a subnet's link is offered that subnet to scan until it has a scan target (`api/tests/test_guided_install.py`).
- A check-in on another protocol gets no jobs and a `409 PROTOCOL_MISMATCH`, recorded in the agent's `last_error`. Agent-reported fields are length-capped and printable-only; a check-in that breaks either is refused and recorded the same way.
- A subnet's `dns_servers` over 8 entries is refused on write, naming the limit, and a longer list stored before the bound survives an unrelated edit. A job carries at most three servers and its CIDR in its canonical spelling, whatever the subnet stores, and the largest check-in answer the server can build is inside the agent's 1 MiB answer limit.
- A subnet's CIDR is stored in its canonical spelling whatever was typed; another spelling of a network already in the section is refused as a duplicate; a subnet stored with another spelling before #97 is read as stored, can be edited, and is scanned.
- A second scan request for a subnet within 15 minutes is refused, whoever asks.
- An agent checks in at most once every 10 seconds, and keeps at most 100 audit entries of its own; text it reports about itself never reaches an assistant through `list_changes`. A target whose jobs keep timing out does not starve the agent's other due targets.
- Scan results: an out-of-scope address, a wrong job id and a second result set are each rejected without affecting valid records; a job whose liveness sweep did not complete adds what it saw and marks nothing dead; a stored name is cleared only by an answer that there is none, never by a lookup no DNS server answered, while a scan whose liveness sweep completed marks a departed host dead whatever the lookups got; a result set of protocol 1 is ingested by protocol 1's rule; a hostile `rdns_name` (spaces, markup, instructions) is dropped; deleting a subnet with observations succeeds. Ingest writes no host and no change-log entry, and observations that leave scan scope are deleted with the change that narrows it.
- Findings: each type is raised from hosts and observations inside scan scope only, with no MAC finding for a randomised MAC. Accepting one whose observed value has changed writes nothing and reports `skipped`; an accepted one is written through the host paths and appears in the change log with no network-reported value in its summary. A dismissed finding stays hidden until its observed value changes, and dismissals go when their address leaves scope or the subnet is deleted.
- Forward DNS (#20): a job names a host only when its FQDN is under the subnet's own domain and its address is in scan scope, so a host whose FQDN is outside the domain, by its own override or a lookalike suffix, is never sent; a name that does not resolve gives an `fdns_mismatch` whose observed value is `unresolved`, which accept refuses and dismiss hides (`api/tests/test_fdns.py`, `agent/tests/test_fdns.py`, and through the real routes `agent/tests/test_e2e.py`).

### Testing
- pytest covers CIDR/IP validation, CIDR child invariants, explicit-null updates, the overlap rule, interval maths, consistent backups, MCP clearing, and next-free allocation edge cases.
- ESLint, Vitest component tests, and the production frontend build run in CI alongside pytest, with a check that the dependency locks match their `.in` files.
- The scan agent's tests run in CI with no packet sent: a fake server and a fake prober drive the loop (refusals, back-off bounds, the allowlist, the timeout), a fake ARP link reads the agent's real request frames and answers with real reply frames, malformed and unsolicited ones among them, its client runs against the real check-in and results routes in process, a loopback TLS server checks that verification cannot be skipped, loopback DNS responders check the arrival times of real queries against `MAX_PPS`, fake clocks that wake late or early check that no second holds more than `MAX_PPS` sends across the three methods and from one job into the next, a send that never waits checks that the rest of the agent still runs, a loopback HTTP server that drips its answer checks the request deadline, and the image is built and started with no network.

### MCP integration
- Claude Desktop connects via `mcp-remote` with the owner key as a bearer and lists all available tools.
- `/mcp` answers `401` to a missing or wrong bearer, and to `X-API-Key` alone.
- All 18 MCP tools are callable from Claude Desktop.
- Bulk import reports per-record outcomes; a batch with some bad rows still imports the good ones.
- No MCP tool configures agents, scan targets or scan scope. `add_reserved_range` creates a scanned range; `delete_reserved_range` on an excluded range fails with a message pointing at the web UI; `get_subnet` shows `scan_excluded` and `scan_dhcp_pool`.
- `list_scan_findings` and `request_scan` are in `EXPECTED_TOOLS` and the tool table. `request_scan` inside the cooldown returns a tool error that says when it can run again.
- Natural-language queries resolve to correct tool calls without ambiguity.

### Remote MCP
- Without `PUBLIC_BASE_URL` the OAuth and discovery paths are 404s and `/mcp` takes the owner key alone; with it, the owner key still works on `/mcp` (`api/tests/test_oauth.py`).
- Outside a link window, registration and authorisation are refused and existing links keep refreshing. A link needs the window's one-time code, and one window makes one link. A request's fifth wrong code ends that request and never the window (`api/tests/test_link_window.py`).
- A grant's token works on `/mcp` only, never on the REST API, the backup or the agent routes. A refresh token reused after its 60-second retry window revokes the grant (`api/tests/test_oauth.py`).
- A link is read-only unless `MCP_REMOTE_WRITES` is `true` **and** its window was opened with `can_write`: otherwise it lists no write tool, and calling one changes nothing. Turning the setting off takes write access from every link at the restart, with no relink, and a link made read-write writes again once it is back on. A linked client's write names it in `actor`. A value other than `true` or `false` stops the start (`api/tests/test_remote_writes.py`, `test_oauth_mcp.py`, `test_oauth_restart.py`, `test_startup.py`).
- `docs/deployment.md` says which paths a tunnel or reverse proxy publishes, so that the REST API and the SPA stay private; how to put SSO or MFA on the authorise and consent paths alone; and how to deploy the server and agents. Its examples use placeholder domains only.

### Operations
- `docker compose up --build` produces a running stack with no manual steps.
- All data persists across container restarts (named volume).
- API key changeable via env var without rebuild. The server refuses to start with `API_KEY` unset, empty, or `change-me` (§4.1).
- Settings exposes a SQLite backup download created through the online backup API rather than streaming the active database file.
- `docs/backup-and-restore.md` describes a scheduled pull of `GET /api/v1/backup` from another host (dated files, retention) and a restore procedure; following it against a running instance produces a dated snapshot and a working restore from it. Its examples use placeholder domains only.
- The container runs one uvicorn worker, pinned by `python -m app.serve`, the image's `CMD` (§2.2).
- The container's process runs as uid and gid 10001, not root; a volume made by an earlier image is given to that user, and made 0700, once with the README's two commands, and until then the server refuses to start rather than start read-only (§2.2).
- A request body over 2 MiB is `413 PAYLOAD_TOO_LARGE` on every route, `/mcp` included, before authentication or parsing, with a declared `Content-Length` and without one (§4.3).
- The bodies of the requests in progress hold at most 16 MiB together (`503` past it), a body not received whole within 60 s is `408`, and both close the connection, on every route (§4.3).
- On the image's server, a request line and headers over 64 KiB as received is `431` and closes the connection, a connection that has not delivered a request's head whole within 10 s of opening, or of its last response, is closed, at most one pipelined request is queued, and a response or a closed connection the client takes nothing of for 60 s is dropped (§4.3).
- The server and the agent are one version, and a tag `v<version>` publishes the agent image and wheel under the names the Agents page's install commands use, then fetches both with no credential (§2.4, `.agents/releases.md`).
