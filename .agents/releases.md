# Releases

What a release is, the owner's one-time setup before the first, and the checklist for each. The workflow is `.github/workflows/release.yml` (#24, spec §5.6). Releasing is the owner's: an agent prepares the version bump, the owner pushes the tag.

## What a release is

One version names the server and the scan agent: `VERSION` in `api/app/version.py` and `__version__` in `agent/src/tlg_ipam_agent/__init__.py`, the same string (`agent/tests/test_release.py` and `web/src/utils/install.test.js` fail otherwise). It is a PEP 440 public version in normal form, with no local `+…` part and no epoch. A server reports it at `GET /health`, its Agents page pins the install and update commands to it, and an agent that reports an older one is flagged "update available". Between releases, `main` carries the next release's `.dev0` (`0.3.0.dev0` after `0.2.0`).

A release is the tag `v<version>` on a commit of `main` at that version. Pushing it runs the workflow, which publishes the two artefacts the install commands name (`web/src/utils/install.js`):

| Artefact | Name | Where |
|----------|------|-------|
| Agent image, `linux/amd64` and `linux/arm64` | `ghcr.io/deusmaximus/tlg-ipam-agent:<version>` | GitHub container registry |
| Agent wheel | `tlg_ipam_agent-<version>-py3-none-any.whl` | the GitHub release `v<version>`, so at `https://github.com/DeusMaximus/TLG-IPAM/releases/download/v<version>/…` |

The server is not published as an image: it is built from the tag (`git checkout v<version> && docker compose up --build`), and then reports that version. A server built from `main` between releases reports a `.devN` version that names no artefact, so its install commands do not resolve. Use a release.

### What the workflow does

| Job | Runs on | Permission, and what for | Does |
|-----|---------|--------------------------|------|
| `build` | every trigger | `contents: read`, to check out the code | Checks that the tagged commit is on `main`, that the two versions are one release version and the tag is `v<version>` (`.github/scripts/release_check.py version`), and that the page's `install.releaseVersion` takes it. Builds the wheel with `python -m flit_core.wheel` from the hashed `agent/requirements-build.txt`, at the commit's time (`SOURCE_DATE_EPOCH`), so a rebuild is the same file. Checks its name, metadata and files (`release_check.py wheel`), then installs it with the agent's locked dependencies on Python 3.11 and 3.13 and runs `--version`. Reads the digest the base image's tag names now and warns when it is not the one `agent/Dockerfile` pins (#94); it never fails on that, since the image is built from the pin either way. Builds the image for both platforms into one OCI archive, with no provenance or SBOM attestation. Then it takes each platform's image out of that archive and runs the start-up checks on it (`.github/scripts/check-agent-image.sh`, `--network none`, arm64 under QEMU). Records the wheel's SHA-256, the image index's digest and the archive's SHA-256, and uploads the wheel and the archive as the run's `release` artefact, the publish jobs' only input, configured to be kept 7 days ([the retry window](#the-retry-window-and-what-to-do-past-it)). |
| `publish-image` | a pushed tag | `packages: write`, to push to ghcr.io | Downloads the artefact and checks the archive's SHA-256. If `:<version>` already exists, it must already be this digest (a re-run), or the job fails. It pushes only when the registry answers that the tag is absent (`MANIFEST_UNKNOWN` or `NAME_UNKNOWN`). Any other failure to read the tag is tried three times, then stops the job with nothing pushed, so a registry error never lets a version be overwritten. Otherwise it pushes the archive as it is (`skopeo copy --all --preserve-digests`) and checks the registry now serves that digest. Checks out nothing. |
| `publish-release` | a pushed tag, after `publish-image` | `contents: write`, to create the release and attach the wheel | Checks the wheel's SHA-256, then reads which releases have the tag from the list of the repository's releases, drafts included, a page of 100 at a time until a page holds fewer (at most 20 pages). The tag has no release only when every page it asked for was read as a list: any other read is tried three times, then stops the job with nothing created, uploaded or edited (#159). With no release it creates `v<version>` (`--verify-tag`), with the wheel attached and the digest and checksum in its notes. A pre-release version (`rc`, `.dev`) is marked as a pre-release. With one: a release that already holds the wheel must hold this one, or the job fails; one without it gets it attached, and a draft an interrupted run left behind is then published. With more than one (a draft beside the published release, say) it stops with nothing changed. Checks out nothing. |
| `verify` | a pushed tag, after `publish-release` | `contents: read`, to check out the image check script | Reads the image's index from the registry and pulls it with no credential, as an operator's host would, then runs the start-up checks. Downloads the wheel from the release URL and checks its SHA-256. Runs the systemd tab's `pip install <release wheel URL>` into a fresh venv on the runner's own Python. |

Every other permission is none (`permissions: {}` at the top). Every action is pinned to a commit, and the BuildKit and binfmt images the build runs are pinned to digests, and so is the agent's base image, in `agent/Dockerfile`. A pull request that changes what goes into the artefacts (`agent/`, `api/app/version.py`, `install.js`, the workflow or its scripts) runs `build` alone, and so does a run by hand (Actions → Release → Run workflow), which has no input that turns publishing on. No `latest` tag is pushed, nothing goes to PyPI, and nothing is signed: the install commands name an exact version, and the release notes carry the digest and checksum to compare against.

## One-time setup, before the first tag

1. **Workflow permissions.** The repository's default token permission (Settings → Actions → General → Workflow permissions) can stay read-only: each job asks for what it uses. Nothing changes here unless the account forbids workflows from asking for write permissions.
2. **The container package.** If `ghcr.io/deusmaximus/tlg-ipam-agent` does not exist yet, the first `publish-image` creates it, connected to this repository by the image's `org.opencontainers.image.source`. If it exists already (pushed by hand earlier), open it (Profile → Packages → `tlg-ipam-agent` → Package settings → Manage Actions access) and give this repository the **Write** role. Without that, `publish-image` fails with `denied`.
3. **The package's visibility, after the first publish.** The install commands pull the image with no login, so the package has to be public, and `verify` reads it the same way.
   - **What the first release showed** (`v0.2.0`, 2026-11-27, [Release run 46008510831](https://github.com/DeusMaximus/TLG-IPAM/actions/runs/46008510831), attempt 1): the package was readable without a login from its first publish. `verify` passed: it read the image's index from the registry and pulled the image with no credential, before any package setting had been changed. Nothing had to be done. Why the package was public was not established: its settings were not read.
   - **If a package does turn out private** (not seen on this repository's first release): `verify` fails with "cannot be read without a credential". In Package settings → Danger Zone → Change visibility, choose **Public**, then re-run `verify` from the workflow run (Re-run failed jobs). This is needed once: later versions inherit the package's visibility.
4. **Optional hardening:**
   - A tag ruleset (Settings → Rules → Rulesets → New tag ruleset, target `v*`) that restricts creation, update and deletion to the owner. It stops a version tag being pushed or moved by anyone else with write access.
   - Release immutability (Settings → General → Releases), so a published release's wheel and tag cannot be changed afterwards. `gh release create` attaches the wheel to a draft before publishing it, so the first run works with it. A re-run that had to attach the wheel to a release already published would be refused. Release the next version instead.

## Checklist for each release

1. **Pick the version**: `X.Y.Z`, or `X.Y.ZrcN` for a release candidate. It is a pre-release, and the install commands of a server at that version use it like any other.
2. **Read what changed since the last tag** (`git log v<last>..main`). If `PROTOCOL_VERSION` (`api/app/agent_protocol.py`) changed, every agent must be updated together with the server: an older agent's check-ins are refused with a protocol mismatch, and it is given no scans until it runs the new release. Say so in the release notes (edit them after the run).
3. **Base image, then the bump PR.** First the base: compare the `Digest` that `docker buildx imagetools inspect python:3.13-slim` gives with the one `agent/Dockerfile`'s `FROM` names (every Release run's build job warns when they differ). If they differ, move the pin in a PR of its own (`AGENTS.md`, Commands, "The agent's base image") and merge it with CI green before the bump. A tag publishes the base its commit pins, so this is where a release takes the base's fixes.

   Then the **bump PR**: a PR that sets `VERSION` in `api/app/version.py` and `__version__` in `agent/src/tlg_ipam_agent/__init__.py` to `X.Y.Z`, and nothing else. Its Release workflow run builds and checks both artefacts at `X.Y.Z` (the run on the PR publishes nothing). Its Tests section records the base digest the release will be built from (`agent/Dockerfile`'s `FROM`) and that the PR's Release run reported it current: the step *The base image's pin, against its tag* printed `python:3.13-slim still names sha256:…`, not a warning. A warning on a green run is easy to miss; a line to write is not. Merge it with CI green.
4. **Tag the merge commit** on `main`, and push the tag:

   ```sh
   git fetch origin && git checkout --detach origin/main
   git log -1 --oneline          # the bump's merge commit
   git tag -a vX.Y.Z -m vX.Y.Z
   git push origin vX.Y.Z
   ```

   A tag is pushed once. Never move or reuse one: an operator who installed `X.Y.Z` has those artefacts.
5. **Watch the run** (Actions → Release): `build`, `publish-image`, `publish-release`, `verify`. If `verify` fails with "cannot be read without a credential", see setup step 3.

   The first release also called for a one-off measurement of the retry: once `verify` had passed, a re-run of the `publish-image` job alone. It was done on `v0.2.0` and is not asked of any later release. [The retry window](#the-retry-window-and-what-to-do-past-it) records what it showed.
6. **See it from an operator's side.** The release page lists the wheel, and its notes give the image digest. Build the server from the tag and open Agents → Add agent: both tabs' commands name `X.Y.Z`, and the image and wheel URL they show are the published ones. An agent of the previous release is flagged "update available".
7. **Open the next cycle.** A PR that sets both versions to the next `.dev0` (`X.Y.(Z+1).dev0`, or `X.(Y+1).0.dev0`).
8. **Hand-off entry**: the version, the run, the image digest, anything that failed and how it was fixed.

## When a step fails

- **`build`:** nothing was published. Fix the cause on `main` with a PR. Then delete the tag (`git push --delete origin vX.Y.Z`, and `git tag -d vX.Y.Z` locally) and tag the fixed commit with the same version. This is the one case where a tag is reused, since nothing was published under it.
- **`publish-image`:** `denied` means setup step 2. "Could not tell whether … exists, so nothing was pushed" means the registry failed to answer three times: re-run the failed jobs. Anything else: re-run the failed jobs of the same run. The build is not repeated, and the archive is pushed by its digest. All of this within the retry window below.
- **`publish-release`:** the image is already published. Re-run the failed jobs, within the retry window below. Only `publish-release`, and `verify` after it, run again: `publish-image` succeeded and is not re-run. `publish-release` finishes a release it had left as a draft (the wheel checked or attached, then published).
  - "Could not tell whether vX.Y.Z has a release, so nothing was created, uploaded or edited" means three reads of the list of releases failed. The `::warning::` lines above it give each attempt's page and answer (`HTTP 5xx`, a rate limit, no answer, `page N was not a list of releases`). `more than 20 pages of releases` every time means the repository has passed 2,000 releases, or GitHub stopped honouring `page`: raise the bound in the step (`release.yml`) in a PR. Nothing changed on the Releases page. Re-run the failed jobs. If an answer was `Bad credentials` or `Resource not accessible by integration` every time, check setup step 1 first.
  - "vX.Y.Z has more than one release (id, draft: …), so nothing was changed" means a draft for the tag sits beside the published release or another draft. The job never makes one: a draft can be left by a run before #159, which created a second release when its lookup failed, or made by hand. On the Releases page, delete the draft (tell it by its Draft label, since its title is the same; the message lists each release's id and whether it is a draft), and re-run the failed jobs. The published release is the one the wheel's URL names. The job stops rather than choose: `gh`'s own lookups answer with either release when both exist.
- **`verify`:** if it failed with "cannot be read without a credential", check the package's visibility (setup step 3). A private package is a case not yet seen: on `v0.2.0`, the first release, `verify` passed on the run's first attempt. If the package is public, or the failure is any other, compare what it fetched with the digests the build recorded (in the job's log and the release notes) before doing anything else. `verify` reads only the registry and the release, not the build's artefact, so it can be re-run at any time GitHub allows a re-run (30 days).
- **A release that is wrong once published:** do not replace its artefacts (the workflow refuses to) or move its tag. Release the next patch version, and say in the bad release's notes which version replaces it.

### The retry window, and what to do past it

The `build` job hands the publish jobs one thing: the run's `release` artefact (the wheel and the image archive), with the digests it recorded as job outputs. It is configured to be kept **7 days** from the build's upload (`retention-days: 7`). It can be gone sooner: deleted by hand, or capped lower by the repository's artifact retention setting. The run page's Artifacts section lists it while it remains. That is the window in which a failed publish can be retried. It was kept at 7 days rather than lengthened: a release is watched as it runs (checklist step 5), and a week is ample to fix a permission or a package setting and retry.

There are two ways to retry, and they are not the same:

- **Re-run failed jobs** (the run page → Re-run jobs → Re-run failed jobs) runs the failed job and the jobs after it, and nothing before. `build` is not run again. GitHub documents that the re-run jobs get its outputs. A re-run attempt can download its artefact too, as the first release measured (below), and so publishes the same files under the same digests. This is the retry. It works while the artefact remains available (configured for 7 days), and GitHub allows a re-run for 30 days after the run started, so the artefact is the limit.
- **Re-run all jobs** runs `build` again from the tag. The wheel is built at the commit's time and comes out the same file, but the image does not. Its base is the same: `agent/Dockerfile` at the tag names it by digest (#94), so the base's layers are the ones the first build used, whatever the tag names now. The packages are the same too, installed from the hashed lock. What differs is time: the image's configuration records when it was built, and every layer the Dockerfile's own steps write after `WORKDIR` (the lock and the source copied in, the packages installed, the state directory) holds a directory or file stamped with the build's time, and the packages' layer holds the bytecode pip compiles, which records the time its sources were installed. So the image's digest differs. Measured on two `--no-cache` builds of one commit (#94): the base's four layers and `WORKDIR`'s were the same; the four after them differed in modification times alone but for 296 `.pyc` files. Once the image is published, `publish-image` then refuses the version ("already published as …, not this build's …") and nothing more is published. Use it only when nothing was published.

**That a re-run attempt can download an artefact an earlier attempt uploaded was measured on the first release** (`v0.2.0`, 2026-11-27, [Release run 46008510831](https://github.com/DeusMaximus/TLG-IPAM/actions/runs/46008510831)). After `verify` had passed on attempt 1, the `publish-image` job alone was re-run (Re-run this job). That was attempt 2: `publish-release` and `verify`, which depend on it, ran again, and `build` did not.

- `publish-image` downloaded the `release` artefact that `build` uploaded in attempt 1, with the SHA-256 `build` logged at the upload (`sha256:4de0998bb19ed74d91c911ac4ecc258b8e26e56f71631a7e5b91afa5328ceab1`), and its check of the archive passed. It logged `ghcr.io/deusmaximus/tlg-ipam-agent:0.2.0 is already this build (sha256:51ace516cf75b89a72d1fe21c958e8f201c8962beb4f5ab5ea985cbb1d5232da)`, the digest `build` recorded.
- `publish-release` downloaded the same artefact, and its checks of that wheel and of the one attached to the release passed. It uploaded and edited nothing: the release's publish time and the wheel's upload time stayed attempt 1's (13:38:26 UTC).
- `verify` passed.

What it did not cover: **Re-run failed jobs** was not the button used, since no job had failed, and the download came about six minutes after the upload. That one days later still works rests on the artefact's configured retention.

Whether the image was published: `publish-image`'s log ends with `pushed ghcr.io/deusmaximus/tlg-ipam-agent:X.Y.Z@sha256:…`, and the package's page (Profile → Packages → `tlg-ipam-agent`) lists `X.Y.Z`. A re-run that finds the tag already holding this build logs `… is already this build (sha256:…)` and then ends with the same `pushed …` line. The step prints that line once it has checked that the registry serves the digest, whether or not it copied anything, so the line does not say which attempt pushed the image. If the package is private (setup step 3; not seen on the first release), a read of the tag without a login fails whether or not it exists.

Past the window (the artefact is gone), and after a whole re-run that `publish-image` refused:

- **If the image was not published,** nothing was: treat it as a failed `build`. Delete the tag, push it again on the same commit, and the new run builds and publishes from the start.
- **If the image was published and the release was not,** the version is spent. Never rebuild it to finish it: a rebuild is another image under a name operators may already have pulled, and the workflow refuses to push it. Leave the published image as it is (do not delete it: an operator may run it), and release the next patch version through the checklist from step 1. A server built from `vX.Y.Z` shows a wheel URL that does not resolve, so build servers from the new tag. Record it in the hand-off entry.
