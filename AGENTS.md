# TLG-IPAM

Homelab IPAM: FastAPI + SQLite backend, React SPA, and an MCP server at `/mcp` so AI assistants (Claude, ChatGPT, or any other MCP client) can query/update it. The full specification — data model, endpoints, MCP tool inventory, UI spec, acceptance criteria — lives in `TLG-IPAM-Project-Brief.md`. **Keep the brief in sync when behaviour changes**; it is the source of truth, not documentation theatre.

## Workflow

v0.2 (scan agents, remote MCP) is specified in `docs/v0.2-spec.md` and tracked as GitHub milestones M0–M3. The spec is the contract for work that has not shipped; the brief describes what `main` does.

- **Session start:** read the newest entry in `HANDOFF.md`. It holds live state: what is merged, in flight, broken, or waiting on the owner.
- **One issue, one branch, one PR.** Branch `<issue>-<slug>` from `main`. The PR closes the issue and carries in the same diff: the tests, the brief update for the behaviour it ships, and the `AGENTS.md` line for any invariant it adds or changes.
- **Green before the PR opens:** the commands CI runs (`.github/workflows/ci.yml`), locally.
- **The PR body is the record.** It opens with the authoring agent, model, and head sha, then **What**, **Deliberate calls**, **Tests**. `.agents/review-brief.md` holds the body shape; read it when opening a PR.
- **Merge needs green CI and every automatic review finding answered.** Codex and Greptile review each PR when it opens: fix each finding or reply on its thread with the reason it stands. The owner merges.
- **A briefed review round as well** for a PR that touches authentication, tokens, OAuth, agent ingest, or code that sends packets. It needs a GO from a reviewer in a different model family from the author; `.agents/review-brief.md` is how the round is briefed.
- **When the spec is wrong** (the code or a spike shows it), change `docs/v0.2-spec.md` in the same PR and list the change under Deliberate calls.
- **Session end:** add a `HANDOFF.md` entry using the template in its header. Hand-off entries commit straight to `main`, so the next session sees them without waiting on a PR. A session working in a worktree ends its final message with its entry, and the orchestrator commits it.
- **Orchestrating** (handing issues to other sessions and checking their results): read `.agents/orchestration.md` first.

`.agents/README.md` indexes the process material that is not needed on every turn.

## Commands

```sh
# Backend (one-time setup: python3 -m venv api/.venv && api/.venv/bin/pip install --require-hashes -r api/requirements-dev.txt)
cd api && .venv/bin/python -m pytest                  # test suite — run before declaring any backend change done
cd api && API_KEY=dev-key .venv/bin/uvicorn app.main:app --port 8080 --reload
#   add STATIC_DIR=../web/dist to also serve the built SPA (single-origin, like production)

# Scan agent (one-time setup: python3 -m venv agent/.venv && agent/.venv/bin/pip install --require-hashes -r agent/requirements-dev.txt)
cd agent && .venv/bin/python -m pytest                # agent tests, incl. end-to-end against the real routes; sends no packet
docker build -f agent/Dockerfile -t tlg-ipam-agent:dev agent

# Frontend
cd web && npm run dev                                  # hot reload, proxies /api → :8080
cd web && npm run build                                # production bundle to web/dist

# Full stack (needs .env with API_KEY)
docker compose up --build
```

### Dependency lock

`api/requirements.txt` (runtime) and `api/requirements-dev.txt` (runtime + test) are **generated lock files**: every package pinned by version and hash, resolved for Python ≥ 3.12 on any platform. The Dockerfile and CI install them with `pip install --require-hashes`. Edit the direct dependencies in `api/requirements.in` / `api/requirements-dev.in` (`fastmcp` stays `>=4.1,<5`), never the lock files, then regenerate **both** from `api/` with [uv](https://docs.astral.sh/uv/):

```sh
uv pip compile requirements.in --universal --python-version 3.12 --generate-hashes --no-header -o requirements.txt
uv pip compile requirements-dev.in --universal --python-version 3.12 --generate-hashes --no-header -c requirements.txt -o requirements-dev.txt
#   append -P <package> to either command to upgrade just that package; -U to upgrade everything
```

Commit the `.in` and lock changes together. The `-c requirements.txt` constraint keeps shared packages at the same version in production and in tests.

Use uv **0.13.6**, the version CI pins. `uvx uv@0.13.6 pip compile …` runs it without changing the uv you have installed. The `locks` job in CI runs these two commands, verbatim, in a fresh checkout and fails if either lock changes. Because recompiling keeps every pin, and its hashes, that still satisfies the `.in` files, a newer upstream release does not make the job fail. Only a `.in` change committed without regenerating does that. When you change these commands, change the `locks` job's copy in `.github/workflows/ci.yml` too. The job fails if `AGENTS.md` no longer lists its commands word for word.

The scan agent has its own pair, `agent/requirements.txt` (what the agent image installs: httpx, icmplib, dnspython and their dependencies, for Python ≥ 3.11) and `agent/requirements-dev.txt` (that plus the server's test set, so the agent's end-to-end tests run against the real routes in one environment). Edit `agent/requirements.in` / `agent/requirements-dev.in`, keep `agent/pyproject.toml`'s `dependencies` the same as `requirements.in` (a test checks), and regenerate both from `agent/`, **after** the server's locks:

```sh
uv pip compile requirements.in --universal --python-version 3.11 --generate-hashes --no-header -c ../api/requirements-dev.txt -o requirements.txt
uv pip compile requirements-dev.in --universal --python-version 3.12 --generate-hashes --no-header -c requirements.txt -c ../api/requirements-dev.txt -o requirements-dev.txt
```

Both are constrained to `api/requirements-dev.txt`, so a package the agent shares with the server (httpx, certifi, idna, dnspython) is the version the server's tests use. A server lock change that moves a shared package therefore fails the `locks` job until the agent's locks are regenerated in the same PR. The job's agent step checks these two commands against this file word for word, as it does the server's.

## Architecture invariants

- **All business logic lives in `api/app/services/`.** REST routers (`api/app/routers/`) and MCP tools (`api/app/mcp_server.py`) are thin wrappers over the same service functions. Never put validation or logic in a router or tool.
- **Every write is audit-logged** via `services/changes.record()` with the correct `source` (`ui`/`api`/`mcp`, or `agent` for a check-in that changes what an agent reports and for the enrolment exchange, `services/enrolment`, whose token and agent entries carry the agent's `actor`). A write path without a change-log entry is a bug, with four deliberate exceptions: heartbeats (`tokens.last_used_at`, `agents.last_checkin_at`), job scheduling (the lease columns on targets and agents), the cap that keeps each agent's own `source="agent"` entries to its newest 100 (`jobs.prune_agent_audit`, run by check-in and by the enrolment exchange; owner entries and token entries are never pruned), and scan results ingest (`services/results`: observations, their 90-day prune, and the target's last-scan columns). Observations deleted because a change narrowed scan scope go with that change's own entry. Over MCP, `list_changes` withholds agent-reported values in `agent` snapshots (`changes.assistant_view`). `actor` names who acted when that is narrower than the `source`; it is null for the owner key (spec §4.3). A name a client or agent declares goes in `actor`, never into `summary`.
- **MCP tools are hand-curated**, never auto-generated from OpenAPI. When adding or changing one: the docstring is the connected assistant's runtime documentation (write it for tool selection), update `EXPECTED_TOOLS` in `api/tests/test_mcp.py`, and update the tool table in the brief. MCP may only mutate hosts and reserved ranges, and ask for a scan — subnet/section deletion stays UI-only by design. No MCP tool creates, configures or lists agents, tokens or scan targets, MCP never gains scan-target or scan-scope configuration, and no MCP call can widen what is scanned (spec §7.2, invariant 2): `add_reserved_range` creates a scanned range, `delete_reserved_range` refuses a range with `scan_excluded` (`services/subnets.delete_reserved_range`, on `source="mcp"`), and `request_scan` sets only a configured target's `scan_requested_at`, under the cooldown every caller shares, so the scope the owner set is scanned sooner; it returns the request and `next_request_after` (`scans.scan_request_out`), never the target. `list_changes` still shows their audit entries. No tool checks scopes yet: #28 adds `ipam:write` to every write tool at once, `request_scan` included. `list_scan_findings` (`findings.list_named`) hands an assistant what devices reported (`observed`, `proposed`) as data, with `findings.NETWORK_REPORTED_NOTE` beside the list and the same warning in its docstring, and leaves out `dynamic` findings. It returns a page of at most `findings.PAGE_SIZE` findings and `findings.PAGE_BUDGET` bytes of them (a domain suffix has no length limit, so the count alone does not bound a page), never the whole network, with `next_cursor` (null on the last page) and the note on every page, both ahead of the findings; the cursor is the position of the page's last finding, and both bounds are measured against what a client holds (the comment on `PAGE_SIZE`; `test_a_page_at_every_field_maximum_fits_a_client` and `test_pages_of_long_domains_stay_inside_the_budget` hold them). That `request_scan` changes only `scan_requested_at` rests on `test_mcp_request_scan_changes_only_the_request_time`, which compares every column of every table, and its refusals change none. There is no accept or dismiss tool: an assistant resolves a finding with `create_host`/`update_host`, which its fingerprint does not bind.
- **Scan scope is computed in one place, `services/scans.scan_scope`** (spec §7.2, invariant 4): usable addresses minus the DHCP pool (unless the target's `scan_dhcp_pool`) minus reserved ranges with `scan_excluded`, and exclusion wins over a scanned range. Job creation, ingest validation, findings and the UI call it; nothing else works scope out, and no packet goes to an address outside it. The UI has it from the scan-target answer (`scans.targets_out`, which reads the scope's inputs for all the targets it answers for at once through `scans._scopes_as_committed`, the one reader of them, in chunks of `scans._IN_BATCH` distinct subnet ids, each chunk reading all three inputs of each of its subnets, so no subnet's scope is put together from two chunks; `scan_scope` is its one-subnet case, one chunk of the same three statements, and `test_each_subnet_gets_its_own_scope_in_any_order_of_ids_and_across_chunks` holds every subnet's scope to it in any order, with repeats, at every chunk size), whose ranges carry their bounds as integers (`start_int`, `end_int`) beside the addresses, and places a host by comparing its `ip_int` with them, never by parsing an address. Observations and finding dismissals exist only inside it: results ingest rejects an address outside the scope at ingest, and every write that can narrow it (pool scanning off, target deleted, a range excluded or added excluded, pool or CIDR edited) calls `scans.drop_out_of_scope` in its own transaction. `scan_scope` reads its inputs as committed columns, never from objects the caller loaded and never refreshing them, and a caller that writes on the strength of the scope holds SQLite's write lock first: `drop_out_of_scope` takes it itself (`scans.take_write_lock`), ingest before it rechecks the request's credential and its lease compare-and-set, check-in after `jobs._claim`. The driver begins a transaction only at its first write, so a read before that is not protected.
- **What a target's agent can run is decided by `services/jobs.job_methods` alone.** Check-in issues jobs by it, and the scan-target answer's `runnable_methods` (`jobs.runnable_methods`, from `scans.targets_out`) applies it on read to the interfaces the agent last reported: `[]` when no job would be issued, null when not known (no agent, or no accepted check-in yet). Nothing stores it. Beside it the answer dates that evidence: `agent_checkin_at` is the agent's `last_checkin_at` and `agent_checkin_refused` whether that check-in was refused (`last_error` set), since a refused check-in moves the time but not the interfaces; both null with `runnable_methods`. The list reads the targets' agents and subnets in one statement each per chunk of `scans._IN_BATCH` (500) distinct ids, never per target: six statements up to 500 (`test_the_list_costs_the_same_statements_for_any_number_of_targets`), a fixed number more per chunk past it (`test_the_list_grows_by_a_fixed_number_of_statements_per_chunk`). No statement binds more than a chunk's ids, so the SQLite build's parameter limit does not bound the list (`test_the_list_answers_for_more_targets_than_one_statement_can_bind` lowers both). The UI's two messages of spec §5.2 come from it alone, never from a job's `job_methods` or from the agent's interfaces, and the time beside them from `agent_checkin_at`, never from the agents list. A time more than one check-in interval ahead of the browser's clock is freshness not known, never "0s ago" or recent, by the one rule the Agents page's status dot uses (`agents.serverAge`, `AHEAD_WITHIN_MS`). The scan-target answer is REST only: no MCP tool returns it (`test_no_mcp_tool_serves_the_scan_target_answer`).
- **Schema changes are additive only** — new nullable columns or new tables. `database._add_missing_columns` auto-migrates existing databases on startup; there is no migration framework, so never rename/drop columns or add non-nullable ones without a default.
- **Response shapes**: `{"data": ...}` on success, `{"error": {"code", "message"}}` on failure. Domain errors raise `ApiError` (`api/app/errors.py`); never return bare HTTPExceptions from services.
- **Datetimes in responses are UTC with their offset** (`+00:00`), on REST and MCP alike (brief §4.3), because SQLite reads a stored value back without its zone. Every datetime field of a response model in `schemas.py` is `schemas.UtcDatetime`, never a bare `datetime`; request models keep `datetime`, since their `model_dump()` goes to the ORM. `test_every_datetime_field_in_the_schemas_is_serialised_with_an_offset` holds it. Every model `schemas.py` defines is a response model unless its `REQUEST_MODELS` lists it (`test_request_models_lists_only_models_a_request_is_validated_against` refuses a listed model that no request body is validated against). The walk follows each field's annotation (nested, in a list, tuple, set, dict or optional; a root model; a computed field's return annotation) to every model it reaches, wherever defined, so an `agent_protocol` model inside an owner response (`ScopeRangeOut` inherits `ScanRange`) is held to the rule. Each datetime is given a value as SQLite returns it and must dump with `+00:00` in both modes. It does not see a field typed `dict` or `Any` (a change's snapshots get their offset from `changes.snapshot`, which its own test checks), a serializer on the model that holds a computed field, the branches of a union after the first, or what a route or tool really returns: it starts at the models `schemas.py` defines, and `test_no_route_or_tool_serves_a_model_outside_the_walks_roots` pins only what the routers under `app.routers` declare as a `response_model` and that every MCP tool advertises a `dict` output. Its docstring lists the annotation shapes it supports and the rest. A host write that repeats the stored `last_seen` as the same instant, in any offset, is not a change (`hosts.update_host` compares instants with the stored column, not the answer's later scan time, before assigning), so `updated_at` stays. A datetime a service puts into an answer itself goes through `times.utc` (`changes.snapshot`, `scans.scan_request_out`). The UI reads every server datetime through `parseServerTime` (`web/src/utils/time.js`), never `new Date(value)`. The agent wire (`agent_protocol.py` and the answers of `/api/v1/agent/*`) keeps its own shapes, outside this rule.
- **One request-body cap, defined once: `body_limit.BODY_MAX` (2 MiB), with a budget and a deadline beside it.** `BodyLimitMiddleware` is the outermost middleware the app adds (`main.py` adds it last; `test_the_cap_wraps_the_whole_app` checks), so it runs before routing, before any authentication dependency or FastMCP's `auth=`, and before any body is parsed, on every route, `/mcp` included. A declared `Content-Length` over the cap is `413 PAYLOAD_TOO_LARGE` with nothing read, and only a request with no `Transfer-Encoding` is trusted to its declared length. The length is read as the HTTP server hands it on, which under httptools (the image's parser) can carry spaces or tabs at either end and any number of leading zeroes: `body_limit._length_digits` drops both, and `_over` compares the digits with the cap by their count before converting any, so Python's 4,300-digit `int()` guard stays on and is never reached. Any other body is counted as it is read and refused at the chunk that would pass the cap, so up to the cap of it is held before authentication. No route reads past it or sets a cap of its own; a route that needs a higher one names it in the brief with the measurement that justifies it. The default was measured from the largest legitimate requests (brief §4.3): lowering it below a full result set (about 1.3 MB) changes what an agent of the current protocol can send. The same middleware bounds all bodies together (#90): the body bytes of every request in progress, read by it or by the route, total at most `body_limit.BODIES_MAX` (16 MiB), counted until the request ends and not only until it authenticates, because FastAPI parses a `Body` before the route's dependencies run (check-in and the owner routes read before their credential); a chunk past it is `503 UNAVAILABLE`, the cap checked first. A body costs its bytes, not its chunk count: one buffer when the middleware reads it, blocks of at least 64 KiB (`body_limit._BLOCK`, the last excepted) when the route does (`test_a_body_in_tiny_chunks_costs_its_bytes_not_its_chunks`). A body not received whole within `body_limit.BODY_TIMEOUT_S` (60 s) of its headers is `408 REQUEST_TIMEOUT`, timed as a whole and never per chunk, and reads after the body is whole are not timed; the deadline stays above the agent's own 30 s (`client.REQUEST_TIMEOUT_S`). Every refusal closes the connection, and so does any response the app starts before its body was received whole. A body the route is reading is refused by the middleware's own answer, after which the route gets `http.disconnect`, its sends are dropped, and its `ClientDisconnect` ends in the middleware. `test_many_stalled_bodies_hold_no_more_than_the_budget` and `test_on_uvicorn_many_stalled_bodies_stay_within_the_budget` hold the budget. Per-client limits, request headers (size and time), idle connections and the number of connections are the proxy's (brief §4.3), not the app's.
- **The owner key is checked only through `auth.is_owner_key`**, which compares in constant time. REST takes it as `X-API-Key` (`require_api_key`: 401 missing, 403 wrong); `/mcp` takes it as `Authorization: Bearer` through FastMCP's `auth=` (`OwnerKeyVerifier`), never a hand-rolled ASGI middleware. An empty value never matches, and `config.load_settings` refuses to start with `API_KEY` unset, empty, the `change-me` placeholder, or with whitespace at either end (refused, never trimmed), in a fixed message that never contains the key. Credential refusals on `/mcp` are FastMCP's RFC 6750 401s, the one exception to the response shape above; a body over the cap is refused before the bearer is looked at, as the cap rule's `413` in the error shape (brief §5.1).
- **Enrolment tokens (`tlge_…`) are exchanged only at `POST /api/v1/agent/enrol`, by `services/enrolment.enrol`**, the one agent route reachable without a long-lived token: it sits on `routers/agent.enrol_router`, which holds nothing else and has no dependency (`test_the_one_agent_route_without_the_agent_token_is_enrol`), and never takes `require_agent` or the owner key. "Add agent" (`agents.create_agent`) creates the agent `pending` with one, re-enrol (`agents.re_enrol`, refused for a disabled agent) issues another and revokes the one it replaces; it, update (enable, disable, rename), revoke and delete read the agent and its tokens only once they hold the write lock (`agents._locked_agent`), so none acts on, or logs, an agent an exchange has since changed, and each lives `agents.ENROL_TOKEN_LIFETIME` (1 hour). The exchange checks the token by its SHA-256 (unused, unrevoked, before `expires_at`, agent not disabled) before it reads the body, then takes the write lock, reads the time, and claims it with a compare-and-set on `used_at` that repeats those conditions in SQL (a body can arrive slowly and the writer can be busy, so the time is the claim's, never the lookup's); in that one transaction it revokes the agent's live agent token, issues the new one, makes the agent `active`, stores the body's report (a field omitted or null leaves the stored value), prunes the agent's own audit entries to their cap, and writes no `last_used_at` on either token. It never uses `agents.authenticate` or `agents.token_in_use`, and refuses (`RuntimeError`) a session that carries an agent token's context (`agents.carries_agent_token`). A token is live while unrevoked and, for an enrolment token, unused and unexpired (`agents.live`); revoke, delete and re-enrol revoke live tokens only. Every attempt passes `enrolment.throttle` first: at most `THROTTLE_ATTEMPTS` (10) attempts that did not enrol in any `THROTTLE_WINDOW_S` (60 s), global, in process memory (one worker), refused `429` before any lookup or body read; an enrolment gives its place back.
- **Agent tokens (`tlga_…`) are authenticated only through `auth.require_agent`**, which finds the token by the SHA-256 of the presented bearer (`services/agents.authenticate`) and accepts only an unrevoked `agent` token of an `active` agent. `authenticate` only reads. The token's `last_used_at` is written by the route that serves the request, in that route's own transaction (`agents.record_token_use`, an `UPDATE` conditional in SQL on the stored time): check-in only once its claim succeeds, results ingest only for an accepted result set, so a request refused before it takes its check-in slot, or a refused result set, never writes it. A check-in refused with `409` or `422` has taken its slot and has written it, with `last_checkin_at` and `last_error`, by design. Neither route relies on that authentication alone: check-in's claim revalidates the agent's state and the token's revocation in SQL under the write lock, and results ingest takes the write lock and rechecks both (`results._credential_live`) before it touches the lease, so a result set authenticated before a disable, revoke, delete or re-enrol exchange committed is `403` with nothing stored (#21; the owner-revoke case was open before it). A write the database refuses on either route as an `OperationalError` is rolled back and answered `503 UNAVAILABLE` (`errors.database_unavailable`: logged with the SQLite error name, never SQL, parameters or the bearer; "busy" only for a lock). Three failures stay a bare 500: a failed rollback, a failure of the authentication `SELECT` itself, which cannot tell a usable token from a refused one, and a database error that is not an `OperationalError`. It alone guards `/api/v1/agent/*` but `enrol`, as a dependency of the router itself (`routers/agent.router`), which `main.py` mounts, with `enrol_router`, outside the `require_api_key` loop; those routes never take `require_api_key`, so the owner key does not reach them, and owner routes and `/mcp` never accept an agent token or an enrolment token. A plain token appears only in the response that issues it (an agent token in the enrol answer, an enrolment token in the create or re-enrol answer): the database holds its hash and display prefix, and `token_hash` stays out of audit snapshots (`changes._SNAPSHOT_EXCLUDE`) and every response model.
- **The agent wire contract is `api/app/agent_protocol.py`**, standard library and pydantic only: every request and response shape of `/api/v1/agent/*` (enrolment's `EnrolRequest`/`EnrolResponse` included, and the two token prefixes; `agent/tests/test_contract.py` checks the agent's `config.TOKEN_PREFIX` against `AGENT_TOKEN_PREFIX`), the caps on agent-reported fields (trimmed, length-capped, printable-only), and the sanitising of what a scan reports (`rdns_name`, `scan_error`). A change that an agent of the current protocol would send or read differently raises `PROTOCOL_VERSION`. A job carries at most `DNS_SERVERS_MAX` DNS servers (3, the agent's `probe.MAX_DNS_SERVERS`; `agent/tests/test_contract.py` checks they match), the first of the subnet's in the order listed, whatever the subnet stores; the owner API takes at most `schemas.SUBNET_DNS_SERVERS_MAX` (8) for a subnet, in `services/subnets`, which lets an update resend a longer list stored before that bound unchanged. A job's `cidr` is `ipnet.canonical_cidr` of the subnet's, whatever the row holds (a subnet stored before #97 may hold a spelling longer than the agent's 64 characters). The largest check-in answer the server can build, whatever spelling and list a subnet stores, stays inside the agent's `client.RESPONSE_MAX`, and `agent/tests/test_answer_limit.py` builds it from both sides' bounds and from a subnet stored with both at their longest. Check-in (`services/jobs.checkin`) checks `protocol` before the rest of the body and records a refusal in the agent's `last_error` by field name, never by value. A check-in inside `jobs.MIN_CHECKIN_GAP` of the last is `429` and changes no row: refused from the agent row loaded at authentication with no write statement, or by the claim (`jobs._claim`, a compare-and-set on `last_checkin_at` that also requires the agent `active` and the token unrevoked, whose losing statement matches no row). The order is fixed: the loaded row's gap is checked first, so a check-in whose loaded row is inside it is `429` whatever the owner committed since (the next request meets the disable, revoke or delete as a `403` at authentication); a check-in the loaded row lets through reaches the claim, which under the write lock answers `403` when the owner's disable, revoke or delete has landed (even if another check-in also took the slot) and `429` when only the slot is gone. The claim is the check-in's first write; the token's use (at most once per `agents.LAST_USED_GRANULARITY`) is recorded in its transaction, and the agent row is then refreshed whole, so the check-in's audit snapshots and `actor` are the committed name and state. A token used at request rate drives no writes. A job lease is a compare-and-set on the lease the check-in read, keeps the methods issued (`job_methods`), and an agent holding a live lease gets no second job. That is read from the agent's own `current_job_id`/`job_issued_at`, never from its targets, which the owner may reassign or delete mid-scan. Results ingest (`services/results.ingest`) accepts a result set only from an agent still `active` presenting a token still unrevoked, read under the write lock, and only while its `job_id` is both a target's and the reporting agent's `current_job_id`, clears both copies in one transaction (each a compare-and-set on that job, so a second result set is refused), keeps the attempt time by setting `last_scan_at` to the job's `job_issued_at`, and judges liveness, MACs and names by `job_methods`, never by what the agent says it ran. Only a `complete` result set from a job issued a liveness method marks addresses dead, and only a `complete` one clears a stored `rdns_name`: in an incomplete one a record without a name leaves the stored name, since its lookup may never have run. Ingest builds and UTF-8-encodes its answer before the commit, which guards the answer's construction and encoding, not its delivery; a failure there is rolled back and answered `500 INTERNAL_ERROR` in the error shape (`errors.internal_error`). The request-scan cooldown lives in `services/scans.request_scan`, applies to every caller (UI, REST, and MCP's `request_scan`), and is a compare-and-set as well.
- **Scan ingest never writes `hosts`** (spec §7.2, invariant 3), and writes nothing to the change log. `services/results` imports neither the host model, the hosts service nor `changes`, and `test_results.py` checks that no such name is bound in the module's namespace (`test_the_ingest_module_binds_neither_hosts_nor_the_change_log`). That check does not follow imports: `results` calls `agents.record_token_use` and `scans`, whose modules import `changes`, so that those helpers write no host and no change entry on the ingest path rests on `test_ingest_writes_no_host_and_no_change_entry`, which counts the rows. Scan data reaches hosts only through the owner accepting a finding (#15), which goes through the hosts service. A host response's `last_seen` joins in the observation's `last_seen_at` on read (`hosts.hosts_out`, one query per batch, never from `alive`), so the stored column keeps meaning "set by hand".
- **Findings are computed on read, never stored** (`services/findings`, spec §5.5), from hosts and observations inside the scan scope; only dismissals are stored (`finding_dismissals`). Accept and dismiss take a finding's key `(subnet_id, ip, type, observed)`, take the write lock (`scans.take_write_lock`) and only then recompute the finding, and write nothing for a key that no longer names a current finding (`skipped`, `changed`). Accept also requires the finding's `fingerprint`, a digest of the key, the host and `proposed`, because the key alone does not say what is written (an `unknown_host`'s name and status). A name accept makes the host's FQDN the PTR name, with a domain override in `proposed` when the name is outside the effective domain. Accept writes only through `hosts.create_host`/`update_host`, with `finding=` set to the type, so the hosts service's own audit entry names the address and the finding, never the hostname or MAC the network supplied. A dismissal's summary is a count; its keys go in `after`. Dismissals deleted because their address left scope go with that change's own entry, as observations do.
- **Strings from the network or a client are sanitised at ingest and never interpolated into change summaries by the paths that carry them in** (spec §7.2, invariant 8): ingest writes no change entry, a check-in's summary names fields and not values, and accepting a finding names the address and the type (`finding=` on the hosts service). A value the owner writes into a host is owner data from then on: an MCP `create_host`/`update_host` is an ordinary host write even when an assistant copied the hostname from a finding, and its summary names the host by it, as every host summary does (the owner's decision, #79; the two docstrings say so). `rdns_name` is kept only if it is a DNS hostname, lowercased, and is otherwise dropped whole (`agent_protocol.rdns_name`); check-in fields are trimmed, capped and printable-only; a result set's `error` is made printable and capped (`agent_protocol.scan_error`) and kept out of audit snapshots (`changes._SNAPSHOT_EXCLUDE`); OAuth client names (M3) follow the same rule. A refusal names the field, never the value.
- **The agent never executes, downloads or updates from anything the server sends** (spec §7.2, invariant 1). Its code comes from the published release (the image; the wheel from M2b), never from the server. A job is data in a fixed vocabulary, parsed by `agent/src/tlg_ipam_agent/protocol.parse_job`. `agent/tests/test_invariants.py` is a tripwire, not a proof of the invariant. It shows only that every agent module imports modules on its allowlist and contains none of its listed names (as a call, attribute, bare name or string): names that start a process, load or evaluate code, reach attributes by computed name or write a file. Code that reaches the same effect without a listed name (`os.__getattribute__("sy" + "stem")`, say) passes it, so review is still what holds the invariant. A new import or listed name is a review decision: change the list in the same PR and say why. No agent module opens a file itself: `open` is a listed name in every spelling, `os.open` included. For files, the checks enumerate named spellings of having a library open one: the ways to write are listed names, and the reads (pathlib's `read_text`, dnspython's `read_resolv_conf`) are held to the modules `test_files_are_opened_only_where_listed` names, as is a file named through an allowed module's keyword (`cafile`, `capath`, `certfile`, `keyfile`, `filename`), read or written (`logging.basicConfig(filename=…)` writes), written out or as a string in `**{…}`. They do not see a keyword built at run time, an allowed module's own way of opening a file under another name, or what a library opens inside a call, and they match names, not types, so harmless code sharing a name is flagged too (`test_what_the_file_checks_flag_that_opens_nothing`). Each refused case in `test_invariants.py` lists exactly the reasons it is refused for, so one check cannot stand in for another. Its dependencies are httpx, icmplib and dnspython only. Before any packet, `guard.plan` refuses a job whose subnet is outside `ALLOWED_CIDRS`, whose ranges leave the subnet, or that holds more than `OBSERVATIONS_MAX` addresses, and the refusal is reported as the result set's `error`. `probe.py` alone sends packets, to addresses `guard.plan` returned (and PTR queries to the job's DNS servers, or, when it names none, the addresses in the host's `resolv.conf`, read again for every job by `DnsResolver.servers` and never cached, off the event loop: `probe.read_resolv_conf` runs in one daemon thread at a time and lets dnspython open and parse the file only if `os.stat` finds a regular file of at most `RESOLV_CONF_MAX` bytes, a look before the open and not a bound on it (a file that grows after it is parsed whole; a FIFO swapped in after it blocks that one thread until a writer comes), and a read not done within `RESOLV_CONF_TIMEOUT_S`, or by the job's deadline, gives no server), and every datagram or ARP frame it sends takes a slot of the agent's one `MAX_PPS` budget first (`scan.Pacer`, which `loop.Agent` keeps from job to job). Each packet is handed to the kernel in the step of the event loop its slot is granted in: an ARP request, an echo request (each probe takes its own slot in `scan._Pool`, and icmplib sends before its first await, which `test_icmplib_send.py` checks), a DNS query on a `probe.QuerySocket` made before the slot. The budget bounds hand-offs: a slot ends when that step has ended (a callback `scan.Pacer` holds its turn for), and the next is granted at least `1/MAX_PPS` after that end, by the agent's clock, so a hand-off made late moves the next slot (#121); never caught up after a late wake, re-slept after an early one, waiters served in turn, and the event loop turns between any two grants. A packet the socket cannot take at once is a failed send, never kept to go later, and a lookup's socket is aborted as the lookup ends. The ARP the kernel sends itself to resolve an on-link address before an echo request (up to `mcast_solicit`, 3 by default, for an address that does not answer) is not the agent's send and is outside the budget, by name (spec §5.6), as is the time from the hand-off to the wire. It sends DNS queries itself, one per server, never through dnspython's resolver, and does not use a truncated reply. A lookup not made is not a lookup that found no name: a job with live addresses and no server to ask sends no DNS packet and is reported incomplete with `probe.NO_DNS_SERVER`, and a lookup that tried and sent its query to no server before its servers or its own time ran out raises `ProbeError`: the lookups still running are cancelled (`scan._Pool`'s `cancel_on_failure`, the PTR lookups' alone) and none starts after it, so no query is handed to a socket after it; a query a cancelled lookup had already handed over is the kernel's, and none is left with asyncio to send later, after the result set or in the next job (`test_a_query_the_socket_cannot_take_at_once_never_leaves_later`). The pool raises the failure ahead of the cancellations it caused, and the result set is incomplete, so the server keeps stored names. A lookup the job's deadline stops before its first attempt is the deadline's cut-off, not that error. ARP requests go from a raw `AF_PACKET` socket (`probe.PacketLink`) bound to the one interface whose network contains the job's subnet, one request and one retry per address. `probe.ArpSession` takes a reply only from an address it sent a request to, and its listener lets every other task run after each `ARP_RECEIVE_BATCH` frames, so a flood cannot hold the event loop. A send never waits for the socket to be writable. `arp.py` builds and reads the frames and opens no socket. `test_only_the_probe_module_opens_a_packet_socket` is a tripwire of the same kind: it sees which modules import `socket` (in any spelling) and which of its names they use, not what they do with them. Past a job's timeout, `loop.SCAN_GRACE_S` (30 s, on the event loop's clock) stops a scan that is still running and reports it as an error, so one stuck await cannot hold the worker until the lease runs out. `client.py` alone speaks HTTP, with TLS verification always on and no setting to turn it off, one deadline per request covering the whole answer, answers read undecoded (it asks for `identity` and refuses any other content encoding) with each network read checked against the 1 MiB cap before it is held, and success acted on only in each route's shape. The agent logs no text the server wrote (status, a vocabulary-shaped code, validated counts), and `loop.Redact` takes its token out of every log record. Only a `200` check-in answer queues a job; every other answer is handled by the refusal rule in spec §5.7 (`agent_protocol.CHECKIN_RETRY_*`). The agent does not import `api/app/agent_protocol.py` (pydantic is not among its dependencies): `agent/tests/test_contract.py` checks its copies of the constants and rules against it.
- **IP maths goes through `api/app/ipnet.py`** and Python's `ipaddress`. No string parsing, no `/24` assumptions — the codebase is deliberately IPv6-ready even though v1 is IPv4-only. `ipaddress` takes many spellings of one network (a dotted netmask, a host mask, a prefix padded with any number of zeroes), so a CIDR is compared as a network, never as a string, and is stored and sent in one spelling, `ipnet.canonical_cidr`: the subnet service stores it on every write that sends `cidr`, and a job and `findings.list_named` (its `subnet_cidr` and cursor) use it whatever an older row holds. No migration rewrites such a row; it keeps its spelling until a write sends `cidr`.
- **One uvicorn worker.** The image starts uvicorn with `--workers 1` in its `CMD`, so `WEB_CONCURRENCY` in the environment cannot raise the count (no other `--workers`, no replicas): MCP session state is per-process memory and SQLite has one writer. Reason in the brief §2.2; backup and restore procedure in `docs/backup-and-restore.md`.
- **Bulk endpoints report per-record results** (`created`/`skipped`/`error` + reason) and never abort the batch on a bad record.
- Frontend: shared reference data (sections, subnets, device types) comes from `TreeContext` (`web/src/context.jsx`) — call `refreshTree()` after any mutation that affects it. Checkboxes use the `.tlg-check` class; device icons come from the `ICONS` registry in `DeviceIcon.jsx`.

## Gotchas

- `/mcp` must work **without** a trailing slash (`MCPPathRewriteMiddleware` in `main.py`) — `mcp-remote` and most MCP clients request the bare path, and the SPA catch-all would otherwise swallow it. `test_mcp_reachable_without_trailing_slash` guards this.
- Some MCP clients (Claude Desktop, for one) snapshot the tool list at connect time — after server restarts that change tools, fully restart the client app (Cmd+Q, not just closing the window).
- The repo uses placeholder domains (`home.arpa`, `example.com`) in code, docs, and tests. Do not introduce the user's real domains.
