# TLG-IPAM

Homelab IPAM: FastAPI + SQLite backend, React SPA, and an MCP server at `/mcp` so AI assistants (Claude, ChatGPT, or any other MCP client) can query/update it. The full specification — data model, endpoints, MCP tool inventory, UI spec, acceptance criteria — lives in `TLG-IPAM-Project-Brief.md`. **Keep the brief in sync when behaviour changes**; it is the source of truth, not documentation theatre.

## Workflow

v0.2 (scan agents, remote MCP) is specified in `docs/v0.2-spec.md` and tracked as GitHub milestones M0–M3. The spec is the contract for work that has not shipped; the brief describes what `main` does.

- **Session start:** read the newest entry in `HANDOFF.md`. It holds live state: what is merged, in flight, broken, or waiting on the owner.
- **One issue, one branch, one PR.** Branch `<issue>-<slug>` from `main`. The PR closes the issue and carries in the same diff: the tests, the brief update for the behaviour it ships, and the `AGENTS.md` line for any invariant it adds or changes.
- **Green before the PR opens:** the commands CI runs (`.github/workflows/ci.yml`), locally.
- **The PR body is the record.** It opens with the authoring agent, model, and head sha, then **What**, **Deliberate calls**, **Tests**. `.agents/review-brief.md` holds the body shape; read it when opening a PR.
- **Merge needs green CI and every automatic review finding answered.** Codex and Greptile review each PR when it opens: fix each finding or reply on its thread with the reason it stands. The owner merges.
- **A briefed review round as well** for a PR that touches authentication, tokens, OAuth, agent ingest, or code that sends packets. It needs a GO from a reviewer in a different model family from the author; `.agents/review-brief.md` is how the round is briefed.
- **When the spec is wrong** (the code or a spike shows it), change `docs/v0.2-spec.md` in the same PR and list the change under Deliberate calls.
- **Session end:** add a `HANDOFF.md` entry using the template in its header. Hand-off entries commit straight to `main`, so the next session sees them without waiting on a PR. A session working in a worktree ends its final message with its entry, and the orchestrator commits it.
- **Orchestrating** (handing issues to other sessions and checking their results): read `.agents/orchestration.md` first.

`.agents/README.md` indexes the process material that is not needed on every turn.

## Commands

```sh
# Backend (one-time setup: python3 -m venv api/.venv && api/.venv/bin/pip install --require-hashes -r api/requirements-dev.txt)
cd api && .venv/bin/python -m pytest                  # test suite — run before declaring any backend change done
cd api && API_KEY=dev-key .venv/bin/uvicorn app.main:app --port 8080 --reload
cd api && API_KEY=dev-key .venv/bin/python -m app.serve --host 127.0.0.1   # as the image starts it: one worker, the header and idle limits, no reload
#   add STATIC_DIR=../web/dist to also serve the built SPA (single-origin, like production)

# Scan agent (one-time setup: python3 -m venv agent/.venv && agent/.venv/bin/pip install --require-hashes -r agent/requirements-dev.txt)
cd agent && .venv/bin/python -m pytest                # agent tests, incl. end-to-end against the real routes; sends no packet
docker build -f agent/Dockerfile -t tlg-ipam-agent:dev agent

# Frontend
cd web && npm run dev                                  # hot reload, proxies /api → :8080
cd web && npm run build                                # production bundle to web/dist

# Full stack (needs .env with API_KEY)
docker compose up --build
```

### Dependency lock

`api/requirements.txt` (runtime) and `api/requirements-dev.txt` (runtime + test) are **generated lock files**: every package pinned by version and hash, resolved for Python ≥ 3.12 on any platform. The Dockerfile and CI install them with `pip install --require-hashes`. Edit the direct dependencies in `api/requirements.in` / `api/requirements-dev.in` (`fastmcp` stays `>=4.1,<5`), never the lock files, then regenerate **both** from `api/` with [uv](https://docs.astral.sh/uv/):

```sh
uv pip compile requirements.in --universal --python-version 3.12 --generate-hashes --no-header -o requirements.txt
uv pip compile requirements-dev.in --universal --python-version 3.12 --generate-hashes --no-header -c requirements.txt -o requirements-dev.txt
#   append -P <package> to either command to upgrade just that package; -U to upgrade everything
```

Commit the `.in` and lock changes together. The `-c requirements.txt` constraint keeps shared packages at the same version in production and in tests.

Use uv **0.13.6**, the version CI pins. `uvx uv@0.13.6 pip compile …` runs it without changing the uv you have installed. The `locks` job in CI runs these two commands, verbatim, in a fresh checkout and fails if either lock changes. Because recompiling keeps every pin, and its hashes, that still satisfies the `.in` files, a newer upstream release does not make the job fail. Only a `.in` change committed without regenerating does that. When you change these commands, change the `locks` job's copy in `.github/workflows/ci.yml` too. The job fails if `AGENTS.md` no longer lists its commands word for word.

The scan agent has its own locks: `agent/requirements.txt` (what the agent image installs: httpx, icmplib, dnspython and their dependencies, for Python ≥ 3.11), `agent/requirements-dev.txt` (that plus the server's test set, so the agent's end-to-end tests run against the real routes in one environment), and `agent/requirements-build.txt` (what the release workflow builds and checks the wheel with: `flit_core` and `packaging`, #24). Edit `agent/requirements.in` / `agent/requirements-dev.in` / `agent/requirements-build.in`, keep `agent/pyproject.toml`'s `dependencies` the same as `requirements.in` and its `[build-system]` `requires` the same as the `flit_core` line of `requirements-build.in` (tests check both), and regenerate all three from `agent/`, **after** the server's locks:

```sh
uv pip compile requirements.in --universal --python-version 3.11 --generate-hashes --no-header -c ../api/requirements-dev.txt -o requirements.txt
uv pip compile requirements-dev.in --universal --python-version 3.12 --generate-hashes --no-header -c requirements.txt -c ../api/requirements-dev.txt -o requirements-dev.txt
uv pip compile requirements-build.in --universal --python-version 3.12 --generate-hashes --no-header -c ../api/requirements-dev.txt -o requirements-build.txt
```

All three are constrained to `api/requirements-dev.txt`, so a package the agent shares with the server (httpx, certifi, idna, dnspython, packaging) is the version the server's tests use. A server lock change that moves a shared package therefore fails the `locks` job until the agent's locks are regenerated in the same PR. The job's agent step checks these three commands against this file word for word, as it does the server's.

## Architecture invariants

- **All business logic lives in `api/app/services/`.** REST routers (`api/app/routers/`) and MCP tools (`api/app/mcp_server.py`) are thin wrappers over the same service functions. Never put validation or logic in a router or tool.
- **Every write is audit-logged** via `services/changes.record()` with the correct `source` (`ui`/`api`/`mcp`, or `agent` for a check-in that changes what an agent reports and for the enrolment exchange, `services/enrolment`, whose token and agent entries carry the agent's `actor`). A write path without a change-log entry is a bug, with four deliberate exceptions: heartbeats (`tokens.last_used_at`, `agents.last_checkin_at`), job scheduling (the lease columns on targets and agents), the cap that keeps each agent's own `source="agent"` entries to its newest 100 (`jobs.prune_agent_audit`, run by check-in and by the enrolment exchange; owner entries and token entries are never pruned), and scan results ingest (`services/results`: observations, their 90-day prune, and the target's last-scan columns). Observations deleted because a change narrowed scan scope go with that change's own entry. Over MCP, `list_changes` withholds agent-reported values in `agent` snapshots (`changes.assistant_view`). `actor` names who acted when that is narrower than the `source`; it is null for the owner key (spec §4.3). A name a client or agent declares goes in `actor`, never into `summary`.
- **MCP tools are hand-curated**, never auto-generated from OpenAPI. When adding or changing one: the docstring is the connected assistant's runtime documentation (write it for tool selection), update `EXPECTED_TOOLS` in `api/tests/test_mcp.py`, and update the tool table in the brief. MCP may only mutate hosts and reserved ranges, and ask for a scan — subnet/section deletion stays UI-only by design. No MCP tool creates, configures or lists agents, tokens or scan targets, MCP never gains scan-target or scan-scope configuration, and no MCP call can widen what is scanned (spec §7.2, invariant 2): `add_reserved_range` creates a scanned range (and, like every path that adds one, is refused once the subnet holds `schemas.SUBNET_RESERVED_RANGES_MAX` ranges, `services/subnets.create_reserved_range`, counted under the write lock), `delete_reserved_range` refuses a range with `scan_excluded` (`services/subnets.delete_reserved_range`, on `source="mcp"`), and `request_scan` sets only a configured target's `scan_requested_at`, under the cooldown every caller shares, so the scope the owner set is scanned sooner; it returns the request and `next_request_after` (`scans.scan_request_out`), never the target. `list_changes` still shows their audit entries. No tool checks scopes yet: #28 adds `ipam:write` to every write tool at once, `request_scan` included. `list_scan_findings` (`findings.list_named`) hands an assistant what devices reported (`observed`, `proposed`) as data, with `findings.NETWORK_REPORTED_NOTE` beside the list and the same warning in its docstring, and leaves out `dynamic` findings. It returns a page of at most `findings.PAGE_SIZE` findings, each at most `findings.FINDING_MAX` bytes, in a `findings` array of at most `findings.PAGE_BUDGET` bytes as sent, brackets and commas included, never the whole network, with `next_cursor` and the note on every page, both ahead of the findings. Every value a finding carries has a length bound (a domain suffix `ipnet.DOMAIN_MAX`, 253, since #86); a host whose effective domain was stored longer before it is listed with `host_fqdn` null (`findings._listed_fqdn`), never cut. One call runs at most `findings.CALL_STATEMENTS` statements, each reading at most `findings.SCAN_CHUNK` hosts and observations (`findings._read_chunk`) along the `(subnet_id, ip_int)` index of hosts, observations and dismissals, passing over no row it does not return: inside the DHCP pool, observations are read only at the chunk's hosts' addresses; the scope a visit needs (`scans.scan_scope`) reads the subnet's excluded reserved ranges along `ix_reserved_ranges_subnet_excluded`, never another subnet's or a scanned one, and at most `SUBNET_RESERVED_RANGES_MAX` of them but for a subnet stored with more before that limit, which is read whole (`test_no_statement_of_a_call_scans_or_sorts` holds the query plans of every statement but the subnet list, `test_unhosted_pool_observations_cost_no_work` and `test_every_read_of_a_call_does_bounded_work` the SQLite instructions, which count the rows a statement reads or passes over but not the bytes it returns or Python's processing, and `test_no_read_of_a_call_returns_text_the_listing_does_not_use` the bytes each statement returns, each with and without `subnet_id`, whose existence check reads the subnet's id alone, #133); the two exceptions to the bound are the one statement listing the subnets that can hold a finding and those legacy ranges, and reads at least one chunk; `next_cursor` is null only at the end of the listing, and is otherwise the page's last finding or, when the call reached the bound, the last address it examined, so a page can be short or empty with a cursor. A cursor's address past what a row can hold never reaches a statement. An unhosted observation in the DHCP pool is never read, so no cursor names its address; a stopped call's cursor is a host's address, an observation's outside the pool, or a bound of the pool. The comments on `PAGE_SIZE` and `CALL_STATEMENTS` give the measurements; `test_the_largest_finding_fits_its_bound`, `test_the_page_budget_is_held_at_its_exact_boundary`, `test_a_host_with_a_domain_stored_before_the_limit_is_listed_without_its_fqdn`, `test_one_call_costs_at_most_the_statement_bound` and `test_a_walk_that_stops_early_still_lists_every_finding_once` hold them, and every page the tests read is checked against all three bounds (`test_mcp.scan_page`). That `request_scan` changes only `scan_requested_at` rests on `test_mcp_request_scan_changes_only_the_request_time`, which compares every column of every table, and its refusals change none. There is no accept or dismiss tool: an assistant resolves a finding with `create_host`/`update_host`, which its fingerprint does not bind.
- **Scan scope is computed in one place, `services/scans.scan_scope`** (spec §7.2, invariant 4): usable addresses minus the DHCP pool (unless the target's `scan_dhcp_pool`) minus reserved ranges with `scan_excluded`, and exclusion wins over a scanned range. Job creation, ingest validation, findings and the UI call it; nothing else works scope out, and no packet goes to an address outside it. The UI has it from the scan-target answer (`scans.targets_out`, which reads the scope's inputs for all the targets it answers for at once through `scans._scopes_as_committed`, the one reader of them, in chunks of `scans._IN_BATCH` distinct subnet ids, each chunk reading all three inputs of each of its subnets, so no subnet's scope is put together from two chunks; `scan_scope` is its one-subnet case, one chunk of the same three statements, and `test_each_subnet_gets_its_own_scope_in_any_order_of_ids_and_across_chunks` holds every subnet's scope to it in any order, with repeats, at every chunk size), whose ranges carry their bounds as integers (`start_int`, `end_int`) beside the addresses, and places a host by comparing its `ip_int` with them, never by parsing an address. Observations and finding dismissals exist only inside it: results ingest rejects an address outside the scope at ingest, and every write that can narrow it (pool scanning off, target deleted, a range excluded or added excluded, pool or CIDR edited) calls `scans.drop_out_of_scope` in its own transaction. `scan_scope` reads its inputs as committed columns, never from objects the caller loaded and never refreshing them, and a caller that writes on the strength of the scope holds SQLite's write lock first: `drop_out_of_scope` takes it itself (`scans.take_write_lock`), ingest before it rechecks the request's credential and its lease compare-and-set, check-in after `jobs._claim`. The driver begins a transaction only at its first write, so a read before that is not protected.
- **What a target's agent can run is decided by `services/jobs.job_methods` alone.** Check-in issues jobs by it, and the scan-target answer's `runnable_methods` (`jobs.runnable_methods`, from `scans.targets_out`) applies it on read to the interfaces the agent last reported: `[]` when no job would be issued, null when not known (no agent, or no accepted check-in yet). Nothing stores it. Beside it the answer dates that evidence: `agent_checkin_at` is the agent's `last_checkin_at` and `agent_checkin_refused` whether that check-in was refused (`last_error` set), since a refused check-in moves the time but not the interfaces; both null with `runnable_methods`. The list reads the targets' agents and subnets in one statement each per chunk of `scans._IN_BATCH` (500) distinct ids, never per target: six statements up to 500 (`test_the_list_costs_the_same_statements_for_any_number_of_targets`), a fixed number more per chunk past it (`test_the_list_grows_by_a_fixed_number_of_statements_per_chunk`). No statement binds more than a chunk's ids, so the SQLite build's parameter limit does not bound the list (`test_the_list_answers_for_more_targets_than_one_statement_can_bind` lowers both). The UI's two messages of spec §5.2 come from it alone, never from a job's `job_methods` or from the agent's interfaces, and the time beside them from `agent_checkin_at`, never from the agents list. A time more than one check-in interval ahead of the browser's clock is freshness not known, never "0s ago" or recent, by the one rule the Agents page's status dot uses (`agents.serverAge`, `AHEAD_WITHIN_MS`). The scan-target answer is REST only: no MCP tool returns it (`test_no_mcp_tool_serves_the_scan_target_answer`).
- **The guided install is rendered by the page from fixed names, and the server only reads for it** (#23, spec §5.6). Every command the Agents page shows comes from `web/src/utils/install.js`, pinned to the server's version from `GET /health` (`install.releaseVersion`, else `<version>`), and `web/src/utils/install.test.js` holds each to the spec's install and update tables, read from `docs/v0.2-spec.md` itself: change the spec's shapes and the builders together. No command holds an agent token (`tlga_…`); the enrolment token is in the container command alone, and the systemd install takes it on standard input. Which pages are warned that they are served over plain HTTP is `install.agentServerUrl`'s rule alone, read through `EnrolmentSteps.serverUrlFor`, at every step: before a token is issued (`PlainHttpBeforeIssue`, Add agent's form and re-enrol's confirmation, which still issue it), beside it, and with the update commands (`PlainHttpWarning`); `web/` parses no address for it (#92). The agent flags are computed on read by `agents.agent_out`, which every owner answer for an agent goes through: `update_available` (PEP 440, `packaging`, against `settings.version`), `protocol_mismatch` (`last_error` starts with `agents.PROTOCOL_MISMATCH_PREFIX`, which `jobs._protocol_error` uses) and each token's `expires_in_s` (`agents.expires_in_s`: the seconds a token `agents.live` holds has left by the server's clock, else null). The page judges an enrolment token open, and its time left, from `expires_in_s` less the time since it requested the list by the monotonic clock (`agents.monotonicNow`, `sinceAsked`, `enrolmentLeft`), never from `expires_at` or the wall clock, schedules the next change on its own timer (`agents.nextEnrolmentChange`), not on the list refresh, and never shows a disabled agent's as open (#143). `install.releaseVersion` takes no number with a leading zero, and `install.test.js` reads its cases from `agent/tests/test_release.py`, strictly (a line it cannot read exactly as Python does, an escape included, fails it), so the page and the release check judge one list. The scan offers are `scans.suggestions` (`GET /scan-targets/suggestions`): read-only, two statements whatever the data holds, an `active` agent's last reported interfaces judged by `jobs.l2_local`, subnets with no scan target only; accepting one is the ordinary `POST /scan-targets`. Neither reaches MCP (`test_no_mcp_tool_serves_suggestions_or_the_flags`).
- **One version, released from a tag** (#24, spec §5.6). The server's `VERSION` (`api/app/version.py`) and the agent's `__version__` are one string, a PEP 440 public version in normal form with no local part or epoch (`install.releaseVersion` takes it), held by `agent/tests/test_release.py` and `web/src/utils/install.test.js`. `settings.version` is a class attribute read from it, never from the environment, so a server reports the release it runs and `update_available` compares against that. A release is the tag `v<version>` on a commit of `main`. `.github/workflows/release.yml` builds the wheel (`python -m flit_core.wheel`, tools from `agent/requirements-build.txt`) and the image (linux/amd64 and linux/arm64, one OCI archive), checks both (`.github/scripts/release_check.py`; `check-agent-image.sh`, `--network none`, on each platform), and only for a pushed tag publishes them under exactly the names `install.js` renders, then fetches both with no credential as the install commands do. Only its two publish jobs hold a write permission, one each (`packages: write`, `contents: write`); they check out nothing and publish the build job's files by the digests it recorded, and a version already published with other content is refused, never overwritten. Every action is pinned to a commit and every image the build runs to a digest; a pull request's run, or one by hand, never reaches a job that can publish. `test_release.py` holds the workflow's triggers, permissions and pins, and `install.test.js` its two names. `test_release_publish.py` runs the two publish jobs' `run` scripts as the workflow holds them, with stand-ins for `gh`, `skopeo` and `sleep` (`agent/tests/release_stubs.py`) first on a `PATH` that holds only them and four text tools, and checks what each pushes and leaves for every answer it handles: a registry error is never taken for absence, a version published with other content is never pushed over, a draft an interrupted run left is published, and whichever release `gh`'s lookup returns when a draft and a published release share a tag, no wheel is replaced. A DEBUG trap (`TRACE`) records the commands bash runs in a step, and `Publish.run` fails on one whose word is not a listed shell builtin, a stub, a tool or the script's own function, whatever the step did with its stderr or exit status; every line of each script that holds a command runs in some test (`test_every_line_of_each_publish_script_runs_in_some_test`). It is a tripwire for changes made in good faith, not a sandbox: it judges each command by its text after the step has run and stops nothing, and a script written to get past it can (it does not see a step writing to the trace file, any redirection's target such as `/dev/"tcp"/…`, or an `EXIT` trap's handler), which is what review of the workflow's diff is for. The build's `release` artefact, the publish jobs' only input, is configured to be kept 7 days. A failed publish is finished by re-running the failed jobs while it remains; that a re-run attempt can download it is assumed until the first release measures it (`.agents/releases.md`, checklist step 5). Once the image is published, past that window or after a rebuild, the version is spent and the next one is released. `.agents/releases.md` is the checklist.
- **Schema changes are additive only** — new nullable columns, new tables or new indexes. `database._add_missing_columns` and `database._add_missing_indexes` auto-migrate existing databases on startup (an index declared on an existing table is created there, once; `create_all` makes indexes only with their table); there is no migration framework, so never rename/drop columns or add non-nullable ones without a default.
- **Response shapes**: `{"data": ...}` on success, `{"error": {"code", "message"}}` on failure. Domain errors raise `ApiError` (`api/app/errors.py`); never return bare HTTPExceptions from services.
- **Datetimes in responses are UTC with their offset** (`+00:00`), on REST and MCP alike (brief §4.3), because SQLite reads a stored value back without its zone. Every datetime field of a response model in `schemas.py` is `schemas.UtcDatetime`, never a bare `datetime`; request models keep `datetime`, since their `model_dump()` goes to the ORM. `test_every_datetime_field_in_the_schemas_is_serialised_with_an_offset` holds it. Every model `schemas.py` defines is a response model unless its `REQUEST_MODELS` lists it (`test_request_models_lists_only_models_a_request_is_validated_against` refuses a listed model that no request body is validated against). The walk follows each field's annotation (nested, in a list, tuple, set, dict or optional; a root model; a computed field's return annotation) to every model it reaches, wherever defined, so an `agent_protocol` model inside an owner response (`ScopeRangeOut` inherits `ScanRange`) is held to the rule. Each datetime is given a value as SQLite returns it and must dump with `+00:00` in both modes. It does not see a field typed `dict` or `Any` (a change's snapshots get their offset from `changes.snapshot`, which its own test checks), a serializer on the model that holds a computed field, the branches of a union after the first, or what a route or tool really returns: it starts at the models `schemas.py` defines, and `test_no_route_or_tool_serves_a_model_outside_the_walks_roots` pins only what the routers under `app.routers` declare as a `response_model` and that every MCP tool advertises a `dict` output. Its docstring lists the annotation shapes it supports and the rest. A host write that repeats the stored `last_seen` as the same instant, in any offset, is not a change (`hosts.update_host` compares instants with the stored column, not the answer's later scan time, before assigning), so `updated_at` stays. A datetime a service puts into an answer itself goes through `times.utc` (`changes.snapshot`, `scans.scan_request_out`). The UI reads every server datetime through `parseServerTime` (`web/src/utils/time.js`), never `new Date(value)`. The agent wire (`agent_protocol.py` and the answers of `/api/v1/agent/*`) keeps its own shapes, outside this rule.
- **One request-body cap, defined once: `body_limit.BODY_MAX` (2 MiB), with a budget and a deadline beside it.** `BodyLimitMiddleware` is the outermost middleware the app adds (`main.py` adds it last; `test_the_cap_wraps_the_whole_app` checks), so it runs before routing, before any authentication dependency or FastMCP's `auth=`, and before any body is parsed, on every route, `/mcp` included. A declared `Content-Length` over the cap is `413 PAYLOAD_TOO_LARGE` with nothing read, and only a request with no `Transfer-Encoding` is trusted to its declared length. The length is read as the HTTP server hands it on, which under httptools (the image's parser) can carry spaces or tabs at either end and any number of leading zeroes: `body_limit._length_digits` drops both, and `_over` compares the digits with the cap by their count before converting any, so Python's 4,300-digit `int()` guard stays on and is never reached. Any other body is counted as it is read and refused at the chunk that would pass the cap, so up to the cap of it is held before authentication. No route reads past it or sets a cap of its own; a route that needs a higher one names it in the brief with the measurement that justifies it. The default was measured from the largest legitimate requests (brief §4.3): lowering it below a full result set (about 1.3 MB) changes what an agent of the current protocol can send. The same middleware bounds all bodies together (#90): the body bytes of every request in progress, read by it or by the route, total at most `body_limit.BODIES_MAX` (16 MiB), counted until the request ends and not only until it authenticates, because FastAPI parses a `Body` before the route's dependencies run (check-in and the owner routes read before their credential); a chunk past it is `503 UNAVAILABLE`, the cap checked first. A body costs its bytes, not its chunk count: one buffer when the middleware reads it, blocks of at least 64 KiB (`body_limit._BLOCK`, the last excepted) when the route does (`test_a_body_in_tiny_chunks_costs_its_bytes_not_its_chunks`). A body not received whole within `body_limit.BODY_TIMEOUT_S` (60 s) of its headers is `408 REQUEST_TIMEOUT`, timed as a whole and never per chunk, and reads after the body is whole are not timed; the deadline stays above the agent's own 30 s (`client.REQUEST_TIMEOUT_S`). Every refusal closes the connection, and so does any response the app starts before its body was received whole. A body the route is reading is refused by the middleware's own answer, after which the route gets `http.disconnect`, its sends are dropped, and its `ClientDisconnect` ends in the middleware. `test_many_stalled_bodies_hold_no_more_than_the_budget` and `test_on_uvicorn_many_stalled_bodies_stay_within_the_budget` hold the budget. Below the app, where no middleware sees a request before its head is complete, the image's server (`python -m app.serve`) runs uvicorn's httptools parser through `header_limit.HeaderLimitProtocol`. A head (request line, header lines, blank line) is measured by its bytes as received, whatever its spelling, from the byte after the previous request ended: past `header_limit.HEADER_MAX` (64 KiB) it is `431 HEADERS_TOO_LARGE` with the connection closed and the app not called, with at most one byte past the limit parsed. To count exactly, reads reach the parser in pieces of at most `_PIECE` (4 KiB), cut at the end of each head (its first CRLF CRLF, once per head: `_head_cut`, since the parser skips blank lines before a request line) and of each declared-length body, and of one byte at the limit; a head after a chunked body in the same piece is the one case counted from the piece's start, at most 4 KiB over. No cut a sender can multiply: the parser gets one piece per read, as in uvicorn, plus at most one per `_PIECE` and three per request (`test_no_body_a_sender_chooses_costs_more_than_a_piece_per_4_kib`); cutting chunked bodies at each CRLF CRLF cost 1.3 s of parsing for a 1.9 MB body of them. A head over the limit pipelined behind a response in progress, finished or not, drops the connection with nothing written into or queued behind that response. A connection that has not delivered a head whole within `header_limit.HEADER_TIMEOUT_S` (10 s) of opening, or of its last request being both received and answered, is closed without an answer; a response in progress (an MCP event stream) is never timed by it. uvicorn's keep-alive (`serve.KEEP_ALIVE_S`, 5 s) is not enough alone: it is armed only after a response and cancelled by the next byte. While a request is queued behind the one being answered, nothing more is parsed or read: the transport wrapper (`header_limit._Transport`) holds back uvicorn's `resume_reading`, which a request being answered calls when it asks for its body. A second request completing in the piece a chunked body ended in stops the taking of requests (`_stop_taking`). A refusal by the parser follows one rule (`send_400_response`): uvicorn's `400` only when the refused request is the only one owed an answer (`_owed`, from `_taken`, the requests taken in order: uvicorn keeps no reference to the one being answered once another is queued); otherwise the taking stops, the refused request is dropped without running (taken out of `pipeline`), and the earlier answers are sent in order, the last closing the connection: with `Connection: close` if its answer has not started, at the end of its frame if its head has gone. `test_on_the_image_every_request_received_before_a_refusal_is_answered_first` holds it over 30 rows (first request × where the malformed bytes are × one write or split). A response paused with its send buffer full for `header_limit.STALL_TIMEOUT_S` (60 s), and a closed connection whose client takes none of what it holds for as long, are aborted (`close()` waits for a flush): every `close` passes through the protocol's transport wrapper (`header_limit._Transport`), so uvicorn's own closes are timed too. `test_header_limit.py` holds each, in process (a fake transport chooses how bytes split into reads) and against the image's server on loopback. No concurrency limit is set: uvicorn's counts idle connections and answers everyone past it `503`. Per-client limits on request rate and requests in progress, a cap on one client's sockets (the firewall's, by source address, so per client only where clients connect directly: nginx's `limit_conn` counts only connections whose whole head has been read), the number of connections, and a client that keeps reading slowly are in front of the server (brief §4.3; spec §8 says how to check each), not the app's; no timeout on a whole response belongs where `/mcp` is served.

The order is fixed: the loaded row's gap is checked first, so a check-in whose loaded row is inside it is `429` whatever the owner committed since (the next request meets the disable, revoke or delete as a `403` at authentication); a check-in the loaded row lets through reaches the claim, which under the write lock answers `403` when the owner's disable, revoke or delete has landed (even if another check-in also took the slot) and `429` when only the slot is gone. The claim is the check-in's first write; the token's use (at most once per `agents.LAST_USED_GRANULARITY`) is recorded in its transaction, and the agent row is then refreshed whole, so the check-in's audit snapshots and `actor` are the committed name and state. A token used at request rate drives no writes. Results ingest (`services/results.ingest`) accepts a result set only from an agent still `active` presenting a token still unrevoked, read under the write lock, and only while its `job_id` is both a target's and the reporting agent's `current_job_id`, clears both copies in one transaction (each a compare-and-set on that job, so a second result set is refused), keeps the attempt time by setting `last_scan_at` to the job's `job_issued_at`, and judges liveness, MACs and names by `job_methods`, never by what the agent says it ran. Each result set is judged by the rule of the protocol it names (`ResultsRequest.protocol`, one of `RESULTS_PROTOCOLS`, absent meaning 1, so a job leased to an agent of protocol 1 before the server was upgraded is still ingested by protocol 1's rule; #100). Its code comes from the published release (the image; the wheel from M2b), never from the server. Code that reaches the same effect without a listed name (`os.__getattribute__("sy" + "stem")`, say) passes it, so review is still what holds the invariant. A new import or listed name is a review decision: change the list in the same PR and say why. For files, the checks enumerate named spellings of having a library open one: the ways to write are listed names, and the reads (pathlib's `read_text`, dnspython's `read_resolv_conf`) are held to the modules `test_files_are_opened_only_where_listed` names, as is a file named through an allowed module's keyword (`cafile`, `capath`, `certfile`, `keyfile`, `filename`), read or written (`logging.basicConfig(filename=…)` writes), written out or as a string in `**{…}`. Before any packet, `guard.plan` refuses a job whose subnet is outside `ALLOWED_CIDRS`, whose ranges leave the subnet, or that holds more than `OBSERVATIONS_MAX` addresses, and the refusal is reported as the result set's `error`. `probe.py` alone sends packets, to addresses `guard.plan` returned (and PTR queries to the job's DNS servers, or, when it names none, the addresses in the host's `resolv.conf`, read again for every job by `DnsResolver.servers` and never cached, off the event loop: `probe.read_resolv_conf` runs in one daemon thread at a time and lets dnspython open and parse the file only if `os.stat` finds a regular file of at most `RESOLV_CONF_MAX` bytes, a look before the open and not a bound on it (a file that grows after it is parsed whole; a FIFO swapped in after it blocks that one thread until a writer comes), and a read not done within `RESOLV_CONF_TIMEOUT_S`, or by the job's deadline, gives no server), and every datagram or ARP frame it sends takes a slot of the agent's one `MAX_PPS` budget first (`scan.Pacer`, which `loop.Agent` keeps from job to job). Each packet is handed to the kernel in the step of the event loop its slot is granted in: an ARP request, an echo request (each probe takes its own slot in `scan._Pool`, and icmplib sends before its first await, which `test_icmplib_send.py` checks), a DNS query on a `probe.QuerySocket` made before the slot. The budget bounds hand-offs: a slot ends when that step has ended (a callback `scan.Pacer` holds its turn for), and the next is granted at least `1/MAX_PPS` after that end, by the agent's clock, so a hand-off made late moves the next slot (#121); never caught up after a late wake, re-slept after an early one, waiters served in turn, and the event loop turns between any two grants. A packet the socket cannot take at once is a failed send, never kept to go later, and a lookup's socket is aborted as the lookup ends. The ARP the kernel sends itself to resolve an on-link address before an echo request (up to `mcast_solicit`, 3 by default, for an address that does not answer) is not the agent's send and is outside the budget, by name (spec §5.6), as is the time from the hand-off to the wire. No migration rewrites such a row; it keeps its spelling until a write sends `cidr`.
- **One uvicorn worker.** The image's `CMD` is `python -m app.serve` (`api/app/serve.py`): uvicorn's own command line, so options and `UVICORN_*` variables apply as they did, with `serve.PINNED` laid over what it parsed (one worker, no reloader, `header_limit.HeaderLimitProtocol`, no HTTP/2, no WebSocket, the 5 s keep-alive), so `WEB_CONCURRENCY`, `UVICORN_WORKERS` or `UVICORN_RELOAD` in the environment cannot raise the process count (`test_the_image_runs_one_worker_whatever_the_environment_says`, `test_the_image_command_takes_uvicorn_settings_from_the_environment_but_not_the_pinned_ones`; no other worker count, no replicas). It is also how the image gets the limits of `header_limit` (the body-cap bullet), which uvicorn's `--http` cannot name, so the image is never started as plain `uvicorn`: MCP session state is per-process memory and SQLite has one writer. Reason in the brief §2.2; backup and restore procedure in `docs/backup-and-restore.md`.
- **Bulk endpoints report per-record results** (`created`/`skipped`/`error` + reason) and never abort the batch on a bad record. A host row over a length limit (a domain over `ipnet.DOMAIN_MAX`, 253; `notes` over `schemas.HOST_NOTES_MAX`, 4,096, checked by `services/hosts._check_notes` on every host write) is that row's `error` from the UI, REST and MCP alike (`test_length_limits.py`), never a refused import. The limits bound one host, not a request: an import over the body cap is still refused whole with `413`, and the import dialog measures it first (`utils/csv.importSize`) rather than sending a file in parts. An update that resends notes stored longer before the limit, unchanged, is let through.
- Frontend: shared reference data (sections, subnets, device types) comes from `TreeContext` (`web/src/context.jsx`) — call `refreshTree()` after any mutation that affects it. Checkboxes use the `.tlg-check` class; device icons come from the `ICONS` registry in `DeviceIcon.jsx`.

## Gotchas

- `/mcp` must work **without** a trailing slash (`MCPPathRewriteMiddleware` in `main.py`) — `mcp-remote` and most MCP clients request the bare path, and the SPA catch-all would otherwise swallow it. `test_mcp_reachable_without_trailing_slash` guards this.
- Some MCP clients (Claude Desktop, for one) snapshot the tool list at connect time — after server restarts that change tools, fully restart the client app (Cmd+Q, not just closing the window).
- The repo uses placeholder domains (`home.arpa`, `example.com`) in code, docs, and tests. Do not introduce the user's real domains.
